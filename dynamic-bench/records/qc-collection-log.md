# 레일 QC 수집 일지

> 한 줄 요지: **레일 시험(GNSS-1 · FIRMWARE-1 · FIRMWARE-2 등)이 QC 로 쓸모 있는지 가리려고, 셀 세트를 바꿔 가며 같은 절차로 데이터를 모은다.** 이 문서는 PC 나 세션이 사라져도 흐름을 잃지 않도록, 날마다 무엇을 어떤 조건으로 돌렸고 무엇이 남았는지를 적는다. 원본 데이터 위치와 다음 할 일도 여기 있다.

> 이름: 2026-11-12 부터 시험은 시험 ID 로 부른다([`../design/qc-tests.md`](../design/qc-tests.md)). 아래 3절 이후의 11-11 까지 기록은 그때 이름 그대로 둔다 — **A = 셀 정지(지금 GNSS-1 판정), C = 레일 가속도 운전(지금 FIRMWARE-1), B = 레일 + 움직이는 장면(지금 FIRMWARE-2)**, B300 · B100 · B500 은 FIRMWARE-2 의 300 · 100 · 500 mm/s 다. 기록 폴더 이름(`collect_` · `collectA_` · `railC_` · `railB_` …)도 바꾸지 않는다.

## 1. 목적과 판단 기준

목적은 셀 값이 세트끼리 같은지가 아니라, **시험의 성질이 세트가 바뀌어도 같은지**를 보는 것이다(2026-11-05 사용자). 그래서 세 가지를 세트마다 같은 방법으로 잰다.

| 무엇 | 어떻게 | 쓸모 있다는 뜻 |
|---|---|---|
| 구분력 | 항목마다 같은 셀을 다시 쟀을 때의 흔들림 ÷ 셀끼리 차이 (`motionbench/qc_criteria.py`) | 0.5 이하 — 시험이 셀을 가른다 |
| 불합격이 무엇을 따라가나 | 같은 셀이 자리를 바꿔도 다시 걸리는지, 같은 회차 · 칸에 몰리는지 | 셀을 따라가면 셀 판정에 쓸 수 있다. 칸 · 회차를 따라가면 장비 · 환경 문제다 |
| 장비 무효 비율 | 레일과 장면 출발 차 ±1.0초 밖, 셀 GPS 시각 없음 | 낮고 원인이 설명되면 장비가 안정적이다 |

## 2. 한 바퀴의 절차 (세트마다 같게)

FIRMWARE-1(50 mm/s²) 10번 → FIRMWARE-2 300 · 100 · 500 mm/s 각 10번 → 셀 정지 30분(GNSS-1 로 판정, 5분 구간 6개). 독 플러그는 시험 중 끈다(방전 상태). 1바퀴는 원래 자리, 2바퀴는 자리 바꾸기(1열↔3열 · 2열↔4열, 열 안 위아래 뒤집기 — `dock_layout.json` 의 `<세트>-swap`). 실행기는 `cell-bench/tools/qc_loop.py <배치> <앞 바퀴 번호> [수집 폴더]` 이고(바퀴 폴더 안 운전 폴더는 `FIRMWARE-1_a50` · `FIRMWARE-2_v<속도>`, 11-11 까지는 `C` · `B<속도>`), FIRMWARE-2 는 장면을 바꿀 때마다 셀이 GPS 를 잡을 때까지 5분까지 기다린다(90초에 못 잡은 셀은 원격 재부팅. `--no-reboot` 를 주면 재부팅 없이 10분까지 — X5E 부터). 판정은 기준 없이(`--criteria none`) 내고, 멈춘 회차는 판정에서 빠지며 정상 10번이 될 때까지 다시 돈다. 정지 구간은 이 수집의 조건(꽉 찬 독 · 감쇠 0)이다 — GNSS-1 의 2026-11-11 확정 방식(독 1 · 3행 · 장면 구간 고정 · 감쇠 18 dB)은 `cell-bench/tools/qc_tests/gnss1_run.py` 로 따로 돈다.

### X5E 세트 — CLBX-5E 24대, 34349 ~ 34354 · 34357 ~ 34374, 1열 위부터 차례대로 (2026-11-06)

- 1바퀴(r01, 원래 자리 X5E, 11:40 ~ 13:40): B300 앞에서 위치를 못 잡은 셀을 원격 재부팅했더니 23대 중 6대만 측정으로 돌아와 B 는 16 ~ 18대로 돌았다. 34349 · 34350 은 재부팅 뒤 안 들려 기록을 못 받았다(셀 안에 남아 있다).

- 3바퀴(r03, X5E-swap — 2바퀴와 같은 자리, 17:26 ~ 19:53): 충전(16:20 ~ 17:13, 91 ~ 98 %) 뒤 20대로 돌았다. 34349 · 34350 · 34369 · 34370 은 그 앞 기록 받기 뒤 측정으로 돌아오지 않아 빠졌다. B 는 재부팅 없이 10분 기다려 B300 16 · B100 18 · B500 17대가 위치를 잡고 시작했다. A 앞에서 못 잡은 34358 · 34361 을 원격 재부팅했더니 2대 모두 돌아와 20대로 30분을 끝까지 돌았다(가장 낮은 셀 67 %). 기록은 20대 모두 받았다(`data/ftg_x5e_20261106-194510`).
- 다시 판정: 1 · 2바퀴를 그날 받은 기록 네 묶음(`ftg_x5e_20261106-133334` · `-155837` · `ftg_x5e-swap_20261106-171524` · `ftg_x5e_20261106-194510`)으로 다시 판정해, 바퀴 · 시험마다 들린 셀은 모두 셀 기록까지 붙었다(1 · 2바퀴 C · B 24대, 2바퀴 A 20대). 꺼졌던 셀의 기록은 모두 받았다.
- 판정(기준 없이): 세 바퀴 모두 강한 기준 셋(A 위치 수신률 · B 신호 세기 · B300 속도 비율)과 셀 기록 항목은 불합격 0건이다. 불합격은 전부 라이브 수신(rx)이다.

  | 바퀴 · 시작 | C | B300 | B100 | B500 | A |
  |---|---|---|---|---|---|
  | 1바퀴 11:38 | 164 / 240 (24대) | 0 / 144 (16대) | 0 / 152 (16 ~ 17대) | 0 / 157 (17 ~ 18대) | 12 / 132 (22대) |
  | 2바퀴 13:49 | 66 / 240 (24대) | 49 / 216 (24대) | 35 / 216 (24대) | 2 / 168 (24대) | 28 / 95 (12 ~ 20대) |
  | 3바퀴 17:26 | 0 / 200 (20대) | 6 / 180 (20대) | 16 / 180 (20대) | 0 / 180 (20대) | 14 / 120 (20대) |

  괄호 안은 그 회차에 라이브를 보낸 셀 수다.
  - **rx 불합격은 셀도 칸도 아니라, 동시에 라이브를 보내는 셀 수를 따라간다.** A 를 뺀 회차를 셀 수로 묶으면 18대 이하 0 / 453, 19 ~ 22대 22 / 740(3 %), 24대 316 / 1080(29 %)이다. 셀마다 불합격 비율을 바퀴끼리 비교하면 같은 셀 · 같은 칸(2 ↔ 3바퀴) 상관이 −0.01, 같은 셀 · 다른 칸(1 ↔ 3바퀴) −0.06, 같은 칸 · 다른 셀 −0.17 로 셀 탓도 칸 탓도 아니다. 1 · 2바퀴만 보고 낸 앞의 분석(독 자리 1 ~ 3열 위쪽을 따른다)은 3바퀴를 더하자 성립하지 않았다.
  - 다만 24대에서도 회차마다 크게 달라(1바퀴 C 68 %, 2바퀴 C 28 %, 2바퀴 B500 1 %) 셀 수만으로 다 설명되지 않는다 — 그 시각의 무선 환경도 섞여 있다. LiveHub 한 대가 24대를 받는 데서 패킷이 빠지는 것으로 보이나, 허브 쪽 원인은 확인하지 못했다.
  - 그래서 지금의 rx 는 셀 품질이 아니라 수신 장비 · 환경을 잰다. 합불에서 뗄지는 사용자 결정 대기다(바꾸지 않았다).
  - 2바퀴 A 의 rx 불합격은 배터리로 꺼진 셀과 A 시작 때 재부팅한 셀(34357 · 34359 · 34362 · 34369 는 6구간 모두)이 섞여 있어 셀 품질과 따로 본다.
- 셀 기록 지우기(0x13)는 X5E 도 거의 응답하지 않는다(1바퀴 22대 중 1대, 2바퀴 9대 중 1대, 3바퀴 20대 중 0대 지움). 셀 저장량은 1바퀴 뒤 3 ~ 13 MB 로 측정이 멈추는 약 160 MB(Y 실측)까지는 멀다.

### X 대 Y 첫 비교 (2026-11-06 새벽, 3바퀴 전체와 재부팅 뒤만)

같은 방법(`motionbench/qc_criteria.derive`, 기준 파일은 쓰지 않음)으로 쟀다. 오염 의심 회차(11-05 17:15 재부팅 전, 메모리 누수 상태)는 지우지 않고 '재부팅 뒤만' 결과를 따로 냈다. 계산 스크립트와 전체 표는 아래 5절의 `compare_xy.md`.

|---|---|---|---|---|
| A | 0 % | 6.2 % (4회 중 1회) | 0 / 828 | 1 / 360 |
| C | 0 % | 3.3 % (5 %) | 74 / 460 | 7 / 696 |
| B300 | 15 % | 16.7 % (10 %) | 18 / 391 | 2 / 600 |

- **구분력:** Y 에서 낸 강한 기준 셋이 X 에서도 자격(0.5 이하)을 유지한다 — B 신호 세기 0.44 · 0.39 · 0.47, B300 속도 비율 0.34. A 위치 수신률은 X 가 모두 100 % 라 흔들림 자체가 없다. 다만 X 는 대부분 항목에서 셀끼리 차이가 바닥값에 붙어 있다. 셀이 서로 거의 같다는 뜻이어서, 이 데이터만으로 '나쁜 셀을 잡는 힘'이 증명되지는 않는다.
- **불합격이 따라가는 것:** 걸린 항목은 모두 라이브 수신(rx)이다. 11580 이 C 에서 5번 걸렸는데 원래 칸(2-5)과 바꾼 칸(4-2) 양쪽에서 걸렸다 — 셀을 따라가므로 셀 탓이다(Y 의 10697 과 같은 꼴). 나머지는 셀 · 회차가 제각각이다.
- **장비 무효:** 재부팅 뒤에는 B 묶음마다 장면을 바꾼 첫 회차 1번(출발 차 약 −3.3초, 알려진 현상), C 도달 오차 13 µm 1번, A 끊긴 구간 1번뿐이다. 재부팅 전에는 플러그 호출 지연(+34초 · +17초 · −19초)이 더 있었다. 재부팅 전후 값 차이는 작다 — 누수의 영향은 값보다 멈춤 쪽이었다.

| PC 메모리 누수(11-02 부팅 뒤 사흘 — 남은 메모리 2 GB, 비페이징 풀 2.9 GB) | 주기 지연 멈춤의 유력 원인. 재부팅으로 풀린다('종료'가 아니라 '다시 시작'). 11-05 ~ 06 밤 시험 두 번(`collect_20261105/leak_test.log` · `leak_test2.log`)으로, 1초마다 파일을 새로 써 바꿔 끼우는 일을 **C:\Dev 안에서 하면** 파일 감시 쪽 커널 메모리가 40 ~ 50분에 43 ~ 265 MB 늘고, **C:\Dev 밖에서 하면 늘지 않는다**는 것을 확인했다. 쓰는 방식(새 이름 · 같은 이름 · 덮어쓰기)은 차이를 가르지 않았고, 기록 파일처럼 한 파일에 이어 쓰는 것은 늘지 않았다. 그래서 1초마다 다시 쓰는 실시간 파일(`qc_now.json` · `rail_batt.json`)을 `%LOCALAPPDATA%\cellbench\live` 로 옮겼다(PR #40). C:\Dev 를 감시하는 드라이버 쪽은 손대지 않고 IT 에 확인을 요청한다. **11-06 수집 날 실기 확인:** 파일 감시 쪽 풀(FMsc · FMsl · File · CBfs)은 시험이 도는 내내 늘지 않았다(FMsc 11-05 저녁 30분에 30 → 115 MB, 11-06 11:16 ~ 16:01 은 33 → 34 MB). 대신 다른 풀 Proc(끝난 프로세스의 개체)가 11-05 23:16 58 MB 에서 11-06 16:16 249 MB 로, MiP2 가 25 → 107 MB 로 늘었고, 비페이징 풀 전체는 시험 중 9시간에 1,921 → 2,304 MB 늘었다. Proc 를 누가 붙잡는지는 확인하지 못했다 |

| 기록 받기로 깨운 셀 일부가 측정으로 돌아오지 않는다(11-06 17:15 받기 뒤 34349 · 34350 · 34369 · 34370) | 실행기는 들리는 셀로만 돈다. 사람이 셀을 껐다 켠다 |

| X 셀 배터리 % 는 40 %대에서 20분 안에 0 % 로 떨어지고 꺼진다(11-06 2바퀴 A) | 실행기의 잔량 기준(시작 30 % · 멈춤 20 % · 바퀴 사이 35 %)은 Y 에 맞춘 것이고, 들리는 셀만 계산해 꺼진 셀은 빠진다. 바퀴는 꽉 채운 뒤에만 시작한다. 시험 사이 셀 상태 점검(꺼진 셀 · 잔량 · 저장량)은 아직 없다 |
| X 셀은 독에서 충전되는 동안 라이브를 보내지 않는다 | PC 는 충전이 끝났는지 모른다 — Tapo 앱 전력으로 사람이 본다. 지그비 플러그(전력 측정)로 바꾸면 PC 가 판단한다 |
| 기록 받기는 시작 순간 들리는 셀만 받는다 | 꺼진 셀은 충전 뒤 따로 받는다(기록은 셀 안에 남는다) |
| 모터가 도는 동안 같은 PC 의 무거운 일 | 주기 지연 멈춤을 부른다 — 분석 · 시험 · 큰 파일 복사는 모터가 멈췄을 때만 |
