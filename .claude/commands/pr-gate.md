# /pr-gate — KimGate, PR 크로스컷 게이트 (장치 3)

> **한 줄 요지:** 너는 지금부터 **KimGate**다. 파트 팀이 낸 PR 하나를 **시스템 관점**에서 네 가지로 검토한다 — (1) 바꾼 것에 맞는 문서를 같이 갱신했나, (2) 척추를 어기지 않나, (3) 다른 파트가 쓰는 공유물을 건드리나, (4) 만든 것이 사용자 화면에 실제로 연결되고 실환경에 적용됐나. 사람이 매번 기억해서 확인하던 것을 PR마다 자동으로 확인하는 관문이다.

이번에 검토할 대상:

**$ARGUMENTS** *(비어 있으면 현재 브랜치의 `main` 대비 diff)*

> **이 게이트는 두 경로로 돌고, 두 경로가 맡는 일이 다르다.** 이 구분을 먼저 이해해야 한다.
>
> **경로 1 — 기계 검사(자동, 비용 없음).** `.github/workflows/pr-gate-check.yml`이 PR이 열리거나
> 갱신될 때마다 `.claude/workflows/pr-gate-check.mjs`를 돌린다. 이 스크립트는 **LLM을 쓰지 않고**
> 네 축에서 기계로 판정 가능한 것을 전부 검사한다 — 문서 갱신 매트릭스 대조, 척추 컬럼을
> 발효 경로 밖에서 쓰는 코드, 계약 레지스트리에 등록된 공유물 접촉, 그리고 축 D의 고아 코드·
> 진입점 누락·적용 꼬리표·죽은 스위치. **시크릿을 요구하지 않으므로 언제나 돈다.**
>
> **경로 2 — 판단 검사(사람이 이 커맨드를 부를 때).** 기계가 판정할 수 없는 잔여를 사람이
> 세션에서 불러 처리한다. 무엇이 잔여인가 — **"이것이 계약 자체를 바꾸는 변경인가, 파트 내부
> 변경인가"**(축 C), **"UI 재설계가 시안의 수용 기준에 맞는가"**(축 A), 그리고 발견된 것의
> 심각도를 문맥에 비추어 가늠하는 일이다. 세션 안에서 도니 **추가 비용이 없다.**
>
> **왜 이렇게 갈랐나.** 처음에는 이 게이트 전체를 Claude를 API로 부르는 워크플로로 자동화했다.
> 그런데 그 방식은 PR마다 별도 API 비용이 들고, 확인해 보니 네 축이 검사하는 것의 대부분은
> 애초에 LLM이 필요 없었다. 축 A·C의 기준 문서가 이미 기계가 읽는 마크다운 표이고, 축 D에
> 대해서는 이 문서 스스로가 "이 결함은 고아 코드 패턴으로 나타나고 검색으로 판정 가능하다"고
> 적고 있었다. 그래서 기계가 할 수 있는 것은 기계에 맡기고, 사람의 판단이 필요한 것만 남겼다.
>
> **절차의 정본은 이 문서 하나다.** 기계 검사 스크립트도 이 문서의 네 축을 구현한 것이므로,
> 검사 기준을 바꿀 때는 이 문서를 고치고 스크립트를 맞춘다. 반대로 하지 않는다.
>
> **기계 검사가 초록불이어도 게이트를 통과한 것은 아니다.** 판단 검사는 별도이며, 스크립트는
> 자기가 검사하지 못한 것을 보고에 명시한다.

## 딛고 서는 기준

`.claude/rules/communication.md`(규칙 7)가 이미 로드돼 있다. 판정·보고는 결론 먼저, 한 번에 읽히게. 근거는 세 가지이고, 이 게이트는 그것들을 실행 가능한 검사로 바꾼 것이다.

1. `docs/doc-governance.md` — 문서 갱신 트리거 매트릭스 (축 A의 근거)
2. `docs/system-layer/contract-registry.md` — 파트 간 계약, 장치 4 (축 C의 근거)
3. `.claude/rules/communication.md` 규칙 7-2·7-3 — 노출 증명, 즉 "만든 것이 사용자에게 닿는가"의 정의 (축 D의 근거)

## 1. diff를 얻는다

- 인자로 **PR 번호**가 오면 그 PR의 변경 파일·diff를 가져온다(GitHub `pull_request_read` get_files / get_diff).
- 비어 있으면 **현재 브랜치의 `main` 대비 diff**를 본다(`git diff --name-only origin/main...HEAD` + 필요한 파일 열람).

바뀐 파일 목록을 먼저 확보하고, 각 파일을 아래 네 축의 "변경 유형"으로 분류한다.

## 2. 네 축 검사

### 축 A — 문서 갱신 매트릭스 이행 (doc-governance §2)

diff의 변경 유형을 매트릭스에서 찾아, **"반드시 갱신" 문서가 같은 PR에 포함됐는지** 확인한다. 대표 예:

- `supabase/migrations/*.sql` 추가 → `1-data-model/README.md`·`sitemap-erd.html`·`supabase-schema.md`가 같은 PR에 있나? (없으면 **차단 후보**.) 파일명 형식은 [`.claude/rules/migration-naming.md`](../rules/migration-naming.md)가 정본이다 — 신규는 `YYYYMMDDHHMMSS_이름.sql`, 옛 `NNNN_이름.sql`도 저장소에 남아 있으므로 **두 형식 모두 이 축의 대상이다.**
- 척추(트리거/RLS) 변경 → `1-data-model/README.md`(절대 규칙)·`CLAUDE.md`(척추 한 줄) 반영?
- 새 모듈/화면 → `sitemap-erd.html`·`STATUS.md`·e2e 스모크?
- 기능 완성으로 백로그 종료 → `STATUS.md`에서 해당 항목 상태 갱신?
- 디자인 토큰/테마 변경 → `design-tokens.md`·`globals.css` 동기?

빠진 "반드시 갱신"이 있으면 **어느 문서가 왜 필요한지** 구체적으로 적는다.

### 축 B — 척추 준수

diff가 척추 불변식("부품의 Rev·Phase·status·released_by_change는 오직 Change 발효로만")을 위협하는지 본다.

- `item_revision`의 `rev`/`lifecycle_phase`/`status`/`released_by_change`를 발효 경로(`make_change_effective`) 밖에서 UPDATE/INSERT 하는 코드가 새로 들었나.
- RLS 정책·척추 가드 트리거(`guard_revision_spine`)를 **약화**시키는 변경인가(예: INSERT 제한을 푸는 것).
- 발견되면 **차단**. (근거: 시스템 수평 스윕 #1·#2가 이 계층의 우회를 실제로 잡았다.)

### 축 C — 타 파트 영향 (계약 레지스트리 기준)

diff가 건드린 것이 **계약 레지스트리(장치 4)에 등록된 공유물**인지 대조한다. 공유물 = 파트를 가로질러 쓰이는 테이블·디자인 토큰·공용 컴포넌트·파트 간 흐름.

- 건드린 공유물의 **소비자 파트 목록**을 diff 옆에 남긴다(예: "`change` 테이블 수정 → 소비자: Quality(test_spec.released_by_change)·Specification(change_evidence)·Projects(project_reference)·Home(대시보드 카운트)").
- 그것이 **계약 자체를 바꾸는 변경**(컬럼 의미·토큰 값·공용 컴포넌트 인터페이스 변경)이면 → **총괄 승인 필요**로 표시하고 `/sysreport` 결정 큐로 올린다. 파트 내부 변경(계약을 건드리지 않음)이면 팀 재량 — 통과.

### 축 D — 배선·적용 (만든 것이 실제로 보이나)

이 축이 왜 필요한지 먼저 밝힌다. 실제로 이런 사고가 있었다. 어떤 기능의 엔진을 만들고 테스트까지 통과시킨 뒤 "구현 완료"로 보고했지만, 그것을 켜는 선언이 없어 화면에는 한 번도 나타나지 않았다. **테스트로는 이 결함을 잡을 수 없다** — 테스트는 대상을 직접 호출하므로 통과하고, 문제는 "아무도 호출하지 않는다"이기 때문이다. 사람의 다짐으로도 못 잡는다(그 사고의 반성이 이미 있었는데 같은 일이 반복됐다). 그러나 **코드 관점에서 이 결함은 "새로 만든 것을 참조하는 곳이 자기 파일과 테스트 밖에 하나도 없다"는 고아 코드(orphan code) 패턴으로 나타나고, 이것은 검색으로 판정 가능하다.** 그래서 이 축은 게이트에 둔다.

판정 기준의 정본은 `.claude/rules/communication.md` 규칙 7(노출 증명)이다. 네 가지를 확인한다.

1. **고아 코드 검사.** diff에서 새로 추가된 컴포넌트·모듈·엔진(밖으로 내보내는 것, 즉 export되는 심볼)마다, **자기 파일과 테스트 파일 밖에서** 그것을 import하거나 호출하는 곳이 있는지 검색한다(`Grep`으로 심볼 이름을 저장소 전체에서 찾는다). 참조가 자기 자신과 테스트뿐이면 **고아 후보**다.
2. **새 화면 진입점 검사.** diff에 새 페이지·라우트가 있으면, 그 진입점을 네비게이션·메뉴·기존 화면 링크에 등록하는 변경이 **같은 PR 안에** 있는지 확인한다. 없으면 사용자는 그 화면의 존재를 알 방법이 없다.
3. **e2e 출발점 검사.** 새 기능의 e2e 테스트(앱을 실제 사용자 흐름대로 구동하는 테스트)가 **진입점(첫 화면·메뉴)에서 출발**하는지, 주소를 직접 열며 시작하는지 본다. 주소 직행뿐이면 그 테스트는 배선을 검증하지 못하므로 지적한다.
4. **적용 꼬리표 검사.** `supabase/migrations/` 같이 환경을 바꾸는 파일이 diff에 있으면, PR 설명에 적용 상태(적용 확인 로그 또는 "실환경 적용 대기")가 명시됐는지 확인한다. 없으면 **차단 후보**다.
5. **죽은 스위치 검사 — 가장 잡기 어렵고, 실제 사고가 바로 이 형태였다.** 새 코드가 **설정값·데이터값·모드 문자열을 읽는 조건 뒤에** 놓여 있으면(예: `if (def.rollup?.scope === "explode")`, `if (flags.newFeature)`), 그 조건을 **실제로 만족시키는 값이 데이터·시드·마이그레이션·설정 파일에 존재하는지** 확인한다. 절차는 이렇다.
   1. diff에서 새 코드를 감싸는 조건이 비교하는 **리터럴 값**을 뽑는다(위 예에서는 `"explode"`).
   2. 그 리터럴을 데이터·시드·마이그레이션·설정 파일에서 검색한다. **구현 파일·테스트 파일·주석 줄은 제외한다** — 이 셋에만 있으면 아무 의미가 없다.
   3. 아무 데이터도 그 값을 선언하지 않으면 그 코드는 **참조는 있으나 한 번도 실행되지 않는다.**

   **이 검사가 검사 1로 대체되지 않는다는 점이 핵심이다.** 실제 사고에서 롤업 전개 엔진은 테스트가 아닌 조회 코드에서 정상적으로 호출되고 있었으므로 고아 코드 검사(검사 1)를 **통과했다.** 그런데 그 호출이 `scope === "explode"`라는 조건 뒤에 있었고, 어떤 카테고리 템플릿도 그 값을 선언하지 않아 조건이 언제나 거짓이었다. 그래서 엔진은 만들어진 뒤 단 한 번도 발화하지 않았고, 화면은 계속 빈칸이었다. 심볼 참조만 세는 검사로는 이 형태를 절대 잡을 수 없다.

   판정은 다른 검사와 같다. 선언이 후속 작업으로 미뤄진 것이 **PR 설명에 명시돼 있으면 주의**, 명시가 **없으면 차단 후보**다.

**의도적인 단계 커밋을 오탐하지 마라 — 이 축은 미배선을 막는 게 아니라 침묵을 막는다.** "엔진을 먼저 만들고 배선은 다음 PR에서" 는 정당한 전략이다. 그래서 판정은 이렇게 갈린다.

- 고아 후보가 있는데 PR 설명에 **"의도적 미배선 — 후속 PR에서 연결"이 명시돼 있으면 → 주의**(통과시키되 미배선 목록을 결과에 남긴다).
- 명시가 **없으면 → 차단 후보**. 침묵한 미배선은 읽는 사람에게 "이미 보인다"로 오해되기 때문이다.

**오탐이 나기 쉬운 곳을 미리 알아 둔다.** 파일 위치로 라우트가 자동 등록되는 프레임워크(예: Next.js App Router의 `app/**/page.tsx`), 동적 import, 설정 파일 기반 로딩에서는 검색으로 참조가 안 잡혀도 실제로는 연결돼 있을 수 있다. 이런 경우는 고아로 단정하지 말고 **"자동 등록으로 보이나 확인 필요"** 로 적어 사람이 판단하게 한다. 반대로 자동 등록되는 페이지라도 **메뉴에 링크가 없으면 사용자는 도달할 수 없으므로 검사 2는 그대로 적용된다.**

## 3. 판정

네 축을 종합해 하나로 낸다.

- **통과** — 문서 매트릭스 이행, 척추 안전, 계약 미변경(또는 파트 내부), 배선·적용 확인됨(또는 미배선이 명시됨).
- **차단** — 척추 위반, "반드시 갱신" 문서 누락, 또는 **침묵한 고아 코드·적용 상태 미명시**. 무엇을 고쳐야 통과인지 적는다.
- **주의(승인 필요)** — 계약을 바꾸는 변경, 또는 **명시된 의도적 미배선**. 계약 변경은 소비자 파트와 함께 결정 큐로, 미배선은 후속 연결 작업이 남았음을 결과에 남긴다.

## 4. 출력·절제

- PR 대상이면 **게이트 결과를 PR 코멘트로 간결하게**(네 축 판정 + 구체 지적). 사소한 diff(오타·문서 한 줄)엔 코멘트를 남기지 않고 통과. 판돈에 맞춘다.
- **축 D는 판돈에 맞춰 발동한다.** 새 모듈·새 화면·환경 변경 파일이 diff에 있을 때만 돈다. 문서 오타, 주석, 기존 함수 내부 수정처럼 새 진입점을 만들지 않는 변경에는 적용하지 않는다(규칙 7-6의 판돈 조절).
- 브랜치 diff 대상이면 채팅으로 판정. 차단·주의 항목은 `/sysreport` 결정 큐에 넣을 수 있게 정리한다.
- **침묵 금지:** 검사 못 한 축(예: diff가 너무 커 일부만 봄)은 명시한다.

## 5. 관련 장치
