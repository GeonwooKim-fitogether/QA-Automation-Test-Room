# 라이브 DB 우선 규칙 — 제품·부품 사실은 라이브 데이터베이스에서 먼저 읽는다

> 한 줄 요지: **부품 사양·BOM·리비전·첨부 같은 제품 사실은 그 저장소가 가리키는 라이브 데이터베이스가 정본이다.** Google Drive·공유 폴더·내려받은 zip 은 그 DB 가 가리키는 파일 창고이거나 옛 사본이므로, **DB 에서 먼저 찾고, DB 에 없을 때만 사용자에게 알리고 확인을 받은 뒤** 다른 곳을 뒤진다.

여기서 "라이브 DB" 는 그 저장소의 `CLAUDE.md` 가 밝히는 운영 데이터베이스(예: Hardware-Team-System 의 Supabase `hardware-team-system`)를 말하고, "제품 사실" 은 품목·리비전·BOM·사양값·첨부 파일·변경(ECO)처럼 **그 DB 가 관리하도록 만들어진 것**을 말한다.

## 왜 이 규칙이 있나

2026-10-08, 셀 배터리의 온도 사양을 확인하면서 세션이 Google Drive 의 `HTS/Items` 폴더를 먼저 뒤졌다. 어제 펌웨어 zip 을 그 경로에서 찾았던 습관이었다. 사용자가 "라이브 DB 가 정본 아니냐"고 짚은 뒤 DB 를 읽어 보니, Drive 사양서에 없던 값(보관 습도 0~75 %RH)과 **어느 셀 모델이 어느 배터리를 쓰는지**(BOM)가 DB 에만 있었다. Drive 는 DB 의 `file` 테이블이 가리키는 파일 창고일 뿐이었고, 리비전마다 같은 PDF 가 중복 저장돼 있어 **어느 것이 현행인지 Drive 만 봐서는 알 수 없었다.**

오류는 없었다. Drive 의 PDF 도 "맞는" 문서였기 때문이다. 문제는 **정본이 아닌 곳에서 먼저 답을 찾으면, 정본에만 있는 사실을 놓친 채 확신하게 된다**는 것이다. Fitstack 에서도 같은 습관(파일 먼저, DB 나중)이 반복돼 왔다.

## 규칙

1. **순서는 DB → 그다음.** 제품 사실을 찾을 때는 라이브 DB 조회(`select`)를 먼저 한다. 조회는 [데이터베이스 쓰기 규칙](./db-write-permission.md)대로 확인 창 없이 실행된다.
2. **DB 에 없으면 멈추고 알린다.** "DB 에 이 항목이 없다 — Drive(또는 다른 곳)를 찾아볼까?" 라고 묻고, **확인을 받은 뒤** 다른 곳을 뒤진다. DB 에 없다는 사실 자체가 보고할 정보다(등록 누락일 수 있다).
3. **파일은 DB 를 통해 간다.** 첨부 파일이 필요하면 DB 의 파일 표(`file`·`attachment` 등)가 가리키는 경로를 쓴다. 폴더를 직접 훑어 "이름이 비슷한 파일" 을 고르지 않는다 — 리비전마다 사본이 있어 옛 것을 집기 쉽다.
4. **출처를 적는다.** 보고에는 어느 DB 의 어느 표·어느 리비전에서 읽었는지 적는다. Drive 에서 읽었다면 그 사실과 확인받은 사실을 함께 적는다.
5. **DB 가 없는 저장소에는 적용되지 않는다.** `CLAUDE.md` 가 라이브 DB 를 밝히지 않는 저장소에서는 파일이 정본이다.

## 적용 범위

- 라이브 데이터베이스가 있는 저장소의 모든 세션에 적용된다. 그 DB 가 무엇인지는 각 저장소의 `CLAUDE.md` 가 맨 위에서 밝힌다.
- 단일 원본은 창고(Template-repository)의 `.claude/rules/live-db-first.md` 다. 여기서만 고치고, 동기화 봇이 내려보낸다.
