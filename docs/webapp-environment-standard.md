# 웹앱 환경·데이터베이스 운영 표준

## 목적

개발자와 에이전트가 운영 데이터베이스를 직접 실험 장소로 사용하지 않게 하고, 변경을 local → development → staging → production 순서로 검증한다. AWS·Supabase·Vercel 중 무엇을 사용하더라도 같은 승인 흐름을 유지하는 것이 목적이다.

## 환경별 역할

| 환경 | 설명 | 데이터 | 변경 권한 | 필수 조건 |
|---|---|---|---|---|
| local | 각 작업자의 컴퓨터에서 실행 | 합성·테스트 데이터 | 자유 | Docker로 재생성 가능 |
| development | 여러 작업을 합쳐 보는 비운영 환경 | 합성·비식별 데이터 | 자동화된 적용 경로 | CI 통과 |
| staging | 실제 배포 직전 리허설 | 운영과 형태가 같은 비식별 데이터 | 제한적 | 운영과 같은 배포 절차 |
| production | 실제 고객이 사용하는 환경 | 실제 데이터 | 승인된 담당자 | 백업·영향·복구 계획·사람 승인 |

초기 소규모 프로젝트는 development와 staging을 하나의 비운영 환경으로 합쳐도 된다. 사용자가 생기거나 배포 빈도가 높아져 리허설과 일상 개발이 충돌하면 분리한다.

## 권장 최소 구성

- local: Docker PostgreSQL
- non-production: AWS의 별도 비운영 DB 또는 별도 관리형 프로젝트
- production: 기존 운영 DB
- GitHub: 코드, 마이그레이션, 검증 기록, 승인 요청의 단일 장부

비운영 DB를 비용 때문에 공유한다면 프로젝트별 데이터베이스와 사용자 계정을 분리한다. production은 비운영 인스턴스와 공유하지 않는다.

## 변경 흐름

1. 작업 브랜치에서 코드와 마이그레이션을 함께 작성한다.
2. local DB를 비운 뒤 전체 마이그레이션을 처음부터 적용한다.
3. 자동 테스트와 핵심 사용자 흐름을 확인한다.
4. DB 변경 요청서를 포함해 PR을 연다.
5. CI 통과 후 development에 적용한다.
6. 필요하면 staging에서 같은 산출물을 검증한다.
7. 운영 담당자가 백업과 영향 범위를 확인한다.
8. 사람 승인 후 production에 적용한다.
9. 적용 직후 API·화면·핵심 쿼리와 오류율을 확인한다.

## 금지 사항

- 운영 콘솔에서 시험 SQL 실행
- 운영 비밀번호를 `.env`, PR, 채팅, 로그에 기록
- 운영 데이터를 그대로 local/development에 복사
- 검증되지 않은 마이그레이션을 운영에 먼저 적용
- 실패 시 절차가 없는 파괴적 변경
- 환경 이름만 믿고 실제 연결 대상 확인을 생략

## 서버를 별도로 만들어야 하는 경우

로컬에서 화면·API·DB가 모두 동작하면 서버를 추가하지 않는다. 아래 경우에만 비운영 원격 서버를 검토한다.

- 외부 서비스가 호출할 공개 URL이 필요함
- 여러 사람이 같은 환경에서 QA해야 함
- 예약 작업·큐·이메일·푸시를 실제처럼 시험해야 함
- AWS IAM, S3, Lambda 등 AWS 전용 연결을 시험해야 함

## 프로젝트에 적용할 산출물

`templates/webapp-environment/`에는 다음 시작 파일이 있다.

- `.env.example`: 환경변수 계약
- `compose.local.yml`: 로컬 PostgreSQL
- `db/migrations/README.md`: 마이그레이션 규칙
- DB 변경 PR 템플릿

각 서비스에 적용할 때는 프레임워크의 실행 명령과 DB 도구만 맞추고 환경 경계와 승인 조건은 바꾸지 않는다.
