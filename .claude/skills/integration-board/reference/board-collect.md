# 자동 수집 — GitHub의 사실로 보드를 스스로 갱신하기

> **한 줄 요지:** 보드가 요구하는 사실의 대부분은 이미 GitHub에 있다. `board-collect.mjs`가 그것을 `board.json`으로 옮기고, 워크플로가 **사건마다**(PR 검사 완료 · main 푸시 · 30분 심장박동) 그것을 돌려 보드를 다시 그린다. 사람이 손으로 옮겨 적을 것은 **GitHub에 없는 세 가지**뿐이고, 그것도 PR 본문에 한 줄로 선언하면 끝난다.

이 문서는 자동 수집을 켜는 방법과 대응표(`board.map.json`)의 규격을 담는다. 보드 자체의 규격(config·data 스키마)은 [`board-schema.md`](./board-schema.md)에 있고, 다 만들어진 보드를 읽는 법은 [`../READING-GUIDE.html`](../READING-GUIDE.html)에 있다.

---

## 1. 무엇이 자동으로 채워지고, 무엇이 사람 선언인가

이 구분이 이 문서에서 가장 중요하다. **자동 수집은 모르는 것을 지어내지 않는다.** GitHub에 없는 사실은 비워 두고, 엔진은 비어 있는 축을 초록이 아니라 회색 "알 수 없다"로 그린다.

| 보드가 요구하는 사실 | 어디서 오나 |
|---|---|
| 작업 목록 · 제목 · 상태 | 열린 PR과 최근 머지된 PR |
| 막힘 — 충돌 | PR의 머지 가능 상태가 `dirty`일 때 |
| 막힘 — 대기 | 리뷰어가 지정돼 있을 때 |
| 며칠째 멈췄나 | PR의 마지막 갱신 시각 |
| 실제 완료일 | 머지 시각 |
| 건드린 공용 자산 | 변경 파일 경로 → `assetByPath` |
| 제품 영역 | 변경 파일 경로 → `areaByPath` |
| 팀 | PR 작성자 → `teamByAuthor` |
| 검사가 이번 회차에 돌았나 | main 최신 커밋의 체크 실행 결과 |
| 위반 목록 | 실패한 체크 (main은 지목 없는 위반, PR은 그 PR을 지목) |
| **계획 시작·종료일** | **PR 본문 선언** (없으면 열린 PR은 "일정 미정"으로 남는다) |
| **진척률** | **PR 본문 선언** (머지된 것은 자동으로 100) |
| **해소 작업** | **PR 본문 선언** (없으면 걸린 검사가 "해소 작업 미보고"로 남는다) |

머지된 요청에는 **실제 구간**(요청 생성 → 머지)을 계획 구간으로 넣는다. 계획이 아니라 실제이지만, 이미 끝난 일을 "일정 미정"으로 몰아 두면 두 가지가 함께 망가진다 — 간트가 최근에 무엇이 나갔는지 보여 주지 못하고, "언제 끝날지 모르는 일" 카드가 이미 끝난 일까지 세어 거짓 경보를 낸다.

### 1-1. PR 본문 선언 — 세 줄

PR 본문 어디든 아래 형태로 한 줄 적으면 그 값이 보드에 올라간다. 안 적으면 그 축은 회색으로 남는다. 영어 이름(`Plan:` · `Progress:` · `Fixes-check:`)도 받는다.

```
계획: 2026-08-01..2026-08-14
진척: 40%
해소: prgate, registry
```

`해소:`에 적는 값은 **config의 `checks` key**다. 없는 key를 적으면 수집기가 그 자리에서 멈추고 쓸 수 있는 key 목록을 보여 준다. 조용히 무시하면 사람은 선언한 줄 알고 있는데 보드는 여전히 "미보고"로 남기 때문이다.

## 2. 켜는 법 — 세 단계

### 1) 설정 두 개를 저장소에 둔다

- `.integration/board.config.json` — 프로젝트의 어휘(팀·영역·자산·검사·카드). 규격은 `board-schema.md` 1절.
- `.integration/board.map.json` — GitHub의 사실을 그 어휘로 옮기는 대응표(3절). `assets/board.map.example.json`을 복사해 시작한다.

`.integration/board.json`(회차 사실)은 **저장소에 두지 않는다.** 사건마다 수집기가 새로 쓰므로, 커밋해 두면 옛 사실과 방금 모은 사실 두 벌이 생기고 화면만 보고는 어느 쪽이 지금인지 알 수 없다.

### 2) 워크플로를 복사한다

`.github/workflows/integration-board.yml`을 프로젝트에 복사한다. 동기화 봇은 `.claude/` 아래만 내려보내므로 이 파일은 저장소마다 한 번 복사해야 한다(같은 저장소의 `pr-gate-check.yml`도 같은 사정이다).

### 3) Pages를 켠다 — 사람이 해야 하는 한 번

저장소 **Settings ▸ Pages ▸ Source**를 **"GitHub Actions"**로 바꾼다. 이것을 안 하면 마지막 게시 단계가 실패한다. 비공개 저장소에서 Pages를 쓰려면 유료 플랜이 필요하며, 못 쓰는 환경이면 워크플로의 게시 두 단계를 지우고 산출물 업로드만 남겨 실행 결과에서 내려받아 본다.

## 3. `board.map.json` 규격

모두 선택이지만, 아래 표에서 **필수**로 적힌 넷이 없으면 수집기가 멈춘다. 대응표가 config에 없는 것을 가리키면 그것도 그 자리에서 멈춘다 — 보드가 만들어진 뒤 엔진이 거부하는 것보다, 무엇이 어긋났는지 이름을 대며 먼저 멈추는 편이 낫다.

```json
{
  "timezone": "Asia/Seoul",
  "recentMergedDays": 14,
  "statusOf": { "draft": "doing", "open": "review", "merged": "shipped" },
  "teamByAuthor": { "github-login": "팀 B" },
  "teamDefault": "팀 B",
  "areaByPath": [ ["app/src/components/change/**", "change"], ["docs/**", "docs"] ],
  "areaDefault": "docs",
  "assetByPath": [ ["docs/design-tokens.md", "token"] ],
  "checkByRun": { "gate": "prgate", "e2e": "e2e" },
  "severityByCheck": { "prgate": "block" },
  "mainSeverity": "block",
  "prSeverity": "warn"
}
```

| 항목 | 필수 | 뜻 |
|---|---|---|
| `timezone` | | '오늘'을 어느 시간대로 볼지. 기본 `Asia/Seoul`. 팀이 있는 곳 기준이 맞다 |
| `recentMergedDays` | | 며칠 안에 머지된 것까지 보드에 남길지. 기본 14 |
| `statusOf` | **필수** | PR의 세 상태(`draft` · `open` · `merged`)를 각각 config의 어느 상태 열에 놓을지 |
| `teamByAuthor` | | GitHub 로그인 → 팀. `config.teams` 명부를 선언했다면 그 안의 이름이어야 한다 |
| `teamDefault` | **필수** | 대응표에 없는 작성자를 어느 팀으로 볼지 |
| `areaByPath` | | `[[경로 glob, 영역 key], …]`. **위에서부터 처음 맞는 것** 하나가 그 PR의 영역이 된다 |
| `areaDefault` | **필수** | 어느 규칙에도 걸리지 않는 PR의 영역 |
| `assetByPath` | | `[[경로 glob, 자산 key], …]`. 맞는 것 **전부**가 그 PR의 `touches`가 된다 |
| `checkByRun` | | 체크 이름 → config의 검사 key. **아래 3-1을 반드시 읽어라** |
| `severityByCheck` | | 검사별 위반 무게(`block`·`warn`). 적지 않으면 아래 두 기본값 |
| `mainSeverity` | | main에서 실패한 검사의 무게. 기본 `block` — 저장소가 그 상태다 |
| `prSeverity` | | PR에서 실패한 검사의 무게. 기본 `warn` — 아직 본선에 들어오지 않았다 |

경로 glob은 `**`(여러 단계)와 `*`(한 단계)만 받는다. 그 이상은 필요한 적이 없었다.

### 3-1. `checkByRun`의 열쇠는 워크플로 이름이 아니라 **잡(job) 이름**이다

**이것을 모르면 검사가 하나도 대응되지 않는다.** 실제 응답을 확인해 알아낸 사실이다. GitHub이 체크의 이름으로 주는 것은 워크플로의 표시 이름(`PR 크로스컷 게이트`)도 파일명(`pr-gate-check.yml`)도 아니고, 그 워크플로 안의 **잡 이름**이다.

```yaml
# .github/workflows/pr-gate-check.yml
name: PR 크로스컷 게이트     # ← 이것이 아니다
jobs:
  gate:                     # ← 이것이 체크 이름으로 온다
```

그래서 대응표에는 `"gate": "prgate"`처럼 적는다. 표시 이름이나 파일명을 적어 둔 항목도 함께 받아 주지만(사람이 그렇게 적기 쉽고 해가 없다), **실제로 맞는 것은 잡 이름이다.** 대응표에 없는 체크를 만나면 수집기가 그 이름을 요약에 적어 주므로, 한 번 돌려 보고 그 이름을 그대로 옮기면 된다.

## 4. 검사 결과와 위반은 서로 어긋날 수 없다

수집기가 지키는 규칙 하나를 밝혀 둔다. **걸린 것이 있는 검사는 '통과'로 보고하지 않는다.**

처음에는 main의 결과를 그대로 두고 PR의 실패만 위반으로 올렸다. 그러자 main에서 통과한 검사가 어떤 PR에서 실패하면 "통과인데 위반 1건"이라는 앞뒤가 안 맞는 회차가 나왔고, **엔진이 그것을 거부하며 알려 주었다.** 스키마의 뜻을 따르면 답은 분명하다 — 위반은 "이 회차에 이 선이 걸렸다"는 사실이고, 그러면 그 검사의 이번 회차 결과는 통과가 아니다.

main의 통과가 사라지는 것은 아니다. 검사 칸에 걸린 PR이 이름으로 남아, **본선이 아니라 들어오려는 것이 걸렸다**는 사실이 그 자리에서 읽힌다.

## 5. 이 자동화가 하지 않는 것

- **결정 큐를 만들지 않는다.** 수집기가 만드는 것은 **사실판**이다. "그래서 무엇을 답해야 하나"는 여전히 `/sysreport`가 사람과 함께 만든다. 보드는 무엇이 걸렸는지를, 채팅은 그래서 무엇을 정할지를 맡는다.
- **회차 이력을 남기지 않는다.** Pages에는 언제나 최신 한 장만 있다. 회차를 비교하려면 board.json을 어딘가에 쌓아야 하는데, 그것은 지금 필요하지 않아 만들지 않았다.
- **진짜 실시간이 아니다.** 페이지가 열린 채로 스스로 갱신하지는 않는다. 사건이 생기면 다시 그려지고, 다음에 열 때 최신이 보인다. 다른 검사 워크플로가 끝나는 사건(`workflow_run`)에 매달아 두었으므로 새 PR은 보통 1분 안에 반영된다.

  이 사건을 `check_suite`가 아니라 `workflow_run`으로 잡은 데는 이유가 있다. "체크 묶음이 끝나면 돈다"로 두면 **이 워크플로 자신의 실행도 체크를 만들므로 자기 자신을 다시 깨워 끝없이 도는 구조**가 만들어질 수 있다. `workflow_run`은 깨울 워크플로를 이름으로 지목하고 이 파일은 그 목록에 없으므로 자기 자신을 깨우지 못한다. **파생 저장소는 그 목록을 자기 검사 워크플로의 `name:`으로 바꿔 적어야 한다** — 틀리게 적어도 보드가 깨지지는 않고 갱신이 30분 심장박동에만 의존해 느려질 뿐이지만, 조용히 느려지는 것이라 여기 적어 둔다.

## 6. 스스로 확인하는 법

```
python3 tools/integration-board/test_collect.py      # 녹여 둔 응답으로 수집 규칙을 확인
node .claude/workflows/board-collect.mjs --fixture tools/integration-board/board-collect.fixture.json --out /tmp/b.json
```

`--fixture`는 네트워크 없이 녹여 둔 GitHub 응답으로 같은 경로를 돌린다. 대응표를 고친 뒤 이것을 먼저 돌려 보면, 워크플로가 돌기 전에 어긋난 곳을 잡을 수 있다.
