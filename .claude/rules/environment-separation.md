# 환경 분리 규칙 — 실험 장소와 운영 장소를 섞지 않는다

> 한 줄 요지: **데이터베이스나 외부 서비스를 바꾸기 전에 대상 환경을 먼저 밝힌다. 로컬은 자유롭게 실험하고, 개발·스테이징은 정해진 통로로 검증하며, 운영은 버전 관리된 변경안·백업/복구 계획·사람 승인이 모두 있을 때만 바꾼다.**

## 네 환경

| 환경 | 목적 | 기본 쓰기 권한 |
|---|---|---|
| local | 개인·에이전트의 반복 개발 | 자유. 버려도 되는 데이터만 쓴다 |
| development | 합쳐진 기능의 통합 테스트 | 저장소의 적용 스크립트·워크플로만 사용 |
| staging | 운영 직전 리허설 | 운영과 같은 절차, 비식별·합성 데이터만 사용 |
| production | 실제 사용자 서비스 | 명시적 사람 승인 뒤에만 적용 |

작은 프로젝트는 처음부터 네 환경을 모두 만들 필요가 없다. **local + 비운영 환경 하나(development와 staging을 임시 통합) + production**으로 시작할 수 있다. 다만 비운영 자격증명과 데이터는 운영과 반드시 분리한다.

## 변경 전에 반드시 확인할 것

1. 대상 환경을 `local`, `development`, `staging`, `production` 중 하나로 명시한다.
2. 사용하는 URL·계정이 그 환경의 것인지 확인한다. 이름이나 포트만 보고 추측하지 않는다.
3. 운영 변경이면 버전 관리된 마이그레이션, 영향 범위, 백업 확인, 실패 시 복구 또는 forward-fix 계획, 실행 담당자와 승인자를 준비한다.
4. 운영 자격증명은 로컬 파일·PR 본문·로그·스크린샷에 넣지 않는다.
5. 운영 데이터를 비운영 환경으로 그대로 복사하지 않는다. 필요한 경우 최소 범위로 비식별화하거나 합성 데이터를 만든다.

## 에이전트가 지켜야 할 것

- local DB는 테스트 목적에 맞게 만들고 지울 수 있다.
- development와 staging은 저장소가 정한 스크립트나 워크플로로만 바꾼다.
- production에는 직접 SQL을 입력하지 않는다. 기존 [데이터베이스 쓰기 규칙](./db-write-permission.md)의 일회용 승인 관문을 따른다.
- 승인 파일·토큰·운영 자격증명을 스스로 만들거나 우회하지 않는다.
- 적용 성공만 확인하지 말고, 서비스 읽기 경로와 핵심 쿼리가 정상인지까지 검증한다.

자세한 도입 절차와 장애 대응은 [환경 분리 실행서](./reference/environment-separation-runbook.md)에 있다.
