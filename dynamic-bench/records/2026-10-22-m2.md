# M2 입회 10 mm 왕복 — 개발과 실제 실행 기록 (1회차 18:24 · 2회차 19:08)

> **지금 상태 (2회차 뒤, 2026-10-26 저녁):** 모터는 아직 명령대로 움직인 적이 없다. 2회차(19:08)에서 통신 · OP 진입 · 서보 온 전 검사는 모두 정상이었지만, 서보를 켜는 마지막 단계(Enable 0x0F)에서 드라이브가 1초 안에 Operation enabled 로 넘어오지 않아 프로그램이 스스로 멈췄다. 그 1초 동안 드라이브는 **명령 없이 슬라이더를 최대 1.6 mm(최고 약 80–90 mm/s) 움직였고**, 사용자도 "살짝 꿈적거렸다"고 봤다. 원인은 전원 투입 뒤 첫 서보 온 때 드라이브가 스스로 하는 **자극(磁極) 위치 추정**으로 판단한다 — 파라미터 백업과 객체 덤프의 Pr9.20 "자극 검출 방식" = 2, Pr9.22–9.28 "자극 위치 추정 …" 값, 전임자 설명서의 "서보 온 때 '또오오오오' 소리" 가 근거다(5.4절, 걸리는 시간은 `[추정]`). 서보 온 대기를 10초로 늘리고(`[제안값]`), 추정이 끝난 자리에서 Target 을 얼리게 했다. 2회차에서 드러난 결함 하나도 고쳤다 — 종료 순서에서 Quick stop(0x02)이 실제로는 한 번도 전송되지 않았다(5.6절). 장비 없는 시험 3개를 더했고, 이 시험들은 고치기 전 코드에서는 2회차를 그대로 재현하며 실패한다. 다음 실행(3회차)은 사용자가 새로 승인한다.
>
> **1회차 결론 (18:24, 아래 1~4절):** M2 코드(`run_motion.py move`, 안전 판정 `motionbench/safety.py`, 명령 순서 `motionbench/m2.py`)를 만들고 장비 없이 도는 시험 7개를 통과시킨 뒤, 사용자 입회 하에 2026-10-26 18:24:35 KST 에 **한 번** 실행했다. **모터는 움직이지 않았다.** 드라이브가 시작 시점에 이미 알람 상태였기 때문이다 — Statusword `0x0218`(Fault), 0x603F = `0xFF1A`, 그리고 첫 SDO 를 읽는 순간 같은 코드의 비상 메시지(EMCY)가 왔다. 프로그램은 지시문 규칙 1 대로 **Fault reset 을 보내지 않고, 서보 온 전에 멈춰 기록하고 EtherCAT 을 INIT 로 내렸다.** OP 요청 · SDO 쓰기 · Controlword 전송은 한 번도 없었다. 규칙 7 에 따라 재시도하지 않았다.
>
> 알람만 없었다면 나머지 사전 검사(전자 기어 1:1, 과속도 레벨, 창 안의 목표)는 이번에 실제로 읽은 값으로 모두 통과했다(3.3절). `0xFF1A` 는 Err26(과속도) 일 가능성이 크다 `[추정 — 0x1A 는 10진 26]` — **1회차 뒤 사용자가 드라이브 표시 Err26.0 을 확인해 사실이 됐다(5.1절).** 또 하나 새로 알게 된 것은 **Pr5.13 과속도 레벨이 50 mm/s 로 읽혔다**는 것이다(10-21 백업에는 7400). **전원 재투입 뒤에는 7400 으로 읽혔다(5.2절) — 50 은 임시값이었다.**

### 1.3 드라이브에서 읽은 값 (전부 SDO 읽기)

| 객체 | 값 | 해석 |
|---|---|---|
| 0x1018:04 시리얼 | `0x25010217` | M1 기록값 · 명판과 같다 (통과) |
| **0x6041 Statusword** | **`0x0218`** | **Fault** — bit 3(fault) 켜짐 |
| **0x603F Error code** | **`0xFF1A`** | 알람. Panasonic 은 0x603F 를 `FF00h + 알람 번호`로 내는 것으로 보이며, 0x1A = 26 이라 **Err26(과속도 보호)** 일 가능성이 크다 `[추정 — 드라이브 앞면 표시로 확인 필요]` |
| EMCY | error_code `0xFF1A`, error register `0x80` | 첫 SDO(0x1018:04)를 읽는 중에 도착. 이 프로그램이 PRE-OP 로 올리기만 한 시점이라, **알람은 실행 전부터 있었다** |
| 0x6064 실제 위치 (p0) | −5,067 pulse | M1(10-22) 때 −3,967 근처에서 약 1.1 mm 다른 자리 |
| 0x608F:01 / :02 | 1,000,000 / 1,000 | PANATERM 객체 덤프(2025-04-25)와 같다 |
| 0x6091:01 / :02 | 1,000 / 1,000 | **전자 기어 1:1** — 위치 단위 = 엔코더 1 pulse |
| 0x6092:01 / :02 | 1,000,000 / 1,000 | 덤프와 같다 |
| **0x3513 Pr5.13 과속도 레벨** | **50** (mm/s) | 10-21 백업(`20261021_원복백업.prm5` 232행)의 7400 과 다르다 — 그 뒤 누군가 바꿨다. 시운전 기록 §5 의 "50 mm/s 설정에서는 정상" 과 같은 값이다 |
| 0x6081 · 0x6083 · 0x6084 | 0 · 1,000,000 · 1,000,000 | 쓰기 전 값. 이번에는 쓰지 않았다 |
| 0x6085 Quick stop 감속 | 1,000,000 pulse/s² (= 1 m/s²) | 10 mm/s 에서 정지 거리 50 pulse (0.05 mm) |
| 0x605A Quick stop option | 2 | 감속해 멈춘 뒤 Switch on disabled — 코드가 요구하는 값과 같다 |
| 0x607D:01 / :02 | INT32 최솟값 / 최댓값 | 드라이브 쪽 소프트 리미트 없음. 이번에는 창으로 쓰지 않았다 |
| 0x607F · 0x6080 · 0x60C5 · 0x1C32:01 | 838,860,800 · 6,500 · 0xFFFFFFFF · 0 | M1 과 같다 (0x1C32:01 = 0 → FreeRUN) |

### 3.2 지시문 안전 규칙 ↔ 코드

| 규칙 | 코드가 하는 일 |
|---|---|
| 수치는 승인 파일에서만 | 거리 · 창 · 속도 · 가속 · 횟수 · 방향은 전부 `m2-approval.json` 에서 읽는다. 코드에는 넘으면 거부하는 상한(`safety.CAPS`)만 있다 |
| 1. 서보 온 전 검사 | 승인 파일 → 표지 → 슬레이브 · 시리얼 · 0x603F · fault · 0x605A → 단위 · Pr5.13 · 창 순서로 보고, 하나라도 어긋나면 SDO 쓰기 전에 멈춘다. 서보 온은 0x06 → 0x07 → 0x0F 의 정상 전이로만, 각 단계의 Statusword 를 확인한다 |
| 2. 점프 금지 · PP 핸드셰이크 | 서보 온 전에는 매 주기 Target = 방금 읽은 실제 위치. 새 목표는 0x3F(bit4) → bit12 확인 → 0x2F → bit12 내려감 확인. bit5(change immediately)는 늘 1 — 이동이 끝난 뒤에만 새 목표를 주므로 효과는 없고, 전임자 코드의 값을 그대로 썼다 |
| 3. SDO 쓰기 제한 | `ecat.WRITABLE` 밖의 객체는 `sdo_put` 이 거부한다. 쓴 뒤 다시 읽어 다르면 멈춘다. 창으로 좁힌 0x607D 는 끝날 때 원래 값으로 되돌린다 |
| 4. 매 주기 자동 Quick stop | 주기 간격 50 ms 초과 · fault 비트 · 0x603F ≠ 0 · 추종 오차 2 mm `[제안값]` 초과 · 창 밖 위치 · 표지 마감 지남 · WKC 3주기 연속 불일치 → Controlword 를 0x0002 로 걸어 둔다(걸쇠). 이동 직전마다 표지 파일을 다시 읽는다 |
| 5. Quick stop 시험 | 마지막 왕복의 가는 길에서 5 mm 를 지나면 프로그램이 스스로 건다. 시험 중 자동 규칙에 걸린 것이 하나라도 있으면 다시 켜지 않는다. 복귀 이동도 창 검사를 거친다 |
| 6. 종료 순서 | 예외 · Ctrl+C 포함 늘 Quick stop → 0x06 → 0 → SAFE-OP → INIT → 닫기. 한 단계가 실패해도 다음 단계로 간다. 끝난 뒤 Statusword 를 기록한다. (2회차에서 Quick stop 이 실제로는 안 나간 결함이 드러나 고쳤다 — 5.6절) |
| 7. 한 번만 | 이 기록의 실행 한 번. 재시도하지 않았다 |

### 3.3 이번 실행에서 알람 말고 다른 검사는 어땠나

실제로 읽은 값(1.3절)을 그대로 넣어 나머지 판정을 따로 계산했다. 전부 통과였다 — 알람이 유일한 거부 사유다.

| 검사 | 입력 | 결과 |
|---|---|---|
| 단위 (전자 기어) | 0x608F · 0x6091 · 0x6092 여섯 값 | 통과 — 덤프와 같고 기어 1:1 |
| 과속도 | vmax 10 mm/s vs Pr5.13 50 mm/s | 통과 |
| 가는 목표 | p0 + 10,000 + 정지 거리 50 ≤ 15,000 | 통과 |
| 돌아오는 목표 | p0 | 통과 |

### 5.5 이 무명령 움직임을 무엇이 감시하나 — 추종 오차 규칙은 못 보고, 창 규칙이 본다

- **추종 오차(0x60F4) 규칙은 이 움직임을 보지 못한다.** 2회차 728주기 전부에서 0x60F4 는 0 이었다 — 1.6 mm 움직이는 동안에도. 드라이브가 Operation enabled 전에는 추종 오차를 계산하지 않는 것으로 보인다 `[추정]`.
- **창(p0 ± 15 mm) 규칙은 상태와 상관없이 매 주기 돈다.** 2회차 최대 이탈은 1.627 mm 라 걸리지 않았다. 추정 중 움직임이 창을 넘으면 그 주기에 Quick stop 이 걸리고, Switched on 에서 받은 Quick stop 은 CiA402 규칙대로 서보를 끈다(Switch on disabled) — 장비 없는 시험 `test_window_stops_runaway_pole_estimation` 이 이것을 보인다(5.8).
- fault 비트 · 0x603F · 주기 지연 · WKC · 표지 만료 규칙도 추정 중에 그대로 돈다. 추정이 실패해 드라이브가 알람을 내면 fault 비트 규칙이 잡는다.
- **승인 속도(10 mm/s)는 이 움직임에 적용되지 않는다.** 드라이브 내부 동작이라 프로그램이 속도를 정할 수 없다. 프로그램이 할 수 있는 것은 창 밖으로 나가면 멈추는 것뿐이다('결정 필요' 1).

### 5.6 함께 드러난 결함 — 종료 순서에서 Quick stop 이 실제로는 나가지 않았다

지시문 안전 규칙 6 은 "종료는 늘 Quick stop → Shutdown 0x06 → Controlword 0" 이다. 2회차의 결과 파일에는 `Quick stop → SWITCHED_ON` 이라고 적혔지만, trace 에서 실제로 보낸 Controlword 는 **0x0F → 0x06 → 0x00** 이었다 — 0x02 가 한 주기도 없다.

원인: `finish()` 는 Quick stop 을 걸어 둔 뒤 "Operation enabled 도 Quick stop active 도 아니면 이미 멈췄다"로 보고 다음 단계로 갔다. 그런데 그 판단에 쓴 입력은 Quick stop 을 보내기 전의 묵은 값(Switched on)이었고, 자극 추정 중에는 Switched on 이어도 모터가 움직이고 있다. 결과적으로 서보는 0x06(Shutdown)으로 꺼져 안전하게 끝났지만, 규칙이 정한 순서는 아니었다.

**약하게 한 안전 규칙은 없다.** 창 · 자동 Quick stop · 승인 파일 · 표지 · SDO 쓰기 제한은 그대로이고, 대기만 길어졌다. 길어진 동안에도 위 규칙들이 매 주기 돈다. Pr 값 쓰기와 Fault reset 은 여전히 없다. `run_motion.py` · `ecat.py` · `safety.py` 는 바꾸지 않았다.

### 5.8 시험

가짜 드라이브에 자극 추정 흉내를 더했다 — 첫 0x0F 에서 정한 시간 동안 Switched on 에 머물며 무명령으로 갔다가 돌아오고 비켜 선다.

| 새 시험 | 보는 것 |
|---|---|
| `test_servo_on_waits_through_pole_estimation` | 1.5초 추정(1.6 mm 갔다가 0.35 mm 비켜 섬)을 기다려 서보 온에 성공하고, Quick stop 은 걸리지 않고, Target 이 추정이 끝난 자리와 같다 |
| `test_window_stops_runaway_pole_estimation` | 추정 움직임이 창을 넘으면(최고 약 84 mm/s) 0x0F 바로 다음에 0x02 가 나가고 서보가 꺼진다. 최대 이탈은 창 + 1 mm 안 |
| `test_finish_sends_quick_stop_during_estimation` | 2회차 그대로(대기 1초 · 추정 5초) — 종료 때 보낸 마지막 네 Controlword 가 0x0F → **0x02** → 0x06 → 0 |

**새 시험이 결함을 실제로 잡는지 확인했다.** 커밋된 이전 `m2.py` 를 그대로 올려 같은 시나리오를 돌리면, 1.5초 추정에서 `Enable 0x0F → Operation enabled — 1.0초 안에 안 됨` 으로 실패하고, 종료 때 보낸 Controlword 가 0x0F → 0x06 → 0x00 이다 — 2회차 trace 와 같다. 고친 코드에서는 통과한다.

결과: M2 시험 10개 + M1 시험 6개 = **16개 통과**. 전체 `cell-bench/tests` 는 955 통과 · 1 건너뜀 · 1 실패 — 실패는 4.1 의 불안정한 골든 시험(`g1_two_cycles`, 모션 코드와 무관) 그대로다.

## 결정 필요

1회차의 결정 두 개는 풀렸다 — 알람은 사용자가 전원 재투입으로 풀었고(5.1), Pr5.13 은 전원 재투입 뒤 7400 으로 읽혔다(5.2). 3회차 전에 정할 것은 이 둘이다.

1. **첫 서보 온의 무명령 움직임을 받아들이고 3회차를 진행할 것인가.** 드라이브 전원을 넣은 뒤 첫 서보 온에서 드라이브가 스스로 슬라이더를 움직인다 — 2회차 실측 최대 1.6 mm, 최고 약 80–90 mm/s. 승인 파일의 속도 상한(10 mm/s)은 프로그램이 내는 명령에만 적용되고, 이 드라이브 내부 동작에는 적용되지 않는다. 프로그램은 이 움직임이 창(±15 mm)을 넘으면 그 자리에서 멈출 수 있을 뿐이다.
   - **권고: 받아들이고 진행한다.** 움직임이 작고(창의 약 11 %), 사용자가 입회하며, 창 규칙이 지킨다. 자극 추정은 전원을 넣은 뒤 첫 서보 온에서만 일어나는 것으로 보인다 `[추정]`.
   - 다른 길: 추정 추력(Pr9.23 = 80)을 낮추거나 CS 신호(자석 위치 센서)를 배선해 추정을 없앤다. 둘 다 PANATERM · 하드웨어 작업이라 사람이 한다.
   - 무응답 시: 3회차 승인 자체가 사용자 몫이라, 승인하면 받아들인 것으로 본다.
2. **서보 온 대기 10초 `[제안값]` 을 그대로 둘 것인가.** 자극 추정이 몇 초 걸리는지 자료로 확정하지 못했다(5.4). 권고는 10초로 두고 3회차의 `enable_ms` 실측을 보고 줄이는 것이다.
