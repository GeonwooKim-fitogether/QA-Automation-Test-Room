# 환경 분리 실행서

이 문서는 `environment-separation.md`의 상세 실행 절차다. 저장소마다 프레임워크와 클라우드가 달라도 환경 경계와 승인 흐름은 동일하게 유지한다.

## 1. 최소 시작 구조

처음에는 다음 세 층이면 충분하다.

| 층 | 위치 | 용도 |
|---|---|---|
| local | 개발자 컴퓨터의 Docker DB | 기능 개발, 마이그레이션 반복, 파괴 테스트 |
| non-production | AWS의 개발용 DB 또는 관리형 개발 프로젝트 | 통합 테스트와 배포 전 확인. 초기에는 development/staging을 합쳐도 됨 |
| production | 실제 서비스 DB | 승인된 변경만 적용 |

프로젝트가 커져 배포 전 리허설과 일상 개발이 충돌하기 시작하면 non-production을 development와 staging으로 나눈다. production은 어떤 경우에도 비운영 인스턴스와 계정·비밀번호를 공유하지 않는다.

## 2. 저장소 도입 체크리스트

1. `templates/webapp-environment/`의 파일을 대상 저장소 루트에 복사한다.
2. `.env.example`은 변수 이름과 설명만 보존하고 실제 비밀값은 넣지 않는다.
3. 실제 로컬 값은 `.env.local`에 두고 git에서 제외한다.
4. 앱의 DB 연결 문자열이 `DATABASE_URL` 하나를 정본으로 쓰도록 맞춘다.
5. 프로젝트별 `docs/environment-map.md`를 만들어 실제 서비스 이름과 책임자를 적는다.
6. 마이그레이션 적용 명령을 한 가지로 고정하고 README에 적는다.
7. CI는 빈 DB를 만들어 전체 마이그레이션을 처음부터 적용하는 검사를 둔다. 단 **매 PR 이 아니라 DB 를 바꾸는 PR(마이그레이션·시드·스택 설정)과 하루 한 번**(그날 main 에 변경이 있을 때만) 돌린다. 빈 DB 를 세우는 준비가 한 번에 수 분이라, 모든 PR 에서 돌리면 그것 하나가 Actions 사용량의 3분의 1이 된다(Fitstack 2026-09 실측).
8. 운영 적용 경로는 사람 승인 없이는 실행되지 않게 한다.

## 3. 표준 개발 흐름

1. 최신 main에서 작업 브랜치를 만든다.
2. local DB를 실행한다.
3. `YYYYMMDDHHMMSS_name.sql` 형식으로 마이그레이션을 만든다.
4. 빈 local DB에 전체 마이그레이션을 적용해 재현성을 확인한다.
5. 앱 테스트와 핵심 쿼리를 실행한다.
6. DB 변경 요청서가 포함된 PR을 연다.
7. CI가 빈 DB 적용과 정적 검사를 통과한다.
8. development에 적용하고 통합 테스트한다.
9. staging이 분리돼 있으면 같은 산출물을 적용해 리허설한다.
10. production 변경안을 사람이 검토·승인한 뒤 지정된 담당자가 적용한다.

## 4. 운영 변경 카드에 필요한 내용

- 변경 파일과 버전
- 바뀌는 테이블·컬럼·인덱스
- 기존 데이터 변경 여부와 예상 행 수
- 잠금·지연·중단 가능성
- 백업 확인 시각과 담당자
- 실패 판정 기준
- 되돌릴 수 있는지, 아니면 forward-fix가 필요한지
- 실행 담당자와 승인자
- 적용 후 확인할 API·화면·쿼리

`DROP`, 대량 `UPDATE`, 타입 축소, NOT NULL 강제처럼 손실 가능성이 있는 변경은 한 번에 하지 않는다. 새 구조 추가 → 이중 쓰기/백필 → 읽기 전환 → 관찰 → 옛 구조 제거의 여러 배포로 나눈다.

## 5. 데이터와 자격증명

- 운영 데이터 덤프를 개인 PC나 PR 첨부파일로 가져오지 않는다.
- 테스트 데이터는 합성 데이터가 기본이다.
- 운영 형태가 꼭 필요하면 개인정보와 식별자를 제거하고 필요한 행·열만 복제한다.
- 환경별 DB 사용자와 비밀번호를 분리한다.
- CI의 PR 워크플로에는 운영 Secret을 제공하지 않는다.
- 로그에는 연결 문자열 전체를 출력하지 않는다.

## 6. 로컬 서버와 원격 개발 서버

일반적인 화면·API·DB 개발은 컴퓨터 안에서 모두 실행할 수 있으므로 별도 서버가 필요하지 않다. 외부 결제 콜백, 웹훅, 장기 실행 작업, 다른 사람의 원격 QA, AWS 전용 서비스 연동이 필요할 때만 비운영 원격 서버를 만든다.

## 7. 장애와 긴급 변경

운영 장애라도 직접 콘솔에서 고치고 끝내지 않는다. 최소한 변경 SQL을 파일로 남기고, 승인과 실행 결과를 이슈 또는 PR에 기록한다. 긴급 적용 뒤에는 같은 날 안에 마이그레이션 이력과 환경 문서를 실제 상태에 맞춘다.

되돌림이 데이터 손실을 키울 수 있으면 rollback을 강행하지 않는다. 서비스를 이전 코드와 호환되게 유지한 채 새 마이그레이션으로 전진 수정(forward-fix)한다.
