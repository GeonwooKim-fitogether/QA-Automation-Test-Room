# dynamic-bench 기획 지시문 v3 (2026-10-22, 김건우 승인)

너는 이 세션에서 v1·v2 기획을 쓴 kimpm 이다. 이번 일은 **기획 v3** 를 쓰는 것이다. 코드는 쓰지 않는다.

## 산출물과 범위
- 새 파일 `dynamic-bench/plan/plan-v3.md` 를 쓴다. `plan-v1.md`, `plan-v2.md` 는 **한 글자도 바꾸지 않는다.**
- `dynamic-bench/README.md` 가 최신 기획으로 v3 를 가리키도록 고친다.
- `dynamic-bench/` 밖의 파일은 수정하지 않는다. (읽기는 자유)
- 한국어. 결론 먼저. Mermaid 도표 중심. 요구사항을 지어내지 않는다 — 모르는 것은 `[확인 필요]`, 제안은 `[제안값]`, 근거는 `[사실: 출처]` 로 표시한다 (v2 와 같은 표기).
- v2 를 버리지 않는다. v3 는 v2 의 아키텍처(cell-bench 위 모션 엔진 `run_motion.py`, `cell-bench/motionbench/`)와 M1~M6 을 이어받고, 아래 결정들로 **목적·범위·작업 흐름**을 다시 짠다. v2 에서 바뀌는 점은 "v2 정정" 표로 먼저 보여준다.
- 같은 시각에 다른 세션(M1 개발, kimdeveloper)이 같은 브랜치 `feature/dynamic-bench` 의 `cell-bench/motionbench/`, `cell-bench/run_motion.py`, `dynamic-bench/dev/`, `dynamic-bench/records/2026-10-22-m1.md` 를 만들고 커밋한다. **그 파일들은 건드리지 않는다.** M1 결과는 아직 없다고 보고 v3 를 쓴다(있으면 읽어서 반영해도 된다).

## 사용자 결정 (모두 김건우, 2026-10-22) — v3 에 반영
1. **목적.** 이 시스템은 정답 모션(모터 엔코더 ~1 µm)을 만들어, 셀 데이터 — raw, 추출(extracted), iOS LiveApp 화면에 보이는 값 — 이 맞는지 **숫자로** 판정한다. 목표 우선순위: **정확도 → 내구성 → 출하 QC**.
2. **QA 와 출하 QC 를 분리한다.** QA = 표본 기반 심층 검증(설계·펌웨어의 정확도·내구성). 출하 QC = 들어오는 셀 **전수** 선별, 불량 골라내기. 5 모듈 × 24 셀은 회사에 없는 출하 QC 장비를 만들려는 것이 주목적이며 QC 는 정확도만큼 중요하다. **QA 결과가 QC 합격 기준이 된다.**
3. **출하 물량·운영.** 한 번에 10–20 세트(세트당 24 셀)가 들어온다. 별도 QC 작업자가 돌린다: UI 는 상용 제품만큼 쉬워야 한다(세트 스캔/선택 → 시작 → 셀별 초록/빨강 → 빨강 빼기). 작업자 쪽에서 코드·설정 편집 없음. 설정은 사용자/Grr 이 원격으로만. QA 제어 PC 2 는 항상 켜 두고 원격 관리.
4. **QC 시험 시간은 지금 정하지 않는다.** 먼저 **검출력(검증력)** 을 증명한다: 알려진 불량 셀을 정상 셀 사이에 섞어, 불량을 확실히 잡아내는 최소 시험을 찾는다. 그 다음에 시간을 정한다. **그 실험 설계를 제안하라** (표본 수, 불량 종류, 배치 무작위화, 판정 지표, 반복, 합격 기준 — 모르는 값은 표시). QC 판정은 **라이브 데이터만으로** 하는 것을 선호(추출은 셀당 수 분). 추출은 QA 나 의심 셀에만.
5. **GPS 동료 비교.** 24 셀은 모션과 하늘을 공유하므로 이상치 = 불량 후보. 펌웨어 사실 (fitogether-org/cell-y4-ESP32-S3-firmware master 08fe785e):
   - GPS 10 Hz. 라이브 패킷 0x09, 1320 B, 2 Hz, UDP 60222.
   - byte 47 fix mode (ASCII N/A/D/F/R), byte 48 사용 위성 수 = 상위 5비트 (>>3), byte 49 평균 C/N0 dBHz u8, byte 55 gps_validity 비트 (KINEXON=0 빌드), byte 41 hspeed (단위 의심), bytes 57–1256 speed_history mm/s 10 Hz 60 s.
   - HDOP 은 어디에도 출력되지 않음. hAcc/vAcc, PDOP, 추적 위성 수, TTFF 는 추출 FTG 파일에만.
   - cell-bench `protocol.py` 는 지금 GPS 바이트를 하나도 파싱하지 않음 → 파서 추가 필요.
   - iOS `Packet.swift` 는 위성 수를 하위 5비트로 읽음(틀렸을 가능성) → LiveApp 일관성 시험 항목.
   - **양산 펌웨어 확정:** Y4 계열(Y4A, Y4B, Y3B, X6A, X6B) = **v0.99.71**, 2026-10-13 Slack #release-notes, 펌웨어 담당 김빛 (양산 판단은 #release-notes 게시만 인정). GPS 라이브/FTG 필드는 v0.99.61 이후 변경 없음. v0.99.71 은 Y4A/Y4B 에 **RTK 보정원 자동 선택**(인터넷 NTRIP 가능하면 그것, 아니면 LiveHub 보정)을 추가 → GPS 동료 비교에서 **24 셀 모두 같은 보정 조건**임을 보장해야 한다. 아니면 fix mode 차이가 불량이 아니라 보정원 차이일 수 있다. 이를 시험 조건/절차에 넣어라.
   - Y1 계열(X5/Y1) 양산 버전은 **미확정**(릴리스 노트 없음) → 열린 항목.
6. **LiveHub 2대.** 두 번째 LiveHub 를 추가한다: QA 제어 PC 2 가 모듈 1 의 전용 PC 가 된다(v2 결정 2 의 A안 확정). 시험 PC 의 500 사이클 시험은 그대로 둔다. Python 3.11.9 설치됨(`py -3.11`) → v2 결정 1 해결.
7. **모션 승인.** 모션은 M1 이후 사용자가 방향 부호·소프트 리미트·속도 상한을 승인한 뒤에만. 하드웨어 안전장치(H1–H3)가 생기기 전에는 사용자 입회 시에만 모션. 최종 목표는 24 h 무인.
8. **사용자 답 대기 중 (열린 항목):** 페이로드 질량(Fitstack 데이터에서 문의 중), 기존 광센서가 드라이브에 배선돼 있는지(사용자는 아마 아니라고 봄, 사진 올 예정), 알려진 불량 셀 확보 가능 여부.

## 병렬 작업 흐름으로 정리
다음 작업 흐름으로 일을 나누고, **의존관계**(무엇이 무엇을 기다리나)를 Mermaid 로 보여 여러 갈래를 동시에 진행할 수 있게 하라:
- **A 모션 제어** (M1→M2… , run_motion.py / motionbench)
- **B 기계·안전** (사용자 담당: 스테이지, 리미트, STO/비상정지, 가드 = H1–H3)
- **C 시험 시나리오** (QA 정확도·내구성 시나리오, QC 검출력 실험)
- **D 데이터 정렬·분석** (시간 정렬, GPS 파서 추가, raw/추출/LiveApp 비교)
- **E 모니터링 + QC 작업자 UI** (cell-bench 결과판 위)
- **F 조달** (모터/드라이브 4세트 추가)
각 흐름마다: 목표, 첫 산출물, 선행조건, 담당(사용자/Grr/세션), 열린 질문. 그리고 QA→QC 기준 흐름(QA 결과가 QC 합격 기준이 되는 경로)을 한 장으로.
