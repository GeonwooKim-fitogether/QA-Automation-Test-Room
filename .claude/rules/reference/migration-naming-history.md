# 마이그레이션 파일명 규칙 — 부록: 태어난 사고와 선택의 논증

> 이 파일은 [`../migration-naming.md`](../migration-naming.md)의 부록이다. 규범은 코어 파일에 전부 있고, 여기에는 규칙이 태어난 사고와 "왜 번호가 아니라 시각인가"의 상세 논증만 있다. 자동 로드되지 않는다.

## 실제로 일어난 사고

여러 Claude 세션이 서로 다른 브랜치에서 **동시에** 작업하다가, 같은 번호를 각자 집어 갔다. 두 세션 모두 저장소를 보고 "지금까지 `0083`까지 썼으니 다음은 `0084`다"라고 똑같이 옳게 판단했다. 그 결과 서로 다른 내용의 두 파일이 같은 번호를 갖게 됐다.

```
PR #198   supabase/migrations/0084_spec_fill_targets.sql
PR #199   supabase/migrations/0084_project_reference_single_target.sql
```

## 이 충돌이 위험한 이유는 git이 잡지 못하기 때문이다

git이 충돌을 알려 주는 조건은 같은 파일의 같은 자리를 두 브랜치가 다르게 고쳤을 때다. 그런데 위 두 파일은 이름이 서로 다르다. git이 보기에 서로 무관한 새 파일 두 개를 각자 추가한 것일 뿐이므로 텍스트 충돌이 일어나지 않는다. 두 PR 모두 `mergeable_state = clean`(합칠 준비 완료)으로 초록불이 뜨고, 차례로 머지되고, 머지가 끝난 뒤에야 같은 번호 파일이 둘 있다는 것을 알게 된다. 발견 시점에 이미 main에 들어와 있다.

## 더 나쁜 두 번째 효과 — 적용되지 않은 것을 적용된 것으로 착각한다

번호가 겹치면 어느 파일이 실제로 데이터베이스에 적용됐는지 이름만으로 구분할 수 없다. 라이브의 적용 이력(`list_migrations`)에 `0084`가 하나 보이면 자기 파일이 적용됐다고 읽지만, 실제로 적용된 것은 같은 번호의 다른 파일일 수 있다. 결과: **걸리지 않은 제약이 걸린 것으로 보인다.** 오류 메시지는 나지 않고, 데이터베이스는 조용히 제약 없이 돌아간다.

## 같은 일이 곧바로 한 번 더 일어났다

첫 충돌을 해소하려고 PR #199가 번호를 `0085`로 옮겼는데, 라이브에는 이미 `0085_switch_free_text_value`가 적용돼 있었다. 저장소 파일 목록만 보고 고른 번호였기 때문이다. 번호를 안전하게 고르려면 내 브랜치 · main · 라이브 이력 세 곳의 합집합을 봐야 하는데, 이 세 곳을 매번 빠짐없이 확인하는 일은 사람도 에이전트도 안정적으로 해내지 못한다.

## 사람의 기억으로 막는 방식은 이미 실패했다는 증거

이 하나의 문제에 네 개의 세션이 각자 부딪혔다. 한 세션은 커밋 제목에 "번호 충돌 가드"를 달았고, 한 세션은 충돌을 두 번 만들었으며, 한 세션은 충돌을 발견하고도 "내 PR과 무관하다"고 넘겼고, 네 번째 세션이 최종 해소했다. 그 해소 과정에서 결정적 사실이 드러났다 — **한 세션이 번호를 바꾸면서 파일 이름 2개만 고치고, 그 번호를 가리키던 문서·코드 참조 17곳을 놓쳤다.** 개번은 파일 이름만 바꾸는 작업이 아니라 저장소 전체의 참조를 함께 옮기는 작업이고, 그래서 사람이 손으로 하면 빠진다.

## 왜 번호가 아니라 시각인가 — 세 가지 이유

**첫째, 충돌을 잡는 것이 아니라 없앤다.** 번호 방식에 자동 검사를 붙여도 검사는 충돌이 생긴 뒤에 잡는 장치다. 세션은 여전히 충돌을 만들고 매번 개번(참조 17곳을 놓칠 수 있는 위험한 작업)이 따라온다. 시각을 쓰면 두 세션이 같은 초에 파일을 만들지 않는 한 애초에 겹칠 일이 없다.

**둘째, 번호는 확인해야 알 수 있지만 시각은 확인할 필요가 없다.** 번호는 세 곳(내 브랜치 · main · 라이브)을 조회해야 하고 하나만 빠뜨려도 틀린다. 시각은 아무것도 조회하지 않고 혼자 결정한다. **다른 브랜치가 무엇을 하고 있는지 알 필요가 없는 것**이 핵심 이점이다.

**셋째, 도구와 싸우지 않는다.** Supabase CLI가 마이그레이션 파일을 만들 때 쓰는 기본 형식이 바로 이 열네 자리 시각이고, 라이브 적용 이력도 이미 `version`(시각)과 `name`을 따로 갖는다.

## 무엇을 포기했나

**순번 감각을 잃는다** — 파일 이름만 보고 "몇 번째 마이그레이션인가"를 아는 감각. 감수할 만한 근거: 번호는 이미 순서를 뜻하지 않았다(여러 브랜치가 병렬로 번호를 집어 가서 실제 적용 순서는 번호 순서와 달랐다). 반면 시각은 정의상 만든 순서다. 또 사전순 정렬에서 네 자리 번호(`0` 시작)는 항상 열네 자리 시각(`2` 시작)보다 앞에 오므로, 두 형식이 섞여도 사전순이 곧 적용 순서다.
