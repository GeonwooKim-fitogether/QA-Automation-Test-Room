> 규약은 [`.claude/rules/lessons-backport.md`](../.claude/rules/lessons-backport.md).
> 기록은 차단기가 아니다 — 적고 계속 진행한다. 창고 반영은 수확 → 4분류 → 사람 승인 뒤에만.

## 누적

### 2026-08-26 — 티어 판정에 "전담자 유무 확인"이 없다
- **증상**: CEO 브리프 제작을 메인 세션이 직접(T0) 처리했는데, 문서 정제 전담 에이전트(doc-clarifier)가 있는데도 그것을 확인하는 절차가 판돈 규칙에 없어 전담자가 우회됐다. 결과물은 좋았으나 전담자의 규약이 적용됐는지 아무도 보증하지 못한다.
- **제안**: 판돈 규칙의 티어 판정 앞에 "이 일의 전담 에이전트·스킬이 이미 있는가"를 먼저 확인하는 한 줄 추가.
- **일반화**: 가능 — 전담자가 늘수록 어느 저장소에서든 같은 우회가 생긴다. (사례 1건이므로 규칙 격상은 보류, 규약대로 기록만.)
- **처리 (2026-08-26)**: 수확 → **보류**. 재검토 트리거는 동종 우회 1건 추가 관측(누적 2건).

### 2026-08-26 — 동기화 봇 자신의 버전 드리프트를 재는 장치가 없다
- **증상**: career는 스킬만 내려받는 옛 봇, Geonwoo-LLM-Wiki는 존재하지 않는 경로를 바라보며 9회 연속 실패한 화석 봇이었는데, 수동 전파를 시도하기 전까지 아무도 몰랐다. `.github/workflows/`는 동기화되지 않으므로 이 드리프트는 구조적으로 재발한다.
- **제안**: 자산 그래프 검사(또는 주기 스윕)에 "하위 저장소의 sync-skills.yml이 창고 판과 같은가" 대조 한 줄 추가.
- **일반화**: 가능 — 봇이 있는 모든 하위 저장소가 같은 위험을 진다.
- **처리 (2026-08-26)**: 수확 → 추가검토 → 대표 승인(옵션 B). 동기화 봇이 실행 때마다 자기 파일을 창고 판과 대조해 다르면 GitHub 경고를 남기도록 반영했다. 아무것도 막지 않고 알리기만 한다.

### 2026-08-26 — 워크플로 YAML을 파싱 검증 없이 커밋해 5회 연속 조용히 실패했다
- **증상**: `asset-graph.yml`의 스텝 이름에 따옴표 없이 콜론이 들어가(`name: 그래프 정합 검사 (창고: README 배선 포함)`) GitHub가 파일을 파싱하지 못했다. 실행은 0초·잡 0개로 끝나 5회 모두 실패했고, 정작 검사기는 지역에서 통과하고 있어 "검사가 돌아 통과했다"와 "검사가 아예 안 돌았다"가 보고에서 구분되지 않았다.
- **제안**: 워크플로 파일을 커밋하기 전에 YAML 파싱을 한 번 돌린다(`python3 -c "import yaml;yaml.safe_load(open(f))"` 한 줄). 나아가 자산 그래프 검사에 "워크플로 YAML이 파싱되는가" 한 축을 더할 수 있다.
- **일반화**: 가능 — 워크플로를 추가하는 모든 저장소가 같은 실수를 할 수 있고, 실패가 조용해서 더 위험하다.
- **처리 (2026-08-26)**: 수확 → 승인 후보 → 대표 승인(옵션 A). 자산 그래프 검사에 네 번째 축으로 반영했다(`.github/workflows/*.yml` 파싱 검증). 이 축이 어제의 실제 버그를 재현 시험에서 잡는 것을 확인했다.

### 2026-08-28 — 결정 카드가 기본값을 갖고도 차단기처럼 운용됐다
- **증상**: 규칙 개정 세션 하루에 결정 카드 7장이 연속 상신됐다. 전부 "무응답 시 기본 행동"이 있었는데도 답을 기다리며 진행을 멈췄고, 대표가 "사용성이 복잡해졌다 — 결정을 하나씩 선택하게 만든다"고 직접 지적했다.
- **제안**: 기본값 있는 카드는 추천대로 진행하며 기한부 공지로 올린다. 위임 원장에 "추천+기본값+되돌리기 쉬움 결정 전부" 범주를 등재한다 (등재는 규칙대로 사람 승인 대기).
- **일반화**: 일반 — 모든 저장소의 상신이 같은 서식을 쓰므로 같은 오운용이 재현된다.

### 2026-08-28 — 사람에게 셸 명령 실행을 전제 설명 없이 부탁했다
- **증상**: 브랜치 정리 스크립트를 "bash로 실행해 달라"고 부탁하며 실행 장소·운영체제 전제를 밝히지 않아, 대표가 "PowerShell에서 하라는 것인가"부터 되물었다. 결정 카드에는 번역 관문이 생겼지만 행동 부탁에는 관문이 없었다.
- **제안**: 기계 우선 검사(버튼으로 만들 수 있으면 부탁하지 않는다) + 부탁 서식 + 부탁 리트머스 3문항 — communication 규칙 8로 같은 날 격상(대표가 "수도 없이 이야기했다"고 직접 지적 = 2건 이상 누적 기준 충족).
- **일반화**: 일반 — 모든 저장소의 세션이 사람에게 행동을 부탁한다.

### 2026-10-02 — 몇 초짜리 잡은 1분으로 올림 청구된다 — 두 번째 사례, 격상 후보
- **증상**: GitHub 은 잡 하나의 시간을 1분 단위로 올림해 청구한다. 10~40초짜리 정책 검사 잡 셋(크로스컷 게이트 · 겹침 알림 · 이름 검사)이 따로 돌아 PR 이 열린 브랜치에 푸시할 때마다 3분이 나갔다 — Fitstack 9월 실적 셋 합쳐 222분, 9/28~10/1 사흘 반에 124회. Fitstack 은 2026-09-18 에 알림 둘을 하나로, 2026-10-01 에 셋을 하나로 두 번 합쳤고, 창고는 2026-10-02 에 그 판을 받았다.
- **제안**: 에스컬레이션 §2-5(비용 관문) 옆에 한 줄 — "같은 사건에 매달린 몇 초짜리 잡은 따로 만들지 않고 한 잡의 단계로 넣는다. 잡 하나가 1분 단위로 청구된다". 새 워크플로를 만들 때 "이 사건에 이미 잡이 있는가"를 먼저 보게 한다.
- **일반화**: 비공개 저장소라면 어디서나 겪는다(공개 저장소는 Actions 가 무료라 드러나지 않는다). **같은 패턴 2건째**(9/18 · 10/1)이므로 규칙 격상 후보로 올린다.

### 2026-10-02 — 막지 않던 검사를 필수 검사 안에 합치면 조용히 머지 차단이 된다
- **증상**: 비용을 줄이려고 "알리기만 하던" 검사(이름 형식·겹침)를 머지 필수 검사인 잡(`gate`) 안의 단계로 합치면, 그 단계의 `exit 1` 이 그대로 머지 차단이 된다. 특히 브랜치 이름 위반은 그 PR 에서 고칠 수 없다(이름을 바꾸면 PR 이 닫힌다) — 합치는 순간 "영원히 머지 못 하는 PR" 이 생긴다. Fitstack 이 2026-10-01 합치기에서 설계 단계에 발견해, 이름 검사는 Checks API 로 별도 체크 `naming` 을 남기고(필수 아님) 잡은 실패시키지 않게, 겹침은 continue-on-error 로 처리했다.
- **제안**: 잡을 합칠 때 단계마다 "원본은 막았나, 알리기만 했나"를 표로 적고, 알리기만 하던 것은 잡의 종료 코드에 닿지 못하게 한다(continue-on-error 또는 별도 체크). 재사용 워크플로로 바꿀 때는 체크 이름이 "호출부 잡 / 본체 잡" 으로 바뀌어 필수 검사 설정을 먼저 고쳐야 한다는 것도 같은 계열이다.
- **일반화**: 필수 검사가 있는 모든 저장소가 겪는다. 사례 1건이므로 기록만 남긴다. 다만 창고의 `pr-gate-check.yml` 머리말에 그 표를 박아 두어 다음 합치기가 같은 함정을 보게 했다.

### 2026-10-02 — 검사가 실패를 알리는 갈래는 통과하는 동안 아무도 돌려 보지 않는다
- **증상**: `branch-pr-policy.yml` 의 이름 검사는 `set -u` 아래에서 통과했을 때만 정해지는 변수(`branch_note`·`title_note`)를 요약에 출력했다. 위반이 하나라도 있으면 그 줄에서 `unbound variable` 로 죽어 위반 코멘트가 한 번도 남지 않았다 — 통과하는 PR 만 거치는 동안은 드러나지 않는다(Fitstack 에서 같은 줄을 떼어 실행해 재현, 2026-10-01). 창고 원본에도 같은 줄이 있어 물려받은 모든 저장소가 같았다. 이 PR(2026-10-02)에서 창고 쪽을 고쳤다.
- **제안**: 판정 스크립트는 위반 갈래를 한 번은 실제로 돌려 보는 시험을 갖는다 — 가짜 `gh` 와 위반 입력이면 충분하다(Fitstack 이 합치기 전에 그렇게 다섯 경우를 돌렸다). 창고 PR 의 자기 검사에서는 PR 제목을 일부러 형식에 어긋나게 한 번 바꿔(edited 사건) 빨강 → 초록을 본다.
- **일반화**: 다른 저장소도 겪는다. 형태로 보면 **"검사의 실패 갈래는 실패가 날 때만 돌기 때문에 그 갈래 자체의 결함은 통과하는 동안 아무도 모른다"** 는 것이다. 창고의 2026-08-26 항목(YAML 파싱 검증 없이 5회 조용히 실패)과 같은 계열이라 2건째로 볼 수 있다.

### 2026-10-02 — 봇이 여는 초안 PR 은 "Ready" 사건을 듣는 검사만 받는다
- **증상**: 동기화 봇은 초안 PR 을 열고, 봇 토큰이 만든 사건으로는 워크플로가 돌지 않는다. 사람이 Ready for review 를 누른 순간이 첫 기회인데, PR 검사(옛 `pr-gate-check.yml` 과 2026-10-02 의 합친 호출부 모두)는 `ready_for_review` 를 듣지 않았다. 필수 검사로 건 Fitstack 에서 봇 PR #431 이 9/28 부터 사흘 기다리다 수동 재실행 뒤 머지됐다. `sync-skills.yml` 머리말은 "각 저장소의 CI 가 ready_for_review 를 듣고 있어야 한다"고 적었지만, 같은 창고의 PR 검사 견본이 그 약속을 지키지 않았다.
- **제안**: 호출부 견본에 `ready_for_review` 를 더하되, 그 사건에서는 봇이 연 PR 일 때만 잡을 돌린다(사람 PR 은 이미 돌았으므로 건너뛰고, 건너뛴 잡은 청구되지 않는다). 새 PR 검사를 만들 때 "봇이 연 초안 PR 에서 이 검사는 언제 처음 도는가"를 묻는다.
- **일반화**: 동기화 봇이 PR 방식이고 필수 검사가 있는 모든 저장소가 겪는다. 사례 1건이므로 기록만 남긴다. 이 PR 에서 호출부 견본을 고쳤다.
- **정정 (같은 날)**: 위 제안을 `pr-checks.yml` 한 파일에 넣은 판(#95)은 틀렸다. GitHub 은 같은 워크플로·같은 사건 종류의 **가장 최근 실행만** 머지 화면에 보여 준다. 사람 PR 이 Ready 가 되면 "건너뛴" 실행이 하나 더 생겨 PR 을 열 때 성공한 `gate / gate` 를 가렸고, 같은 순간 push 실행은 동시 실행 설정으로 취소돼 있어 필수 검사가 비었다(Fitstack #444 에서 머지 버튼이 잠김). Ready 순간의 호출부를 별도 파일 `pr-checks-bot-ready.yml` 로 옮겨 고쳤다. 일반형: **"조건부로 건너뛰는 실행"은 같은 워크플로의 앞 결과를 가린다 — 건너뛸 수 있는 갈래는 다른 워크플로 파일로 뺀다.**
