# 브랜치·PR 규칙 — 세션 하나는 브랜치 하나를 만들고 PR 하나를 연다

> 한 줄 요지: **요청 하나 = 세션 하나 = 브랜치 하나 = PR 하나.** 브랜치 이름은 `<종류>/<영문-슬러그>`, PR 제목은 `<종류>: <한 문장>`이고 요지는 앞 40자 안에 들어간다. 세션은 시작할 때 이름과 제목을 함께 제안해 승인받고, 그 브랜치 하나에서만 일하며, 브랜치를 만든 직후 초안(Draft) PR 을 연다. 이 규칙은 글로만 있지 않다 — 세션 안에서는 훅(`branch-guard.py`)이 막고, GitHub 쪽에서는 워크플로(`branch-pr-policy.yml`)가 정리한다.

여기서 "브랜치"는 git 의 작업 가지를, "PR"(풀 리퀘스트)은 그 가지를 `main` 에 합쳐 달라는 요청을 말한다. 언제 머지하느냐 같은 절차는 [머지 게이트](../commands/merge-gate.md)와 각 저장소의 `CLAUDE.md` 가 정한다. 이 규칙이 태어난 실측과 설계 논증은 [기획서](../../docs/system-layer/session-branch-pr-plan.md)에 있다.

## 왜 이 규칙이 있나

이름이 제각각이면 **쌓인 뒤에 지워도 되는지조차 판단할 수 없다.** 한 저장소에서 실측하니 원격에 브랜치 87개가 있었고 그중 58개는 이미 머지된 채 남아 있었는데(2026-09-16), 대부분이 `claude/fervent-pasteur-y2g5wr` 처럼 무엇을 하려던 것인지 이름으로 알 수 없는 것이었다.

이름 규칙을 만든 뒤에도 같은 일이 계속됐다. 창고 자신을 재니 브랜치 50개 중 24개가 머지된 채 남아 있었고, 한 브랜치에서 PR 을 5~7개씩 연 세션이 셋이었다(2026-09-29). **규칙이 글로만 있었기 때문이다.** 그래서 이 판(v2)은 원칙을 "세션 = 브랜치 = PR" 하나로 좁히고, 훅과 워크플로를 함께 둔다.

## 1. 브랜치 이름 — `<종류>/<영문-슬러그>`

```
feat/project-group-gen
fix/gen-task-order
mig/project-task-created-at
```

- **종류**는 아래 여섯 중 하나다. 더 만들지 않는다 — 종류가 늘면 고르는 데 시간이 들고 목록에서 묶어 보는 이득이 사라진다.

  | 종류 | 언제 |
  |---|---|
  | `feat` | 새 기능·새 화면 |
  | `fix` | 동작이 잘못된 것을 고칠 때 |
  | `mig` | 데이터베이스 마이그레이션이 들어갈 때 |
  | `refactor` | 동작을 바꾸지 않고 구조만 바꿀 때 |
  | `docs` | 문서·규칙만 바뀔 때 |
  | `chore` | CI·설정·의존성처럼 제품 밖의 것 |

- **슬러그**는 영문 소문자·숫자·하이픈으로 **두세 낱말**이다. 무엇을 하는지가 드러나야 한다 — `fix/bug` 는 슬러그가 아니다.
- **날짜·세션 식별자·PR 번호를 넣지 않는다.** 언제 생겼는지는 GitHub 이 이미 보여 주고, PR 번호는 브랜치를 만든 뒤에야 생긴다. 번호를 넣으려다 이름을 바꾸면 열린 PR 이 닫힌다(2026-09-21 사고).
- **대괄호를 쓰지 않는다.** `[#PR 409]` 같은 형태는 git 이 브랜치 이름으로 받지 않는다.

## 2. PR 제목 — `<종류>: <무엇을 하는지 한 문장>`

```
feat: GEN 단계를 관문에서 서랍으로 바꾼다
fix: 태스크 줄 순서가 고칠 때마다 바뀌던 것을 고정한다
mig: project_task 에 created_at 을 더한다
```

- **종류는 브랜치와 같은 것**을 쓴다. 둘이 다르면 어느 쪽이 맞는지 읽는 사람이 판단해야 한다.
- **한 문장은 "무엇을 하는지"를 평서형으로** 쓴다. `~함`·`~수정` 보다 `~로 바꾼다`·`~을 고정한다` 가 읽힌다.
- **요지가 앞 40자 안에 들어가야 한다.** 목록에서 잘리는 자리가 거기다. 날짜·이슈 번호·절차 이름을 앞에 두지 않는다.
- **제목에 PR 번호를 넣지 않는다.** GitHub 이 제목 옆에 이미 붙여 준다.

## 3. 세션의 순서 — 제안 · 승인 · 브랜치 하나 · Draft PR

세션이 코드나 문서를 바꾸는 요청을 받으면 아래 순서로 간다.

1. **제안.** 요청을 읽고 브랜치 이름과 PR 제목을 **한 번에** 사용자에게 보여 준다. 사용자가 승인한다. 승인 없이 브랜치를 만들지 않는다.
2. **브랜치 하나.** 승인된 이름으로 최신 `main` 에서 딴다. **이 세션에서 브랜치는 이것 하나다.** 두 번째를 만들려 하면 훅이 막는다.
3. **Draft PR 즉시.** 브랜치를 만들면 바로 초안(Draft) PR 을 연다. 본문은 목표 한 줄과 "보는 법" 자리만 비워 둔다. 이렇게 하면 **GitHub 의 열린 PR 목록이 곧 지금 살아 있는 세션 목록**이 되어 한 화면에서 관리된다.
4. **작업.** 그 브랜치에만 커밋한다. 성격이 다른 변경은 **PR 을 나누지 않고 커밋으로 가른다** — 되돌릴 때 `git revert <커밋>` 하나로 그 조각만 빠지게, 커밋 제목에도 같은 종류 접두어를 쓴다(`feat: …`, `docs: …`).
5. **작업완료.** PR 본문을 보고 서식(communication 규칙 7-4의 "어디서·무엇을 하면·무엇이 보이나")으로 채우고 Draft 를 Ready 로 바꾼다. 이 시점의 상태 이름은 **검토대기**다.
6. **보고.** 세션이 끝날 때 브랜치의 상태를 보고에 적는다 — **검토대기**(Ready) 또는 **보류**(Draft 인 채로 둠, 사유 한 줄). 보류는 14일 뒤 정리 후보가 된다.

두 번째 브랜치가 정말 필요한 경우는 하나뿐이다 — 저장소 규칙이 PR 분리를 강제할 때(예: 새 칸을 쓰는 코드와 그 마이그레이션은 같은 PR 로 머지하지 않는다). 그때도 세션은 스스로 만들지 않고, 두 번째 이름을 제안해 승인받는다. 승인은 훅의 일회용 열쇠로 표현된다(6절).

## 4. 하지 않는 것 네 가지

- **한 요청을 여러 PR 로 쪼개지 않는다.** "작게 쪼개 리뷰하기 쉽게"는 사람이 조각을 나눠 검토하는 팀의 관행이고, AI 가 코딩하는 팀에서 실패 복구는 커밋 단위로 충분하다. 실측(Fitstack, 2026-09): 한 달 PR 50건 중 파일 1~2개짜리 18건, 한 브랜치에서 PR 7개. PR 하나가 CI·DB 검사·배포로 약 40분을 쓰므로 **월 Actions 사용량은 사실상 PR 수 × 40분**이었고 조직 한도에 걸려 머지·배포가 멈췄다.
- **머지된 브랜치를 다시 쓰지 않는다.** 머지된 PR 이 있는 브랜치에서 새 PR 을 열지 않는다. 지금까지 PR 번식의 주 경로였다(한 브랜치에서 PR 7개). 다음 요청은 **새 세션, 새 브랜치, 새 PR** 이다. 훅이 막는다.
- **브랜치 이름을 바꾸지 않는다.** 바꾸면 열린 PR 이 닫혀 새 PR 이 생긴다(2026-09-21, 같은 달 두 번 더). 훅이 막는다.
- **`main` 에 직접 push 하지 않는다.** 훅이 막고, GitHub 의 브랜치 보호가 켜진 저장소에서는 GitHub 도 거부한다.

그리고 **머지된 브랜치는 지운다.** GitHub 저장소 설정의 "머지 후 자동 삭제"를 켜 두면 사람이 기억할 필요가 없고, 켜져 있지 않아도 워크플로가 지운다(6절).

## 5. 클라우드 세션과 봇 — 이름만 예외, 나머지는 같다

- **클라우드(claude.ai/code) 세션**은 플랫폼이 `claude/<슬러그>-<난수>` 브랜치를 자동으로 만든다. 이름은 바꿀 수 없고 바꾸면 PR 이 닫히므로, **이름 형식(1절)만 예외**다. 대신 **PR 제목의 `<종류>:` 접두어가 이름을 대신한다** — 워크플로가 이것을 검사한다. 3절의 나머지(브랜치 하나, Draft PR, 커밋으로 가르기)와 4절은 그대로 적용된다. 머지되면 워크플로가 즉시 지운다.
- **봇이 만드는 브랜치**(`chore/sync-warehouse` 등)는 이름이 고정돼 있고 매번 같은 브랜치를 다시 쓴다. 사람이 이름을 고르는 자리가 없으므로 3절이 적용되지 않고, 쌓이지도 않는다. 종류 접두어는 여섯 중 하나를 쓴다.

## 6. 강제 장치 — 훅과 워크플로

| 장치 | 어디서 | 무엇을 하나 |
|---|---|---|
| `.claude/hooks/branch-guard.py` | 세션 안, `Bash` 호출 직전 | 형식에 안 맞는 브랜치 생성, **이 세션의 두 번째** 브랜치 생성, 브랜치 이름 바꾸기, `main` 에서의 push, 머지된 PR 이 있는 브랜치에서의 `gh pr create` 를 **차단**한다. 그 밖의 셸 명령에는 아무 판정도 내지 않는다 |
| `.github/workflows/pr-gate-check.yml` 의 `gate` 잡 | GitHub | PR 이 열리거나 제목이 바뀌거나 브랜치에 푸시되면 브랜치 이름·제목 형식을 검사해 별도 체크 `naming` 을 빨갛게 낸다(머지는 막지 않는다 — 이름 위반은 그 PR 에서 고칠 수 없기 때문이다). 아래 저장소는 이 파일을 복사하지 않고 `workflow_call` 로 부른다(호출부 견본 `templates/workflows/pr-checks.yml`). 2026-10-02 에 `branch-pr-policy.yml` 에서 옮겨 왔다 |
| `.github/workflows/branch-pr-policy.yml` | GitHub | 머지되면 head 브랜치를 지운다. 매주 머지된 채 남은 브랜치를 지우고 14일 이상 방치된 열린 PR 을 잡 요약에 나열한다. API 키 불필요 |

**훅의 일회용 열쇠.** `.claude/branch-unlock` 파일이 있으면 이번 한 번만 통과시키고 즉시 지운다. DB 쓰기 훅과 같은 규약이다 — **Claude 는 사용자가 승인하기 전에 열쇠를 만들지 않는다.** 필요하면 무엇을 왜 하려는지 보여 주고, 승인을 받은 뒤 열쇠를 만들고 실행한다.

**훅이 덮지 못하는 것.** 클라우드 세션은 플랫폼이 브랜치를 만들어 훅이 볼 명령이 없다(워크플로가 받는다). 여러 저장소를 한 폴더에 여는 세션에서는 훅이 실리지 않는 것이 실측됐다(2026-08-17) — 그런 세션에서는 이 규칙을 Claude 가 스스로 지킨다. GitHub MCP 도구로 브랜치·PR 을 만드는 경로는 아직 보지 않는다.

**워크플로는 동기화 봇이 내려보내지 않는다.** 그래서 PR 검사(`pr-gate-check.yml`)는 복사하지 않고 창고 파일을 `workflow_call` 로 부르게 했다(2026-10-02) — 저장소에는 호출부만 두고, 창고를 고치면 다음 실행부터 전부 반영된다. 정리 워크플로(`branch-pr-policy.yml`)는 여전히 저장소마다 사람이 한 번 옮긴다.

## 적용 범위

- 모든 저장소의 모든 세션에 적용된다. 저장소의 `CLAUDE.md` 에 더 구체적인 이름 규칙이 있으면 그것이 이긴다.
- 단일 원본은 창고(Template-repository)의 `.claude/rules/branch-pr-naming.md` 이며, 강제 장치는 `.claude/hooks/branch-guard.py` 와 `.claude/settings.json` 의 `PreToolUse` 설정이다. 셋이 함께 있어야 강제력이 있다 — 번들은 `.claude/workflows/asset-graph.json` 에 선언돼 있다.
- 훅의 판단 시험: `python3 .claude/hooks/branch-guard.test.py`.
