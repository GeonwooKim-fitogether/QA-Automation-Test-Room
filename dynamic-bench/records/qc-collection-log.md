# 레일 QC 수집 일지

> 한 줄 요지: **레일 시험 A · B · C 가 QC 로 쓸모 있는지 가리려고, 셀 세트를 바꿔 가며 같은 절차로 데이터를 모은다.** 이 문서는 PC 나 세션이 사라져도 흐름을 잃지 않도록, 날마다 무엇을 어떤 조건으로 돌렸고 무엇이 남았는지를 적는다. 원본 데이터 위치와 다음 할 일도 여기 있다.

## 1. 목적과 판단 기준

목적은 셀 값이 세트끼리 같은지가 아니라, **시험의 성질이 세트가 바뀌어도 같은지**를 보는 것이다(2026-11-05 사용자). 그래서 세 가지를 세트마다 같은 방법으로 잰다.

| 무엇 | 어떻게 | 쓸모 있다는 뜻 |
|---|---|---|
| 구분력 | 항목마다 같은 셀을 다시 쟀을 때의 흔들림 ÷ 셀끼리 차이 (`motionbench/qc_criteria.py`) | 0.5 이하 — 시험이 셀을 가른다 |
| 불합격이 무엇을 따라가나 | 같은 셀이 자리를 바꿔도 다시 걸리는지, 같은 회차 · 칸에 몰리는지 | 셀을 따라가면 셀 판정에 쓸 수 있다. 칸 · 회차를 따라가면 장비 · 환경 문제다 |
| 장비 무효 비율 | 레일과 장면 출발 차 ±1.0초 밖, 셀 GPS 시각 없음 | 낮고 원인이 설명되면 장비가 안정적이다 |

## 2. 한 바퀴의 절차 (세트마다 같게)

C 10번 → B300 · B100 · B500 각 10번 → A 30분(5분 구간 6개). 독 플러그는 시험 중 끈다(방전 상태). 1바퀴는 원래 자리, 2바퀴는 자리 바꾸기(1열↔3열 · 2열↔4열, 열 안 위아래 뒤집기 — `dock_layout.json` 의 `<세트>-swap`). 실행기는 `cell-bench/tools/qc_loop.py <배치> <앞 바퀴 번호> [수집 폴더]` 이고, B 는 장면을 바꿀 때마다 셀이 GPS 를 잡을 때까지 5분까지 기다린다(90초에 못 잡은 셀은 원격 재부팅. `--no-reboot` 를 주면 재부팅 없이 10분까지 — X5E 부터). 판정은 기준 없이(`--criteria none`) 내고, 멈춘 회차는 판정에서 빠지며 정상 10번이 될 때까지 다시 돈다.

## 3. 세트별 기록

### Y 세트 — CLBY-4B 23대 (2026-11-02 ~ 03)

- 1바퀴(원래 자리) · 2바퀴(Y-swap) · 야간 A 4번. 1차 기준(`motionbench/criteria/rail_v1.json`, 제안값)을 이 데이터로 냈다 — 강한 기준 3개(A 위치 수신률 ≥ 97 %, B 신호 세기 ≥ 43.6 dBHz, B300 속도 비율 0.958 ~ 1.018).
- 10697 은 두 자리 모두 라이브 수신 불합격이 많아 셀 탓, 10699 는 한 자리에서만 걸려 칸 탓으로 갈랐다.
- 조건 차이: 1바퀴와 2바퀴 앞부분은 옛 안테나 위치, 2바퀴 B500 부터 새 위치(11-03 13:06 확정). 1바퀴 B300 초반 4회는 GPS 를 아직 못 잡은 채 돌았다.

### X 세트 — CLBX-6B(X6B) 24대, 11570 ~ 11593 차례대로 (2026-11-05)

- 1바퀴(r01, 원래 자리): 순서가 B → C → A 였다(2바퀴부터 Y 와 같게 C → B → A). 셀 배터리가 끝까지 100 % 라 독 플러그가 켜진 채였을 수 있다. B300 1 ~ 3번째는 플러그 호출 대기로 출발이 늦어 무효.
- 2바퀴(r02, X-swap): C 10번과 B100 이 PC 메모리 부족으로 빠졌고(주기 지연 멈춤, 전자 기어 읽기 실패), 재부팅 뒤 같은 자리에서 채웠다(`r02/C_fill`, `r02/B100_fill`).
- 3바퀴(r03, X-swap): 재부팅 뒤 C · B 를 모두 돌렸고, A 는 21분째(20:00)에 끊겨 그 구간(5분 구간 4개)만 판정했다. 셀 기록은 11-06 01:05 ~ 01:20 에 한 번에 받았다(`data/ftg_x_20261106-010551`).
- 판정 꼬리표: 처음 판정 파일은 세트 이름이 Y 로 적혀 있었다(실행기가 `--set` 을 넘기지 않음, 값과 셀 번호는 X). 11-06 새벽 `--set X` 로 다시 냈고 처음 것은 `rNN/judged_label_Y/` 에 남겼다.
- 발견: 독 왼쪽 위 칸(1열 1행 등)은 B 장면 신호가 약하다 — 자리를 바꾸자 약함이 칸을 따라갔다(셀 탓 아님). 라이브 수신 불합격은 Y 보다 훨씬 적었다(1바퀴 3건, 셀 · 회차 제각각).

### X5E 세트 — CLBX-5E 24대, 34349 ~ 34354 · 34357 ~ 34374, 1열 위부터 차례대로 (2026-11-06)

- 1바퀴(r01, 원래 자리 X5E, 11:40 ~ 13:40): B300 앞에서 위치를 못 잡은 셀을 원격 재부팅했더니 23대 중 6대만 측정으로 돌아와 B 는 16 ~ 18대로 돌았다. 34349 · 34350 은 재부팅 뒤 안 들려 기록을 못 받았다(셀 안에 남아 있다).
- 2바퀴(r02, X5E-swap, 13:49 ~ 16:05): B 장면 원격 재부팅을 끄고(`--no-reboot`) 10분까지 기다렸다 — B300 22대, B100 20대, B500 24대. B500 은 셀 잔량 멈춤 기준에 걸려 9번째에서 끝났다. A 는 시작 때 재부팅이 그대로 돌았고(재부팅 끄기는 B 에만 적용), A 도중 배터리가 다한 셀이 하나씩 꺼져 20대에서 12대로 줄었다. 기록은 들리던 12대 중 9대만 다 받았다(`data/ftg_x5e_20261106-155837`).
- 판정(기준 없이): 강한 기준 셋(A 위치 수신률 · B 신호 세기 · B300 속도 비율)은 모두 합격했다. 불합격은 전부 라이브 수신(rx)이다.
  - C 수신 불합격: 1바퀴 164 / 240(68 %), 2바퀴 66 / 240(28 %). X6B 7 / 696, Y 74 / 460 과 비교해 훨씬 많다.
  - 무엇을 따라가나: 결과판 세션 분석(셀 이동 상관 −0.31, 같은 자리 되풀이 0.35)으로는 셀보다 독 자리(1 ~ 3열 위쪽 1 ~ 4행)를 따라간다. 34352 · 34353 · 34354 는 두 자리 모두 걸렸지만 2바퀴 자리도 1바퀴에 걸린 칸이라 셀 탓으로 단정하지 않는다. 같은 칸이라도 1바퀴가 훨씬 나빠(빠진 패킷 중앙값 11 % 대 2.5 %) 시간대의 무선 환경 영향이 크다 — 원인은 확인하지 못했다.
  - 2바퀴 A 의 rx 불합격은 배터리로 꺼진 셀과 A 시작 때 재부팅한 셀(34357 · 34359 · 34362 · 34369 는 6구간 모두)이 섞여 있어 셀 품질과 따로 본다.
- 셀 기록 지우기(0x13)는 X5E 도 거의 응답하지 않는다(1바퀴 22대 중 1대, 2바퀴 9대 중 1대 지움). 셀 저장량은 1바퀴 뒤 3 ~ 13 MB 로 측정이 멈추는 약 160 MB(Y 실측)까지는 멀다.

### X 대 Y 첫 비교 (2026-11-06 새벽, 3바퀴 전체와 재부팅 뒤만)

같은 방법(`motionbench/qc_criteria.derive`, 기준 파일은 쓰지 않음)으로 쟀다. 오염 의심 회차(11-05 17:15 재부팅 전, 메모리 누수 상태)는 지우지 않고 '재부팅 뒤만' 결과를 따로 냈다. 계산 스크립트와 전체 표는 아래 5절의 `compare_xy.md`.

| 묶음 | 장비 무효 Y | 장비 무효 X (재부팅 뒤) | 셀 불합격 Y | 셀 불합격 X |
|---|---|---|---|---|
| A | 0 % | 6.2 % (4회 중 1회) | 0 / 828 | 1 / 360 |
| C | 0 % | 3.3 % (5 %) | 74 / 460 | 7 / 696 |
| B300 | 15 % | 16.7 % (10 %) | 18 / 391 | 2 / 600 |
| B100 | 25 % | 10 % (10 %) | 6 / 345 | 1 / 648 |
| B500 | 10 % | 10 % (10 %) | 8 / 414 | 2 / 648 |

- **구분력:** Y 에서 낸 강한 기준 셋이 X 에서도 자격(0.5 이하)을 유지한다 — B 신호 세기 0.44 · 0.39 · 0.47, B300 속도 비율 0.34. A 위치 수신률은 X 가 모두 100 % 라 흔들림 자체가 없다. 다만 X 는 대부분 항목에서 셀끼리 차이가 바닥값에 붙어 있다. 셀이 서로 거의 같다는 뜻이어서, 이 데이터만으로 '나쁜 셀을 잡는 힘'이 증명되지는 않는다.
- **불합격이 따라가는 것:** 걸린 항목은 모두 라이브 수신(rx)이다. 11580 이 C 에서 5번 걸렸는데 원래 칸(2-5)과 바꾼 칸(4-2) 양쪽에서 걸렸다 — 셀을 따라가므로 셀 탓이다(Y 의 10697 과 같은 꼴). 나머지는 셀 · 회차가 제각각이다.
- **장비 무효:** 재부팅 뒤에는 B 묶음마다 장면을 바꾼 첫 회차 1번(출발 차 약 −3.3초, 알려진 현상), C 도달 오차 13 µm 1번, A 끊긴 구간 1번뿐이다. 재부팅 전에는 플러그 호출 지연(+34초 · +17초 · −19초)이 더 있었다. 재부팅 전후 값 차이는 작다 — 누수의 영향은 값보다 멈춤 쪽이었다.

## 4. 알려진 장비 문제와 처리

| 문제 | 처리 |
|---|---|
| 장면을 바꾸면 셀이 GPS 를 다시 잡는 데 1 ~ 5분 | `qc_round.gps_ready` 로 기다린다 |
| Tapo 플러그 펌웨어가 TPAP 로 바뀌어 PC 가 못 다룬다(11-05) | `data/plug_manual` 이 있으면 실행기와 충전 지킴이가 플러그를 부르지 않는다(지킴이는 11-06 부터). 사람이 앱으로 켜고 끈다. PC 에 선으로 연결하는 전원 스위치를 검토 중 |
| PC 메모리 누수(11-02 부팅 뒤 사흘 — 남은 메모리 2 GB, 비페이징 풀 2.9 GB) | 주기 지연 멈춤의 유력 원인. 재부팅으로 풀린다('종료'가 아니라 '다시 시작'). 11-05 ~ 06 밤 시험 두 번(`collect_20261105/leak_test.log` · `leak_test2.log`)으로, 1초마다 파일을 새로 써 바꿔 끼우는 일을 **C:\Dev 안에서 하면** 파일 감시 쪽 커널 메모리가 40 ~ 50분에 43 ~ 265 MB 늘고, **C:\Dev 밖에서 하면 늘지 않는다**는 것을 확인했다. 쓰는 방식(새 이름 · 같은 이름 · 덮어쓰기)은 차이를 가르지 않았고, 기록 파일처럼 한 파일에 이어 쓰는 것은 늘지 않았다. 그래서 1초마다 다시 쓰는 실시간 파일(`qc_now.json` · `rail_batt.json`)을 `%LOCALAPPDATA%\cellbench\live` 로 옮겼다(PR #40). C:\Dev 를 감시하는 드라이버 쪽은 손대지 않고 IT 에 확인을 요청한다 |
| X 셀은 기록 지우기(0x13)에 응답하지 않는다 | 받기는 정상. 셀 안 기록이 쌓이므로 저장 공간을 지켜본다 |
| X5E 는 원격 재부팅(0x26) 뒤 측정으로 잘 돌아오지 않는다(11-06: 23대 중 6대, 10대 중 7대) | B 는 `qc_loop.py ... --no-reboot` 로 재부팅 없이 10분까지 기다린다. A 앞 재부팅은 아직 그대로다 |
| X 셀 배터리 % 는 40 %대에서 20분 안에 0 % 로 떨어지고 꺼진다(11-06 2바퀴 A) | 실행기의 잔량 기준(시작 30 % · 멈춤 20 % · 바퀴 사이 35 %)은 Y 에 맞춘 것이고, 들리는 셀만 계산해 꺼진 셀은 빠진다. 바퀴는 꽉 채운 뒤에만 시작한다. 시험 사이 셀 상태 점검(꺼진 셀 · 잔량 · 저장량)은 아직 없다 |
| X 셀은 독에서 충전되는 동안 라이브를 보내지 않는다 | PC 는 충전이 끝났는지 모른다 — Tapo 앱 전력으로 사람이 본다. 지그비 플러그(전력 측정)로 바꾸면 PC 가 판단한다 |
| 기록 받기는 시작 순간 들리는 셀만 받는다 | 꺼진 셀은 충전 뒤 따로 받는다(기록은 셀 안에 남는다) |
| 모터가 도는 동안 같은 PC 의 무거운 일 | 주기 지연 멈춤을 부른다 — 분석 · 시험 · 큰 파일 복사는 모터가 멈췄을 때만 |

## 5. 데이터가 있는 곳

- 수집 원본: 제어 PC 의 `cell-bench/data/collect_<날짜>/` (바퀴 폴더 `rNN/` 안에 시험별 기록 · `judged/` 판정 파일) 과 `cell-bench/data/ftg_<세트>_<시각>/`(셀 기록). git 에 들어가지 않는다.
- 바깥 백업: `tools/backup_drive.py` 가 `cell-bench/data` 전체(11-06 기준 22 GB)를 구글 드라이브 폴더 `<드라이브>/<PC 이름>/cell-bench-data` 로 1시간마다 더하기만 하며 복사한다. 모터 · 시험 · 레일 실행기가 돌면 건너뛴다. 등록은 `tools/install_backup_task.ps1 -Dest <드라이브 폴더>` (구글 드라이브 데스크톱 앱 설치 뒤), 기록은 `data/backup.log`.
- X 대 Y 비교: 계산 스크립트 `compare_xy.py` 와 결과 `compare_xy.md` · `compare_xy.json` 을 `cell-bench/data/collect_20261105/compare/` 에 둔다.
- 실시간 파일(1초마다 다시 쓰는 것): `%LOCALAPPDATA%\cellbench\live\` (11-06 부터, `cellbench.control.live_dir`).
- 결과판에 올라가는 판정 파일: `cell-bench/data/protocol_*.json` → 클라우드 결과판.

## 6. 다음 할 일

1. 실시간 파일을 옮긴 뒤 첫 수집 날에 `mem.log` · `pool.log` 로 커널 메모리가 더는 늘지 않는지 확인한다(실기 확인).
2. X 의 셀끼리 차이가 작아 '나쁜 셀을 잡는 힘'은 아직 증명되지 않았다 — 일부러 다른 셀(불량 이력 셀, 다른 펌웨어)을 섞은 세트로 확인할지 정한다.
3. 구글 드라이브 데스크톱 앱을 깔고 백업 작업을 등록한다(도구는 11-06 에 만들었다).
5. X5E 꺼진 15대의 기록을 충전 뒤 받아 1 · 2바퀴를 24대로 다시 판정하고, 원래 자리로 3바퀴를 돌려 rx 불합격이 시간대를 따라가는지 칸을 따라가는지 가린다.
6. 독 충전 플러그를 지그비(ESP32-C6 + 아카라 플러그, 전력 측정)로 바꿔 충전 끝을 PC 가 판단하게 한다.
4. 칸 차이(왼쪽 위 모서리)를 안테나 위치 조정이나 칸 보정으로 다룰지 정한다.
