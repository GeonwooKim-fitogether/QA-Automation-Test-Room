# 세션 = 브랜치 = PR — 브랜치·PR 정책 기획서

> 한 줄 요지: **Claude Code 세션 하나는 브랜치 하나를 만들고 PR 하나를 연다.** 이 원칙을 규칙 문서로만 두지 않고, 세션 안에서는 훅이 막고 GitHub 쪽에서는 워크플로가 정리하게 만든다. 지난주에 만든 이름 규칙(`branch-pr-naming.md`)이 글로만 있어 지켜지지 않은 것이 출발점이다.

작성일 2026-09-29. 상태: **기획(승인 대기)**. 승인되면 이 문서의 "실행 계획" 절이 그대로 PR 하나가 된다.

---

## 1. 왜 — 실측

창고(Template-repository)를 오늘 잰 결과다.

| 항목 | 실측 |
|---|---|
| 원격 브랜치 | 50개. 그중 **24개는 main 에 이미 머지됐는데 지워지지 않은 것** |
| 이름 | 50개 중 35개가 `claude/…`(클라우드 세션이 자동으로 붙인 이름). 나머지도 `codex/`·`skill/`·`rules/`·`qa-swarm-…` 등 여섯 가지 형식이 섞여 있다 |
| 한 브랜치에서 PR 여러 개 | `claude/sql-auto-execution-93jihj` 에서 PR 6개, `claude/migration-number-collision-prevention-y5yrx3` 에서 7개, `claude/template-repo-system-review-behs7i` 에서 5개 |
| 열린 PR | 3개. 전부 8월 29일에 열려 한 달째 그대로 |
| GitHub 설정 | "머지 후 브랜치 자동 삭제" 꺼짐. `main` 브랜치 보호 없음 |

두 가지 병이 겹쳐 있다.

1. **브랜치가 세션마다 생기는데 세션이 끝나도 사라지지 않는다.** 이름으로 무엇이었는지 알 수 없으니 지우려면 하나씩 열어 봐야 하고, 그 비용 때문에 아무도 지우지 않는다.
2. **한 세션이 한 브랜치에서 PR 을 다섯에서 일곱 개씩 연다.** "작게 쪼개면 리뷰가 쉽고 실패해도 되돌리기 쉽다"는 사람 팀의 관행을 그대로 가져온 것인데, 검토 세부까지 세션이 맡는 이 팀에서는 되돌리기는 커밋 단위로 충분하고 PR 수만 곱절이 된다. PR 하나가 CI·DB 검사·배포로 약 40분을 쓰므로 Actions 사용량이 PR 수에 비례해 늘었고, 9월 말 Fitstack 은 한도에 걸려 머지와 배포가 멈췄다.

규칙 문서(`branch-pr-naming.md`, 2026-09-22)는 이미 이 둘을 금지하고 있다. 그런데 창고의 다른 규칙(DB 쓰기, 폐기 목록)과 달리 **강제 장치가 없다.** 훅도 없고 워크플로도 없다. 규칙이 글로만 있으면 어떻게 되는지는 위 표가 보여 준다.

## 2. 원칙 — 세션 하나, 브랜치 하나, PR 하나

```
요청 하나 ──► 세션 하나 ──► 브랜치 하나 ──► PR 하나 ──► 머지 또는 닫힘 ──► 브랜치 삭제
```

| 단계 | 하는 일 | 누가 |
|---|---|---|
| 세션 시작 | 요청을 읽고 **브랜치 이름과 PR 제목을 한 번에 제안**한다. 사용자가 승인한다 | 세션 제안, 사람 승인 |
| 브랜치 생성 | 승인된 이름으로 `main` 최신에서 딴다. **이 세션에서 두 번째 브랜치는 만들 수 없다**(훅) | 세션 |
| Draft PR | 브랜치를 만든 직후 초안(Draft) PR 을 연다. 본문에는 목표 한 줄만. **열린 PR 목록이 곧 살아 있는 세션 목록**이 된다 | 세션 |
| 작업 | 그 브랜치에만 커밋한다. 성격이 다른 변경은 **PR 을 나누지 않고 커밋으로 가른다** | 세션 |
| 작업완료 | Draft 를 Ready 로 바꾸고 PR 본문을 채운다 (규칙 7 의 보고 서식) | 세션 |
| 머지 | 사람이 머지한다. 머지되면 브랜치는 **즉시 자동 삭제**된다 | 사람, GitHub |
| 다음 요청 | 같은 브랜치를 다시 쓰지 않는다. **새 요청은 새 세션, 새 브랜치, 새 PR** | 사람 |

PR 을 둘로 나누는 유일한 사유는 저장소 규칙이 강제할 때다(예: 새 칸을 쓰는 코드와 그 마이그레이션은 같은 PR 로 머지하지 않는다). 그때도 세션은 두 번째 브랜치를 스스로 만들지 않고, 사용자에게 두 번째 이름을 제안해 승인받는다(훅의 일회용 열쇠).

## 3. 결정 사항 (2026-09-29, 대표 승인)

| 질문 | 결정 | 이유 |
|---|---|---|
| 브랜치 이름에 무엇을 담나 | **`<종류>/<영문-슬러그>` 유지.** 날짜·세션 식별자를 넣지 않는다 | 가장 짧고 목록에서 읽힌다. 언제 생겼는지는 GitHub 이 이미 보여 준다 |
| PR 을 언제 여나 | **세션 시작 때 Draft 로** | 열린 PR 목록이 세션 목록이 되어 GitHub 한 화면에서 관리된다 |
| 클라우드 세션의 `claude/…` 브랜치 | **허용. 대신 PR 제목에 종류를 강제하고, 머지되면 즉시 삭제** | 이름은 플랫폼이 정하니 바꿀 수 없고, 바꾸면 PR 이 닫힌다(2026-09-21 사고) |
| 훅이 위반을 어떻게 다루나 | **차단. 예외는 일회용 열쇠 파일** | DB 쓰기 훅·폐기 훅과 같은 방식. 경고만 하면 지금과 결과가 같다 |

## 4. 세 층의 장치

### 층 1. 규칙 개정 — `.claude/rules/branch-pr-naming.md` v2

기존 규칙의 1·2절(이름 형식)은 그대로 두고, 3·4절을 "세션 = 브랜치 = PR" 절차로 다시 쓴다. 바뀌는 것만 적는다.

- **3절 "세션은 브랜치를 스스로 만들지 않는다" → "세션은 브랜치를 하나만 만든다".** 시작 시 이름과 PR 제목을 함께 제안해 승인받고, 승인된 그 하나만 만든다. 두 번째가 필요하면 다시 승인(열쇠).
- **Draft PR 을 브랜치 생성 직후 연다.** 본문은 목표 한 줄과 "어디서·무엇을 하면·무엇이 보이나" 자리만 비워 둔다. 작업완료 때 채우고 Ready 로 바꾼다.
- **브랜치 재사용 금지를 명문화한다.** 머지된 PR 이 있는 브랜치에서 새 PR 을 열지 않는다. 지금까지 PR 번식의 주 경로였다.
- **클라우드 세션 조항을 바꾼다.** "적용 밖"이 아니라 "이름은 예외, 나머지는 동일". PR 제목의 `<종류>:` 접두어가 이름을 대신한다.
- **커밋으로 가르는 법을 한 줄 예시로 넣는다.** 되돌릴 때 `git revert <커밋>` 하나면 되도록, 성격이 다른 변경은 커밋 제목에 같은 종류 접두어를 쓴다.
- **세션이 끝날 때 브랜치의 상태를 보고에 적는다.** 검토대기(PR Ready) · 보류(Draft 인 채로 둠, 사유) 둘 중 하나. 보류는 14일 뒤 정리 후보가 된다.

### 층 2. 훅 — `.claude/hooks/branch-guard.py` (신설)

`Bash` 호출 직전에 명령을 읽어 아래만 판정한다. 그 밖의 셸 명령에는 아무 판정도 내지 않는다(DB 쓰기 훅의 셸 감시면과 같은 절제).

| 명령 | 판정 | 이유 |
|---|---|---|
| `git checkout -b <이름>` · `git switch -c <이름>` · `git branch <이름>` | 이름이 `<종류>/<슬러그>` 형식이 아니면 **차단**. 이 세션이 이미 브랜치를 만들었으면 **차단** | 형식과 "세션당 하나" |
| `git branch -m` (이름 바꾸기) | **차단** | 바꾸면 열린 PR 이 닫힌다 |
| `git push` 를 `main` 에서, 또는 `git push origin main` | **차단** | main 직접 푸시 금지 |
| `gh pr create` | 현재 브랜치가 `main` 이면 **차단**. 그 브랜치에 이미 머지된 PR 이 있으면 **차단** | 브랜치 재사용으로 PR 이 번식하던 경로 |
| 그 밖의 모든 명령 | 판정 없음 | 셸은 세션이 거의 모든 일을 하는 통로다 |

- **세션 식별.** 훅 입력에 들어오는 `session_id` 로 `.claude/state/branch-guard/<session_id>` 파일에 "이 세션이 만든 브랜치 이름"을 적는다. 두 번째 생성 시도는 이 파일이 있으면 막힌다. `.claude/state/` 는 `.gitignore` 에 넣는다.
- **일회용 열쇠.** `.claude/branch-unlock` 파일이 있으면 이번 한 번만 통과시키고 즉시 지운다. Claude 는 사용자가 승인하기 전에 열쇠를 만들지 않는다(DB 쓰기 규칙과 같은 문장).
- **잴 수 없으면 막지 않는다.** `gh` 가 없거나 인증이 안 돼 머지된 PR 유무를 알 수 없으면 차단하지 않고 그 사실을 판정 이유에 남긴다(적용 전 push 판정과 같은 예외).
- **시험.** `branch-guard.test.py` 가 위 표의 각 행을 재현한다.
- **배선.** `.claude/settings.json` 의 `PreToolUse` 에 `Bash` 매처로 등록하고, `asset-graph.json` 에 번들 `branch-guard`(규칙 + 훅 + 시험)를 선언한다. 훅 없는 규칙이 다시 내려가지 않게 하기 위해서다.

이 훅이 **덮지 못하는 것**을 정직하게 적는다. 클라우드 세션은 플랫폼이 브랜치를 만들므로 훅이 볼 명령이 없다(층 3이 받는다). 여러 저장소를 한 폴더에 여는 세션에서는 훅이 실리지 않는 것이 실측됐다(2026-08-17). GitHub MCP 도구로 브랜치·PR 을 만드는 경로는 이번에는 보지 않는다 — 지금 그 서버가 연결되지 않아 잴 수 없고, 연결되면 매처 한 줄을 더하는 일이다.

### 층 3. 워크플로 — `.github/workflows/branch-pr-policy.yml` (신설)

API 키 없이 `git` 과 `gh` 만으로 돈다(`branch-overlap.yml` 과 같은 설계). 세 가지 사건에 반응한다.

| 사건 | 하는 일 | 판정 |
|---|---|---|
| PR 열림·제목 수정 | 브랜치 이름이 `<종류>/…` 형식인지, `claude/…` 면 제목이 `<종류>:` 로 시작하는지, 제목 요지가 앞 40자 안에 있는지 검사 | **빨간 체크** + 코멘트로 이유와 고치는 법 |
| PR 머지됨 | head 브랜치를 지운다 (`claude/…` 포함) | 삭제 |
| 매주 월요일 + 수동 버튼 | main 에 머지된 채 남은 브랜치를 전부 지운다. 14일 이상 활동 없는 열린 PR 과 21일 이상 활동 없는 브랜치를 잡 요약에 나열한다 | 삭제 + 목록 (열린 PR 은 지우지 않고 보여만 준다) |

- **비용.** 한 번 실행에 1분 안팎, 저장소당 월 30회 이하. 에스컬레이션 규칙 §2-5(쓴 만큼 청구되는 자동화)의 관문 대상이므로 이 기획서의 승인이 그 카드를 대신한다.
- **이 파일은 동기화 봇이 내려보내지 않는다.** `.github/workflows/` 는 저장소마다 사람이 한 번 옮긴다. 첫 대상: 창고 자신, Fitstack, Agent-Studio. 나머지는 필요할 때 옮긴다.
- **첫 실행이 곧 정리다.** 창고에 남은 머지된 브랜치 24개는 이 워크플로의 수동 버튼 한 번으로 지워진다. 스크립트를 사람에게 건네지 않는다(규칙 8-1).

## 5. 사람이 켜는 것 두 가지

이 둘은 GitHub 저장소 설정이라 세션이 대신 켤 수 없다. 저장소마다 한 번씩이다.

**(1) 머지 후 브랜치 자동 삭제**
- **어디서:** GitHub → 저장소 → Settings → General → 아래로 내려 "Pull Requests" 구역
- **무엇을:** "Automatically delete head branches" 체크
- **성공하면:** 다음 머지부터 브랜치가 목록에서 바로 사라진다
- **안 하면:** 층 3 워크플로가 대신 지우지만 머지 직후가 아니라 몇 초 뒤이고, 워크플로가 없는 저장소는 쌓인다

**(2) `main` 브랜치 보호 — PR 을 거쳐야만 머지**
- **어디서:** Settings → Branches → "Add branch ruleset" (또는 classic protection rule)
- **무엇을:** 대상 `main`, "Require a pull request before merging" 켜기. 승인자 수는 0 으로 둔다(혼자 운영)
- **성공하면:** `main` 에 직접 push 하면 GitHub 이 거부한다
- **안 하면:** 훅이 막는 것은 이 세션의 명령뿐이라, 훅이 실리지 않는 세션에서는 main 직접 push 가 가능하다

## 6. 실행 계획 — PR 하나

이 정책 자체를 정책대로 만든다. **브랜치 하나, PR 하나, 커밋은 층별로 가른다.**

| 커밋 | 내용 |
|---|---|
| `docs: 세션=브랜치=PR 기획서를 수록한다` | 이 문서 |
| `docs: 브랜치·PR 규칙을 세션=브랜치=PR 절차로 고친다` | 층 1. `branch-pr-naming.md` v2, README 규칙 표 한 행 갱신 |
| `feat: 브랜치 훅을 만든다` | 층 2. `branch-guard.py` + 시험 + `settings.json` 훅 등록 + `asset-graph.json` 번들 + `.gitignore` |
| `chore: 브랜치·PR 정책 워크플로를 만든다` | 층 3. `branch-pr-policy.yml` (YAML 파싱 검증 후 커밋 — 2026-08-26 교훈) |

제안하는 이름: 브랜치 `feat/session-branch-pr-policy`, PR 제목 `feat: 세션 하나가 브랜치 하나·PR 하나만 만들게 한다`.

머지 뒤에 남는 일(요청 범위 안): 5절의 설정 두 개를 창고에서 켠다. 워크플로 파일을 Fitstack·Agent-Studio 에 옮기는 PR 을 각각 연다(저장소마다 세션 하나). 창고의 열린 PR 3개(#77·#78·#79, 8월 29일)는 정책과 별개로 사람이 머지할지 닫을지 정한다.

## 8. 이 기획이 덮지 않는 것

- **PR 의 크기 상한은 두지 않는다.** "한 요청 = PR 하나"이므로 요청이 크면 PR 도 크다. 그것이 의도다. 리뷰 부담은 PR 본문의 보고 서식(규칙 7)과 커밋 분리가 받는다.
- **세션이 요청 중간에 죽거나 버려질 때** 남는 Draft PR 은 워크플로가 14일 뒤 목록에 올릴 뿐 자동으로 닫지 않는다. 닫는 것은 사람이다.
- **다른 도구(Codex 등)가 만드는 브랜치**(`codex/…`)는 이 훅의 밖이다. 워크플로의 이름 검사와 정리에는 걸린다.
