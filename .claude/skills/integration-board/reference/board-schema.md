# integration-board · config·data 스키마 정본

> **한 줄 요지:** 통합 현황판은 **세 겹**으로 나뉜다. 화면을 그리는 **엔진**은 창고에 고정돼 있고, 프로젝트의 어휘와 관심사는 **config**에, 이번 회차의 사실만 **data**에 담긴다. 화면에 나오는 숫자와 판정 문장은 사람이 쓰지 않고 **엔진이 계산한다.**

이 문서는 `assets/integration_board_engine.py`가 읽는 두 JSON 파일의 규격이다. 엔진은 여기 적힌 규격을 어기는 입력을 **거부하고 아무 것도 만들지 않는다**(종료 코드 2).

이 문서의 예시는 **사내 웹 서비스 팀**(제품 영역이 결제·인증·검색·알림이고, 공용 자산이 API 스키마·디자인 시스템인 팀)을 기본 사례로 든다. 하드웨어 부품·설계변경을 다루는 팀은 그중 **한 가지 사례**일 뿐이며, 그 어휘로 채운 예시는 `assets/board.config.example.json`에 따로 있다. 어느 도메인이든 채우는 방식은 같다 — 엔진은 그 프로젝트가 무엇을 만드는지 모르고, 이름은 전부 config에서 온다.

---

## 0. 세 겹이 각각 무엇을 담나

| 겹 | 사는 곳 | 누가 소유 | 무엇이 들어가나 | 얼마나 자주 바뀌나 |
|---|---|---|---|---|
| 엔진 | 창고 `.claude/skills/integration-board/assets/` | 창고(공통) | 레이아웃, 색, 상호작용, 계산 규칙, **도출 문장** | 거의 안 바뀜 |
| config | 프로젝트 `.integration/board.config.json` | 그 프로젝트 | 팀·제품 영역·공용 자산·자동 검사의 **이름과 설명**, 무엇을 지켜볼지(카드), 경계값 | 분기에 한 번 정도 |
| data | 프로젝트 `.integration/board.json` | 매 실행 | 작업 목록, 상태, 날짜, 위반, **검사 실행 결과** — 사실만 | 실행할 때마다 |

이 구분의 목적은 하나다. **누군가 매번 보고서를 새로 쓰는 것을 막는 것.** 설명 문장은 config에 한 번 적어 두고 계속 재사용하며, data에는 자유 서술 필드가 아예 없다. 그래서 두 번 실행하면 판이 똑같고, 달라지는 것은 숫자뿐이다.

## 1. config — 프로젝트가 소유하는 어휘

최상위에 쓸 수 있는 항목은 아래가 전부다. 다른 이름을 넣으면 "스키마에 없는 항목입니다"로 실패한다.

```
필수:  board · lanes · statuses · areas · cards
선택:  bands · verdicts · assets · checks · teams · drift · honesty · axis · thresholds · text
```

### 1.1 board — 보드의 이름표 (필수)

```json
"board": {
  "title":    "통합 현황판",
  "eyebrow":  "사내 웹 서비스 · Integration Board",
  "subtitle": "네 스쿼드의 일이 하나의 서비스로 맞물리는지 보는 한 장",
  "docTitle": "통합 현황판 — 사내 웹 서비스"
}
```

`title`만 필수다. `docTitle`은 브라우저 탭에 뜨는 이름이며, 없으면 `title`을 쓴다.

### 1.2 lanes — 관심사 열 (필수, 1개 이상)

밴드 1(종합 판정)에서 카드를 묶는 세로 열이다. 화면에는 선언한 순서대로 놓이고, **열 개수만큼 격자가 나뉜다**(4개에 맞춰 고정돼 있지 않다).

```json
"lanes": [ { "key": "delivery", "label": "진척", "en": "Delivery" } ]
```

`key`는 id, `label`은 화면에 크게 나오는 이름, `en`(선택)은 그 옆에 작게 붙는 영문이다.

### 1.3 statuses — 칸반 열 (필수, 1개 이상)

작업이 놓일 수 있는 상태다. 칸반의 열이자 색 범례의 항목이 된다.

```json
"statuses": [
  { "key": "review", "label": "검토대기", "tone": "amber",
    "mean": "반영 요청(PR)이 열려 사람의 승인을 기다리는 중" }
]
```

- `tone`은 **정본 토큰 이름 중에서만** 고른다: `red` · `amber` · `green` · `blue` · `teal` · `dim` · `muted` · `neutral`. 색상 코드(`#ff00ff`)를 직접 쓰면 거부된다. 새 색을 지어내지 못하게 막는 장치다.
- `mean`(선택)은 열 아래 한 줄로 붙는 "이 상태가 무슨 뜻인가" 설명이다.

### 1.4 areas — 제품 영역 (필수, 1개 이상)

작업이 속한 제품의 구획이다. 간트의 부모 행(롤업 행)이 된다.

```json
"areas": [ { "key": "payment", "label": "결제", "en": "Payment" } ]
```

### 1.5 assets — 공용 자산 (선택)

여러 팀이 같이 쓰는 것(API 스키마, 디자인 시스템, 이벤트 규격 등). 하나도 선언하지 않으면 그 구획은 화면에서 사라진다.

```json
"assets": [
  { "key": "apischema", "label": "API 스키마",
    "plain": "여러 클라이언트가 함께 의존하는 요청·응답의 모양",
    "why": "두 팀이 각자 바꾸면 남의 화면이 조용히 깨진다" }
]
```

`plain`은 "뜻"(이게 무엇인가)이고 `why`(선택)는 "걸리면"(어긋나면 무슨 일이 생기나)이다. 이 두 문장이 화면에 그대로 나온다.

### 1.6 checks — 자동 검사 (선택)

> 이름 칸은 다른 항목과 같은 `label`이다. 예전 파일이 쓰던 `name`도 계속 받는다.

지켜야 할 선을 기계가 대신 확인하는 검사다. 밴드 3의 열이 된다.

```json
"checks": [
  { "key": "secscan", "name": "야간 보안 검사",
    "plain": "의존성 목록을 알려진 취약점 데이터베이스와 매일 대조한다",
    "why": "아무도 큐를 보지 않아 알려진 취약점이 그대로 배포된다" }
]
```

**검사의 통과 여부는 여기에 쓰지 않는다.** 그것은 data의 `checkRuns`와 `violations`에서 나오며, 엔진이 계산한다(2.3·2.4 참고).

### 1.7 teams — 팀 명부 (선택)

```json
"teams": ["결제팀", "성장팀", "플랫폼팀", "모바일팀", "데이터팀"]
```

공용 자산 카드에 나오는 **"n팀 중 m팀"의 n**을 무엇으로 셀지 정한다.

- **명부를 선언하면** n은 그 명부의 크기, 즉 **전체 팀 수**다. 대신 모든 작업의 `team`이 명부 안에 있어야 한다(없으면 거부된다 — 그러지 않으면 표시가 거짓말이 된다).
- **선언하지 않으면** n은 **그 자산을 건드린 팀 수**다.

어느 쪽이든, 그 자산과 **무관한** 작업이 늘었다고 분모가 흔들리지 않는다. 이것이 이 절이 있는 이유다.

### 1.8 cards — 밴드 1에서 무엇을 지켜볼 것인가 (필수, 1개 이상)

가장 중요한 절이다. 카드는 "이 프로젝트가 상시로 지켜보는 관심사"이며, **그 카드에 뜨는 숫자와 심각도는 config가 아니라 엔진이 매 실행 계산한다.**

```json
{ "key": "ov-api", "lane": "cohesion", "title": "API 스키마",
  "plain": "여러 클라이언트가 함께 의존하는 요청·응답의 모양",
  "why": "두 방향으로 동시에 바뀌면 남의 화면이 조용히 깨진다",
  "metric": { "kind": "asset", "asset": "apischema" },
  "decide": true,
  "traceChecks": ["apidiff"] }
```

- `lane` — 어느 관심사 열에 놓을지. `lanes`에 없는 값이면 거부된다.
- `metric` — **무엇을 세어 이 카드의 문장을 만들지**(아래 표).
- `decide` — "사람이 정해 주기 전에는 진행할 수 없는 것"인지. `true`라도 배지는 **그 카드가 실제로 위험·주의일 때만** 붙는다. 늘 붙어 있으면 신호가 죽기 때문이다.
- `traceChecks` — 카드를 눌렀을 때 함께 밝힐 자동 검사. 작업·공용 자산 쪽 연결은 지표에서 자동으로 나오므로 적을 필요가 없다.

한 열에 카드가 많으면 급한 순(위험 → 주의 → 정상 → 참고)으로 앞의 몇 장만 펼치고 나머지는 **"그 외 n건 펼치기" 버튼**으로 접는다(몇 장을 펼칠지는 `thresholds.laneMaxCards`, 기본 3). 접힌 카드도 그 버튼을 누르면 그 자리에서 열리므로, 세어 놓고 도달할 수 없는 카드는 없다. 같은 급끼리는 선언한 순서를 지킨다.

#### 지표 종류(metric.kind) — 8가지

| kind | 묶이는 대상 | 엔진이 세는 것 | 나오는 문장(예) | 심각도 판정 |
|---|---|---|---|---|
| `asset` | `asset` | 이 자산을 건드린 팀 수, 그중 충돌·대기 팀 수 | "5팀 중 **2팀**이 서로 다르게 고쳤다" | 충돌 있으면 위험, 대기만 있으면 주의, 없으면 정상 |
| `check` | `check` | 이 검사의 위반 건수, 전체 검사 중 통과 수·미보고 수, 그리고 **해소 작업의 유무**(2.3 참조) | "위반 후보 **1건** · 자동 검사 5개 중 **3개** 통과 · **해소 작업 없음**" | 막힘 위반이면 **위험**, 주의 위반이면 주의, 통과면 정상, **보고 없으면 참고(회색)**. 해소 작업의 유무는 문장에만 나오고 심각도를 바꾸지 않는다 |
| `area_stalled` | `area` | 이 영역에서 가장 오래 멈춘 작업의 `stalledDays` | "검토대기가 **12일**째 움직이지 않는다" | `stallRiskDays` 이상 위험, 1일 이상 주의, **아무도 안 적었으면 참고(회색)** |
| `area_delay` | `area` | 예상 종료가 계획을 넘긴 작업 수와 가장 큰 초과 일수 | "**1건**이 계획보다 **7일** 늦다" | `delayRiskDays` 이상 위험, 1일 이상 주의, **아무도 안 적었으면 참고(회색)** |
| `undated` | (없음) | 계획 날짜가 없어 시간 축에 못 올린 작업 수 | "**1건**이 아직 시간 축에 올라가지 못했다" | 1건 이상 주의 |
| `status_recent` | `status` | 최근 `recentDays`일(기본 7일) 안에 그 상태로 끝난 작업 수 | "최근 7일 배포완료 **1건**" | 항상 참고(좋은 소식은 경보가 아니다) |
| `drift` | (없음) | data의 `drift.gaps` / `drift.pivots` | "기획 이탈 **3건** 누적 · 기획 전환 후보 **1건**" | 항상 참고 |
| `count` | (없음) | `match` 조건에 해당하는 작업 수 | "해당 작업 **2건**" | `riskAt` 이상 위험, `warnAt` 이상 주의, 0이면 정상 |

**"괜찮다"와 "모른다"는 절대 같은 색으로 그리지 않는다.** `check` · `area_stalled` · `area_delay` 세 지표는 각각 판단 근거가 되는 사실을 data에서 요구한다. 그 사실이 하나도 올라오지 않으면 초록불이 아니라 회색 참고 카드로 남고, 문장도 "알 수 없다"라고 말한다.

| 지표 | 판단에 필요한 사실 | 그 사실이 없을 때 나오는 문장 |
|---|---|---|
| `check` | `checkRuns`(검사가 돌았나) | "정보 없음" — 통과로 세지 않는다 |
| `area_stalled` | 작업의 `stalledDays` | "멈춘 기간이 보고되지 않았다 — 이 구획은 아직 알 수 없다" |
| `area_delay` | 작업의 `planEnd`와 `eta` | "계획일과 예상일이 보고되지 않았다 — 늦었는지 알 수 없다" |

이유는 하나다. 아무도 적지 않은 것을 보드가 "이상 없음"이라고 말하면, 읽는 사람은 **모르는 상태를 안전한 상태로 착각한다.** 사실이 아닌 초록불은 보드가 아예 없는 것보다 나쁘다.

`count`는 위 7종에 없는 걱정거리를 위한 **탈출구**다. 숫자를 손으로 적는 것이 아니라 조건을 선언하면 엔진이 데이터에서 센다.

```json
{ "kind": "count", "match": { "block": "waiting" }, "warnAt": 1, "riskAt": 4 }
```

- `match`는 최소 1개가 필요하고, 셀 수 있는 항목은 작업이 실제로 가진 것뿐이다: `area` · `status` · `team` · `block` · `touches` · `drift`. 여러 개를 적으면 **모두** 만족하는 작업만 센다.
- `warnAt`(기본 1)과 `riskAt`(선택)은 몇 건부터 주의·위험으로 볼지다.

### 1.9 bands — 세 밴드의 이름 (선택)

`overview` · `delivery` · `quality` 세 개만 쓸 수 있고, 각각 `n`(번호표) · `title` · `en` · `caption`을 덮어쓸 수 있다. 적지 않으면 "밴드 1 / 종합 판정 / Executive Overview / 지금 무엇을 결정해야 하나" 같은 기본값이 쓰인다.

### 1.10 verdicts — 종합 판정의 말 (선택)

```json
"verdicts": { "risk": { "word": "위험", "why": "공용 자산 충돌이 풀리지 않았다 — 해소 전에는 본선 반영을 멈춘다" } }
```

`risk` · `warn` · `ok` 세 가지에 각각 `word`(크게 나오는 한 단어)와 `why`(그 아래 한 줄)를 정할 수 있다. **색은 의미색이라 엔진이 고정한다**(위험은 빨강, 주의는 주황, 정상은 초록).

판정 자체는 다음 규칙으로 엔진이 정한다.

1. 카드 중 하나라도 **위험**이거나, 자동 검사 중 하나라도 **막힘(block) 위반**이 있으면 → 위험.
2. 그렇지 않고 카드 중 **주의**가 있으면 → 주의.
3. 둘 다 없으면 → 정상.

실행 결과가 보고되지 않은 검사가 있으면, 판정 상자 아래에 **"자동 검사 n개는 실행 결과가 보고되지 않았다"**가 함께 뜬다. 초록 램프가 "다 확인했다"로 읽히지 않게 하려는 장치다.

### 1.11 drift — 기획 정합성 막대 (선택)

```json
"drift": { "gapLabel": "기획 이탈", "pivotLabel": "기획 전환 후보",
           "note": "만들다 보니 원래 기획과 어긋난 곳 — 기획을 고칠지 사람이 정하는 입구",
           "linkLabel": "기획 정합성 상세", "href": "#" }
```

`gapLabel`과 `pivotLabel`은 필수다. data에 `drift`가 있는데 config에 이 절이 없으면(또는 그 반대면) 엔진이 거부한다.

### 1.12 honesty — 이 보드가 못 보는 것 (선택)

보드 맨 아래 한 문단. 초록불이 곧 좋은 제품을 뜻하지 않는다는 식의 한계 고백을 적는다. 비워 두면 그 줄이 사라진다.

### 1.13 axis — 시간 축의 기하 (선택)

```json
"axis": { "leadDays": 14, "days": 84, "tickDays": 7 }
```

`leadDays`는 오늘 기준으로 축을 며칠 앞에서 시작할지, `days`는 축 전체 길이, `tickDays`는 눈금 간격이다. 축 시작일은 **오늘에서 계산**되므로 손으로 적지 않는다.

축보다 멀리 있는 계획(예: 84일 축에 내년 일정)은 **거부되지 않는다.** 대신 축 양끝에 **"축 이전 n건" · "축 이후 n건"** 표식이 붙어, 화면에 막대가 없는 작업이 몇 건인지 말해 준다. 눈금 글자는 보통 `07-19`처럼 나오지만, **첫 눈금과 연도가 바뀌는 눈금에는 연도가 붙는다**(3년짜리 축에서 `01-04`가 세 번 나오면 어느 해인지 알 수 없기 때문).

### 1.14 thresholds — 위험 신호의 경계값 (선택)

```json
"thresholds": { "stallRiskDays": 14, "delayRiskDays": 30, "recentDays": 7, "laneMaxCards": 3 }
```

프로젝트마다 리듬이 다르다. 2주 스프린트로 도는 팀에게 "30일 늦으면 위험"은 너무 늦고, 리드타임이 반년인 프로젝트에는 너무 민감하다. 그래서 이 네 개만 열어 둔다.

| 항목 | 뜻 | 기본값 |
|---|---|---|
| `stallRiskDays` | 며칠 이상 멈춰 있으면 '위험'인가 (1일 이상은 '주의') | 14 |
| `delayRiskDays` | 계획보다 며칠 이상 늦으면 '위험'인가 (1일 이상은 '주의') | 30 |
| `recentDays` | `status_recent`가 보는 "최근"이 며칠인가 | 7 |
| `laneMaxCards` | 관심사 열에 처음부터 펼쳐 두는 카드 수 | 3 |

적지 않으면 기본값이 쓰이므로, 지금까지 쓰던 config는 그대로 같은 판정을 낸다.

### 1.15 text — 화면 문구 덮어쓰기 (선택)

버튼·라벨·안내문 같은 **고정 문구**에 전부 기본값이 있어, 이 절이 없어도 보드는 그대로 동작한다. 프로젝트 어휘에 맞추고 싶을 때만 덮어쓴다. 목록에 없는 키를 쓰면 거부된다.

`metaPrefix` `metaSuffix` `metaNote` `themeLight` `themeDark` `legendTitle` `legendConflict` `legendWaiting` `legendTrace` `band1Hint` `verdictKicker` `decideCount` `decideHint` `decideBadge` `verdictNoData` `countUnit` `laneOk` `laneMore` `laneLess` `meanLabel` `whyLabel` `viewSwitchLabel` `viewNote` `tabKanban` `tabKanbanEn` `tabGantt` `tabGanttEn` `assetsTitle` `blockConflict` `blockWaiting` `areaBadgeConflict` `areaBadgeWaiting` `areaCount` `areaCountUndated` `ganttAxisLabel` `ganttEmptyArea` `ganttDelayTip` `ganttLegPlan` `ganttLegFill` `ganttLegDelay` `ganttLegDep` `ganttLegToday` `ganttLegDue` `ganttLegHint` `axisOffBefore` `axisOffAfter` `axisOffTip` `undatedGroup` `undatedCount` `undatedRow` `checkPass` `checkWarn` `checkBlock` `checkSkipped` `checkNever` `checkUnknown` `vioBlock` `vioWarn` `vioNoTarget` `okNone` `noData` `traceChip` `traceOff` `assetBadgeConflict` `assetBadgeWaiting` `assetBadgeOk`

자리표시자를 쓸 수 있는 문구는 정해져 있고, **그 문구가 허용하지 않는 이름을 쓰면 거부된다**(오타 `{count}`가 화면에 그대로 찍히는 일을 막는다).

| 문구 | 쓸 수 있는 자리표시자 |
|---|---|
| `laneMore` · `areaBadgeConflict` · `areaBadgeWaiting` · `areaCount` · `undatedCount` · `axisOffBefore` · `axisOffAfter` | `{n}` |
| `areaCountUndated` | `{n}`(날짜 있는 건수) · `{u}`(미정 건수) |
| `assetBadgeConflict` · `assetBadgeWaiting` | `{n}`(해당 팀 수) · `{all}`(분모, 1.7 참고) |
| `verdictNoData` | `{unknown}`(실행 결과가 보고되지 않은 검사 수) |

## 2. config로 바꿀 수 없는 것 (중요)

위 1.15의 문구 목록을 보고 "화면의 모든 글자를 바꿀 수 있다"고 읽으면 안 된다. **바꿀 수 없는 것이 분명히 있고, 그것이 이 스킬이 매 실행 같은 판을 내는 이유다.**

1. **도출 문장.** "5팀 중 **2팀**이 서로 다르게 고쳤다", "**1건**이 계획보다 **7일** 늦다" 같은 계산 문장은 엔진 안(`READ`)에 고정돼 있다. config로 덮어쓸 수 없고, `config.text`에 `readXxx` 같은 키를 넣으면 "알 수 없는 문구 키"로 거부된다. 문장을 프로젝트마다 바꿀 수 있게 열어 두면 같은 숫자가 프로젝트마다 다른 뜻으로 읽히기 때문이다. 그 문장 안에 들어가는 **이름**(제품 영역·상태·공용 자산·기획 용어)만 config에서 온다.
2. **숫자 강조 색.** 위험은 빨강, 주의는 주황, 정상은 초록, 참고는 회색. `[[ ]]` 같은 강조 표시를 `text`에 넣으면 거부된다.
3. **판정 규칙과 심각도 계산.** 무엇을 위험으로 볼지의 **골격**은 엔진이 정한다. 프로젝트가 조절할 수 있는 것은 1.14의 경계값 숫자뿐이다.
4. **레이아웃·색 팔레트·상호작용.** 세 밴드의 구조, 칸반/간트 전환, 연결 보기, 테마는 고정이다. 열 **개수**는 데이터를 따르지만, 열의 생김새는 따르지 않는다.
5. **밴드의 개수와 순서.** `bands`로 이름은 바꿔도 세 밴드를 넷으로 늘리거나 순서를 바꿀 수는 없다.

바꿀 수 있는 것은 결국 **이름·설명·고정 라벨·경계값·무엇을 지켜볼지**이며, **판정의 문법과 판의 모양은 창고가 갖는다.**

## 3. data — 이번 회차의 사실

```
필수:  today · works
선택:  updated · target · violations · checkRuns · drift
```

### 2.1 머리

```json
"today": "2026-07-27",
"updated": "2026-07-27 09:15",
"target": { "date": "2026-09-10" }
```

`today`는 오늘선이 서는 자리이자 시간 축의 기준이다. `target`(선택)은 목표일 파선이다. `updated`(선택)는 **`YYYY-MM-DD` 또는 `YYYY-MM-DD HH:MM` 형식만** 쓸 수 있다 — "이번 주 회의 직전 기준" 같은 자유 서술이 여기로 새어 들어오지 못하게 막는다.

### 2.2 works — 작업 목록 (필수, 1개 이상)

```json
{ "id": "PR-812", "title": "결제 응답 구조 분리",
  "area": "payment", "team": "결제팀", "status": "review",
  "block": "conflict", "touches": ["apischema", "eventspec"],
  "planStart": "2026-07-14", "planEnd": "2026-07-28",
  "progress": 85, "eta": "2026-08-14", "completedAt": "2026-07-23",
  "deps": ["PR-800"], "stalledDays": 5, "drift": true }
```

| 항목 | 필수 | 뜻과 규칙 |
|---|---|---|
| `id` | 필수 | 작업의 고유 id. 중복되면 거부된다. |
| `title` | 필수 | 작업 이름. 화면에 그대로 나오는 유일한 자유 문자열이다(설명이 아니라 **이름**이므로 허용). |
| `area` | 필수 | config의 `areas`에 있는 key여야 한다. |
| `team` | 필수 | 팀 이름. 공용 자산의 "n팀 중 m팀"을 셀 때 쓰인다. `config.teams` 명부를 선언했다면 그 안에 있어야 한다. |
| `status` | 필수 | config의 `statuses`에 있는 key여야 한다. |
| `block` | 선택 | `conflict`(충돌) 또는 `waiting`(대기)만 쓸 수 있다. 막힘은 상태가 아니라 사정이므로 열이 아닌 표식으로 붙는다. |
| `touches` | 선택 | 이 작업이 건드리는 공용 자산. **여러 개면 배열**(`["a","b"]`), 하나면 문자열 하나(`"a"`)로도 쓸 수 있다. |
| `fixes` | 선택 | **이 작업이 해소하는 자동 검사.** config의 `checks` key를 가리키며, `touches`와 같은 규칙으로 배열도 문자열 하나도 쓸 수 있다. `touches`가 "무엇을 건드리나"라면 `fixes`는 "무엇을 고치나"이므로 방향이 반대다. 아래 2.3의 마지막 항목이 이 값이 없을 때 무슨 일이 벌어지는지 설명한다. |
| `planStart`·`planEnd` | 선택 | 계획 구간. **둘은 함께 있거나 함께 없어야 한다.** 없으면 "일정 미정" 그룹으로 간다. |
| `progress` | 선택 | 0~100 정수. 없으면 0. |
| `eta` | 선택 | 예상 종료일. `planEnd`가 있어야 쓸 수 있다. `planEnd`를 넘기면 지연 빗금이 그려진다. |
| `completedAt` | 선택 | **실제로 끝난 날.** `status_recent` 지표가 먼저 이 값을 보고, 없을 때만 `planEnd`로 물러난다. 계획보다 늦게 나간 것을 세지 못하거나, 계획 날짜가 없는 작업이 영원히 0으로 남는 것을 막는다. |
| `deps` | 선택 | 선행 작업 id 목록. 없는 id나 자기 자신을 넣으면 거부된다. |
| `stalledDays` | 선택 | 며칠째 움직이지 않았나. `area_stalled` 지표가 쓴다. |
| `drift` | 선택 | 기획과 어긋난 작업인지. `drift` 카드가 연결선을 그릴 때 쓴다. |

### 2.3 violations — 자동 검사에 걸린 것 (선택)

```json
"violations": [
  { "check": "apidiff", "ref": "PR-812", "severity": "warn" },
  { "check": "secscan", "severity": "block" }
]
```

- `check`는 config의 검사 key다(필수).
- `ref`(**선택**)는 걸린 작업의 id다. 야간 보안 검사나 의존성 취약점처럼 **특정 작업이 아니라 저장소·의존성 단위로 걸리는 위반**이 실제로는 더 흔하므로, 가리킬 작업이 없으면 비워 둔다. 그때 화면에는 "특정 작업 지정 없음"이 뜬다. 있는 id를 잘못 적으면(존재하지 않는 작업) 거부된다.
- `severity`는 `block`(막힘) 또는 `warn`(주의)뿐이다.
- **위반을 설명하는 문장은 적지 않는다.** 화면에는 참조된 작업의 제목이 그대로 나온다. 매 실행 새로 쓰이는 설명문을 없애기 위해서다.

#### 위반과 "그럼 누가 고치나" — `ref`와 `fixes`는 방향이 반대다

`ref`는 **위반을 일으킨 작업**을 가리킨다. 그런데 절대규칙 위반(데이터베이스 가드가 없다, 공개 테이블이 잠기지 않았다 같은 것)은 특정 작업이 일으킨 것이 아니라 저장소나 데이터베이스 전체가 그 상태인 것이므로, 일으킨 작업이 애초에 없다. 그래서 `ref`가 비고, 화면에는 "특정 작업 지정 없음"이 뜬다. 여기서 사람이 실제로 알고 싶은 것은 반대 방향의 정보다 — **"그럼 이걸 누가 고치고 있나."**

그 답을 담는 자리가 작업 쪽의 `fixes`다. 어떤 작업이 `fixes`로 검사를 가리키면, 그 검사 카드를 눌렀을 때 밴드 2에서 그 작업이 함께 밝아진다. 걸린 검사에 대해 엔진은 세 상태를 구분한다.

| 데이터 상태 | 화면 | 왜 이렇게 갈랐나 |
|---|---|---|
| 이 검사를 가리키는 작업이 있다 | **해소 작업 n건** (초록) + 그 작업 id, 밴드 2 연결 | 위반과 그것을 고치는 일이 이어진다 |
| 데이터가 `fixes`를 쓰는데 이 검사만 가리키는 작업이 없다 | **해소 작업 없음** (빨강, 밴드 1 문장에도 올라간다) | 위반이 떠 있는데 아무도 손대지 않고 있다는 사실은 위반 자체보다 급하다 |
| 데이터 전체에 `fixes`가 한 번도 쓰이지 않았다 | **해소 작업 미보고** (회색 점선, 밴드 3에만) | 아무도 적지 않은 것을 "없다"고 말하면 모르는 것을 아는 것으로 바꿔 말하는 셈이다 |

통과한 검사에는 이 줄이 붙지 않는다. 고칠 것이 없는데 "해소 작업 없음"을 띄우면 신호가 죽기 때문이다.

### 2.4 checkRuns — 검사가 이번 회차에 실제로 돌았나 (선택, 그러나 권장)

```json
"checkRuns": {
  "lint": "pass",
  "apidiff": "fail",
  "secscan": "fail",
  "integration": "pass",
  "perf": "never"
}
```

**이 절이 없으면 검사는 통과가 아니라 "정보 없음"이 된다.** 위반이 하나도 없다는 사실만으로 초록불을 켜면, 검사를 아직 붙이지 않은 새 프로젝트가 "전부 통과"로 보인다. 사실이 아닌 초록불은 보드가 아예 없는 것보다 나쁘다.

| 값 | 뜻 | 화면 |
|---|---|---|
| `pass` | 돌았고 아무 것도 걸리지 않았다 | 초록 "통과" |
| `fail` | 돌았고 걸린 것이 있다 | 위반의 무게에 따라 빨강 "위반" 또는 주황 "주의" |
| `skipped` | 이번 회차에는 건너뛰었다 | 회색 "건너뜀" |
| `never` | 아직 한 번도 돌린 적이 없다 | 회색 "실행된 적 없음" |
| (적지 않음) | 보고가 없다 | 회색 "정보 없음" |

규칙 두 가지가 더 있다.

1. `pass`라고 적었는데 그 검사의 위반이 올라와 있으면 **거부된다.** 둘 중 하나는 틀린 말이므로 화면에 올리지 않는다.
2. `skipped` · `never`라고 적었는데 위반이 올라와 있으면, 그 검사는 분명히 돌았다고 보고 **위반 쪽을 따른다.** 올라온 사실이 보고보다 강하다.

`checkRuns`를 아예 쓰지 않는 예전 data도 그대로 동작한다. 다만 위반이 올라온 검사만 상태가 정해지고, 나머지는 "정보 없음"으로 남는다.

### 2.5 drift — 기획 정합성 숫자 (선택)

```json
"drift": { "gaps": 3, "pivots": 1 }
```

## 4. 엔진이 계산하는 것 (사람이 쓰지 않는 것)

아래는 전부 도출값이다. data에 적을 자리가 없고, 적으려 하면 "스키마에 없는 항목"으로 거부된다.

1. **종합 판정**(위험·주의·정상)과 **결정 필요 건수**, 그리고 **보고되지 않은 검사 수**.
2. **밴드 1 카드의 문장과 심각도** — 지표 종류별 계산(1.8의 표).
3. **관심사 열의 카드 정렬**과 "그 외 n건".
4. **공용 자산별 집계** — 몇 팀이 건드렸고 그중 몇 팀이 충돌인가.
5. **칸반 열별 건수**.
6. **간트 영역 롤업** — 계획 구간은 자식의 최소~최대, 진척률은 기간 가중 평균, 예상 종료는 자식의 최댓값, 지연은 예상 종료가 계획 종료를 넘겼는지로 판정.
7. **"일정 미정" 그룹 분리** — 날짜가 없는 작업은 영역 아래에 두지 않고 따로 모은다(양쪽에 두면 같은 작업을 두 번 세게 된다).
8. **자동 검사별 상태**(2.4의 규칙)와 통과·미보고 개수, 그리고 걸린 검사의 **해소 작업 상태**(있음·없음·미보고 — 2.3의 표).
9. **시간 축** — 축 시작일, 눈금 글자, 오늘선, 목표일선, 축 밖 건수.
10. **연결 보기의 연결 대상** — 카드에서 작업·공용 자산·검사로 이어지는 선. 자동 검사 카드는 **두 방향을 합친다** — 위반을 일으킨 작업(`ref`)과 해소하는 작업(`fixes`). 절대규칙 위반에는 일으킨 작업이 없으므로 실제로 밴드 2로 이어지는 것은 대개 뒤쪽이다.
11. **격자 열 수** — 관심사 열·칸반·검사·공용 자산의 개수에 맞춰 계산한다. 한 줄에 다 넣기에 너무 많으면 줄을 고르게 나눈다(검사 8개면 4+4).

## 5. 검증이 막는 것

엔진은 오류를 하나 만나고 멈추지 않고 **찾을 수 있는 것을 전부 모아 한 번에** 보여 준 뒤 종료 코드 2로 끝난다. 이때 HTML은 만들어지지 않는다.

막히는 것은 다음과 같다.

1. 필수 항목 누락.
2. **스키마에 없는 여분 필드** — 산문이나 요약문을 끼워 넣으려는 시도가 여기서 막힌다.
3. 알 수 없는 값 — 상태·막힘 사유·위반 무게·지표 종류·색 이름·문구 키·검사 실행 결과.
4. **없는 id 참조** — config에 없는 제품 영역·공용 자산·자동 검사·관심사 열, data에 없는 작업, 명부에 없는 팀.
5. id 중복, 자기 자신을 선행 작업으로 지정.
6. 날짜 문제 — 형식 오류, 달력에 없는 날짜, 종료일이 시작일보다 빠른 경우, 계획 시작·종료 중 한쪽만 있는 경우, `updated`에 자유 서술.
7. 범위 문제 — 진척률이 0~100 밖, 눈금 간격이 축 길이보다 큼, 경계값이 0 이하.
8. 짝이 안 맞는 선언 — `drift` 카드가 있는데 데이터가 없거나 그 반대, `pass` 보고와 위반이 서로 어긋남.
9. 문구 문제 — 그 문구에 없는 자리표시자, 문구에 넣은 `[[ ]]` 강조 표시, 엔진이 고정한 도출 문장을 덮어쓰려는 시도.
10. **타입 오류** — 어떤 항목에 무엇이 들어오든(배열 자리에 객체, 라벨 자리에 숫자 등) 파이썬 예외가 아니라 검증 오류로 나온다.

오류 메시지는 "어디가(경로) · 무엇이 틀렸고 · 무엇을 쓸 수 있는지"를 함께 적는다.

```
통합 현황판 엔진 — 검증 실패 1건. 아무 것도 렌더하지 않았습니다.
  1. data.works[PR-812].touches[1]: 공용 자산 'eventspecs'를 찾을 수 없습니다
       └ 선언된 값: apischema, designsys, eventspec
```
