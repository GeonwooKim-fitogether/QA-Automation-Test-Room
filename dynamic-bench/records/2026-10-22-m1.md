# 2026-10-22 M1 읽기 전용 모니터 — 실측 기록

> **결론:** M1 의 10분 읽기 전용 시험을 2026-10-22 17:16:53–17:26:53 KST 에 EtherCAT SAFE-OP 에서 끝까지 돌렸고, 안전 규칙에 걸린 중단 없이 정상 종료했다. 297,689주기 동안 **WKC 오류 0**(응답 대기 20 ms 기준), 주기 간격 **p99 2.747 ms**(목표 ≤ 4 ms 통과), **최대 19.338 ms**(기준 ≤ 20 ms 를 0.66 ms 차로 통과)였다. Statusword 는 전 구간 `0x0250`(Switch on disabled) 하나뿐이라 **Operation Enabled 는 한 번도 없었고**, 0x603F 는 내내 0, 0x60FD 는 내내 `0x41020000` 이었다. 0x1018:04 는 `0x25010217` 로 읽혀 명판 시리얼 25010217 과 같다. plan-v2 M1 점검 8개 중 기계가 할 수 있는 부분은 모두 통과했고, 사람이 할 항목(③ 부호 s, ④ 의 센서 대응, ⑧ 의 cell-bench 24시간 공존)은 미실시다. 판단이 하나 필요하다 — WKC 오류 0 은 응답 대기를 SOEM 기본 2 ms 에서 20 ms 로 늘린 정의의 값이고, 2 ms 정의였다면 이 USB 랜카드의 늦은 응답 때문에 오류가 세어졌다(잃은 프레임은 0, 4.2절).

작성: 2026-10-22, M1 개발 세션(kimdeveloper). 지시문은 [`dev/m1-prompt.md`](../dev/m1-prompt.md), 통과 기준은 [`plan/plan-v2.md`](../plan/plan-v2.md) 5.1 의 M1 행(v1 의 6개 + ⑦ ⑧)이다. 이 기록에서 모터는 한 번도 움직이지 않았다 — 프로그램은 서보를 켜는 명령을 보낸 적이 없고, EtherCAT 상태는 SAFE-OP 를 넘은 적이 없다.

처음 나오는 용어 몇 개를 먼저 풀어 둔다.

| 용어 | 뜻 |
|---|---|
| SAFE-OP | EtherCAT 의 한 상태. 드라이브가 자기 입력(위치·상태)은 PC 로 보내지만, PC 가 보낸 출력(명령)은 **적용하지 않는다.** M1 은 여기까지만 간다 |
| PDO | 2 ms 마다 PC 와 드라이브가 주고받는 고정 크기 데이터. 출력 9 byte(Controlword 등), 입력 23 byte(Statusword · 위치 등) |
| SDO | 필요할 때 객체 하나씩 묻고 답하는 통로. M1 은 **읽기만** 한다 |
| WKC (Working Counter) | 프레임이 드라이브를 지나며 제대로 처리됐는지 세는 숫자. 이 구성에서 기대값은 3 이고, 다르면 그 주기의 입력은 믿을 수 없다. `-1` 은 기다리는 시간 안에 응답 프레임이 안 왔다는 뜻이다(NOFRAME) |
| Statusword (0x6041) | 드라이브가 자기 상태를 비트로 알려 주는 값. `0x0250` 은 Switch on disabled — 서보가 꺼져 있고 켜질 준비도 안 된 상태다 |
| p99 | 측정값의 99 % 가 이 값 이하라는 뜻(최근접 순위). p99.9 도 같은 방식 |
| 왕복 시간(RTT) | PC 가 프레임을 보내기 직전부터 응답을 받은 직후까지. USB 랜카드의 지연이 여기에 보인다 |

### 1.1 주기 통계

"주기 간격"은 연속한 두 주기에서 응답을 받은 시각의 차다. 2 ms 마다 한 줄씩 남는 기록(CSV)의 줄 간격과 같은 것이다.

| | 주기 간격 | 왕복 시간 |
|---|---|---|
| 개수 | 297,688 | 297,689 |
| 최소 | 0.797 ms | 0.118 ms |
| 평균 | 2.016 ms | 1.197 ms |
| 중앙값 (p50) | 2.056 ms | 1.171 ms |
| **p99** | **2.747 ms** (목표 ≤ 4 ms) | 1.515 ms |
| p99.9 | 4.871 ms | 4.020 ms |
| **최대** | **19.338 ms** (기준 ≤ 20 ms) | 19.272 ms |
| 늦은 것 | 4 ms 초과 1,001건 (0.34 %) | 2 ms 초과 1,844건 (0.62 %) |
| 10 ms 초과 | 5건 | 5건 |
| 20 ms 초과 | 0건 | 0건 |

프로그램 안에서 낸 요약과 별개로, 시험이 끝난 뒤 CSV 를 따로 읽어 같은 값을 다시 계산했고 모든 숫자가 일치했다.

**큰 간격은 응답이 늦게 온 주기에서 나온다.** 9 ms 를 넘은 간격 8건은 모두 그 주기의 왕복 시간이 간격과 0.31 ms 안으로 같았다.

**짧은 간격은 마감 시각을 절대 시각으로 잡았기 때문에 생긴다.** 한 주기의 응답이 조금 늦게 오거나 sleep 이 조금 늦게 깨면, 다음 주기는 원래의 2 ms 격자에 맞추려고 그만큼 일찍 온다. 그래서 1.5 ms 보다 짧은 간격이 13,517번 있고, 가장 짧은 0.797 ms 의 바로 앞 간격은 2.421 ms 였다. 다음 마감 시각까지 넘길 만큼 늦으면 다음 주기는 기다리지 않고 곧바로 보내고 그 시각부터 다시 2 ms 를 센다 — 늦은 만큼 몰아 보내지 않는다. 그래서 10분 동안의 주기 수는 300,000 이 아니라 297,689 다(격자가 모두 합쳐 약 4.6초 밀렸다).

**큰 지연은 한 번에 몰려 왔다.** 왕복 시간이 8 ms 를 넘은 11건 중 10건이, 그리고 10 ms 를 넘은 5건 전부가 17:22:12–17:22:15 의 3초 안에 있었다(나머지 1건은 17:18:40 의 9.7 ms). 최대 19.338 ms 도 이 3초 안이다. 원인은 확인하지 못했다. 이 세션이 시험이 끝나기를 기다리려고 같은 PC 에서 파이썬 프로세스를 하나 더 띄운 시각(17:22 경)과 겹친다 `[추정]`. 이 3초가 없었다면 최대는 10 ms 아래였다. 최대값의 여유가 0.66 ms 뿐이라는 것은 M2 이후 "20 ms 초과 시 경고 · 50 ms 초과 시 자동 Quick stop"(plan-v1 1.4) 문턱을 정할 때 함께 봐야 한다.

**왕복 시간의 바닥은 0.1 ms 대다.** 평소 1.17 ms 걸리는 왕복이 22번은 0.5 ms 안에 끝났다(최소 0.118 ms). 평소의 약 1.1 ms 는 선을 오가는 시간이 아니라 USB 랜카드가 받은 프레임을 모았다가 넘기는 지연일 가능성이 크다 `[추정]`.

### 1.2 WKC

297,689주기 모두 WKC = 3(기대값 3)이었다. 오류 0건, 3주기 연속 불일치로 멈춘 일도 없다. 이것은 응답 대기 20 ms 정의에서의 값이다(4.2절, '결정 필요' 1).

### 1.3 드라이브에서 읽은 값

| 객체 | 10분 동안 관측된 값 | 해석 |
|---|---|---|
| 0x6041 Statusword | `0x0250` 만 (297,689번) | Switch on disabled. bit 4(주 전원 인가)와 bit 9(원격)가 켜져 있다. **Operation Enabled(`sw & 0x6F == 0x27`)는 0번**, Ready to switch on 이상의 상태도 0번 — CSV 를 따로 읽어 다시 셌다 |
| 0x603F Error code | `0x0000` 만 | 알람 없음 |
| 0x6061 Modes of operation display | 0 만 | 운전 모드가 선택되지 않았다 (출력의 Mode 0 과 같다) |
| 0x60FD Digital inputs | `0x41020000` 만 | bit 0(음의 리미트 NOT) · bit 1(양의 리미트 POT) · bit 2(원점 HOME)는 모두 0. 제조사 영역의 bit 17 · 24 · 30 이 켜져 있고, 그 뜻은 `[확인 필요 — 매뉴얼의 0x60FD 비트 표]`. 10분 동안 한 번도 바뀌지 않았다 |
| 0x6064 Position actual | −3,978 ~ −3,961 pulse (폭 17 pulse, 약 17 µm) | 손으로 민 흔적은 없다(밀었다면 mm 단위로 바뀐다). 17:23 경 −3,972 근처에서 −3,965 근처로 몇 µm 옮겨 갔다 |
| 0x60F4 Following error | 0 만 | 서보가 꺼져 있어 추종 오차를 계산하지 않는 것으로 보인다 `[추정]` |

### 1.4 심박 파일 `data/motion.json`

시험 중 별도 프로세스가 이 파일을 0.25초마다 60초 동안 **읽기만** 했다(17:17:08 시작). 238번 읽어 실패 0, 새 심박 59개, 심박 사이 간격 1.014–1.028초, 읽은 순간의 심박 나이는 최대 1.014초였다. 1초마다 갱신된다는 것을 확인했다.

## 2. 슬레이브 · PDO 매핑 · SDO (scan 과 본 시험 시작 때 같은 값)

### 2.1 슬레이브

| 항목 | 값 | 기록(2026-10-21 시운전 §7)과 |
|---|---|---|
| 슬레이브 수 | 1 | 같다 |
| 이름 · Vendor · Product · Revision | MBDLN25BL · 0x066F · 0x60540006 · 0x00010000 | 같다 |
| PRE-OP · SAFE-OP 도달 | 둘 다 도달, AL 상태 코드 0x0000 | — |
| SAFE-OP 에서 WKC | 3 (기대값 3) | — |

### 2.2 PDO 매핑 대조

드라이브의 PDO 할당 객체(0x1C12 출력 · 0x1C13 입력)와 그것이 가리키는 매핑 객체를 SDO 로 읽어, 시운전 기록 §7 과 **항목·순서·비트 수까지** 대조했다. 일치하지 않으면 SAFE-OP 로 가기 전에 멈추게 되어 있다.

| 방향 | 실제로 읽은 매핑 (index:sub/bit) | 기록과 |
|---|---|---|
| 출력 9 byte | 0x6040:00/16 · 0x6060:00/8 · 0x607A:00/32 · 0x60B8:00/16 | 일치 |
| 입력 23 byte | 0x603F:00/16 · 0x6041:00/16 · 0x6061:00/8 · 0x6064:00/32 · 0x60B9:00/16 · 0x60BA:00/32 · 0x60F4:00/32 · 0x60FD:00/32 | 일치 |

### 2.3 SDO 로 읽은 객체 (전부 읽기, 쓰기는 0건)

값은 드라이브가 돌려준 그대로다. 단위는 매뉴얼로 확정하지 않았다 — `[확인 필요]` 는 그 뜻이다.

| 객체 | 이름 | 읽힘 | 값 | 해석 |
|---|---|---|---|---|
| 0x1018:04 | Identity — serial number | 예 | 620823063 = **0x25010217** | 16진으로 읽으면 명판 시리얼 **25010217** 과 같다. 체인 위치가 바뀌어도 모듈을 시리얼로 묶는 계획(plan-v2 2.3)이 이 값으로 된다 |
| 0x607D:01 | Software position limit — min | 예 | −2147483648 | INT32 최솟값 — 드라이브 쪽 소프트 리미트가 사실상 걸려 있지 않다 `[추정]` |
| 0x607D:02 | Software position limit — max | 예 | 2147483647 | INT32 최댓값 — 위와 같다 |
| 0x607F:00 | Max profile velocity | 예 | 838860800 (0x32000000) | 단위 `[확인 필요]`. 1 pulse = 1 µm 의 pulse/s 라면 약 839 m/s 라 실질적 상한이 아니다 `[추정]` |
| 0x6080:00 | Max motor speed | 예 | 6500 | 단위 `[확인 필요]` (mm/s 라면 6.5 m/s) |
| 0x605A:00 | Quick stop option code | 예 | 2 | CiA402 표준 뜻: Quick stop 감속 경사로 멈춘 뒤 Switch on disabled 로. plan-v1 2.5 의 제안값과 같다 |
| 0x6085:00 | Quick stop deceleration | 예 | 1000000 | 단위 `[확인 필요]` (pulse/s² 라면 1 m/s²) |
| 0x60C5:00 | Max acceleration | 예 | 4294967295 (0xFFFFFFFF) | 상한 없음으로 보인다 `[추정]` |
| 0x1C32:01 | SM2 sync mode | 예 | 0 | 0 = FreeRUN. **DC(분산 클럭 동기)가 꺼져 있다**는 증거 |
| 0x6064:00 | Position actual value | 예 | 따로 남기지 않았다 | 첫 출력 프레임의 Target 을 지금 위치로 채우는 데만 썼다. 그 뒤의 위치는 PDO 로 읽었다(1.3절) |

PDO 매핑 대조를 위해 0x1C12 · 0x1C13 · 0x1600 · 0x1A00 계열도 SDO 로 읽었다(2.2). 이 세션 동안 비상 메시지(EMCY)는 한 건도 오지 않았다.

## 4. Windows 타이머와 USB 랜카드 지연 — 무엇을 재고 무엇을 정했나

### 4.1 타이머 해상도

Windows 의 기본 타이머 틱은 15.6 ms 라서, 예전 방식의 `sleep` 이면 2 ms 주기를 지킬 수 없다. 그런데 Python 3.11 의 `time.sleep` 은 Windows 에서 **고해상도 대기 타이머**(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)를 쓰므로 그 틱에 묶이지 않는다. 코드를 쓰기 전에 장비 없이 이 PC 에서 2 ms 주기 2,500번(5초)을 재 보았다.

| 방식 | p99 | 최대 |
|---|---|---|
| 절대 마감 시각까지 `time.sleep` (채택) | 2.486 ms | 2.783 ms |
| 위 + `timeBeginPeriod(1)` | 2.459 ms | 2.795 ms |
| 위 + 마지막 0.5 ms 바쁜 대기(spin) | 2.192 ms | 2.450 ms |

차이가 작아서 가장 단순한 첫 줄을 택했다 — `timeBeginPeriod` 도, CPU 를 태우는 바쁜 대기도, 프로세스 우선순위 올리기도 쓰지 않았다. 대신 두 가지는 했다. 마감 시각을 절대 시각으로 잡아 늦은 주기가 다음 주기를 밀지 않게 했고(늦으면 몰아 보내지 않고 그 자리에서 다시 시작), 파일 쓰기는 주기 스레드가 아니라 다른 스레드가 0.1초마다 몰아서 하게 했다. 또 Python 의 GIL(한 번에 한 스레드만 파이썬 코드를 돌리게 하는 잠금)을 주기 스레드가 기다리는 시간을 줄이려고 전환 간격을 5 ms 에서 0.5 ms 로 줄였다(`sys.setswitchinterval(0.0005)`).

### 4.2 응답 대기를 2 ms 에서 20 ms 로 바꾼 이유

첫 30초 점검(17:12:02, 응답 대기 = SOEM 기본 2 ms)에서 WKC 오류가 4건 나왔다. 4건 모두 `wkc = -1`(NOFRAME)이었고, 그 주기의 간격은 2.92 · 3.01 · 3.32 · 4.72 ms 였다. 잃어버린 프레임인지 늦게 온 프레임인지를 가르려고, 같은 안전 조건(SAFE-OP · Controlword 0 · 매 주기 Statusword 검사)에서 응답 대기만 20 ms 로 늘린 일회성 진단을 1분 돌렸다(17:13 경, 코드는 저장소에 남기지 않았다).

| 진단 1분 (29,805주기, 응답 대기 20 ms) | 값 |
|---|---|
| WKC 오류 | **0** — 잃은 프레임이 없다 |
| 왕복 시간 최소 · 중앙값 · p99 · p99.9 · 최대 | 1.107 · 1.152 · 1.489 · 4.132 · 5.559 ms |
| 왕복 시간 2 ms 초과 · 3 ms 초과 · 5 ms 초과 | 177건(0.59 %) · 111건 · 3건 |

즉 이 USB 랜카드는 프레임을 잃지 않지만, 응답의 약 0.6 % 가 2 ms 넘게 늦게 온다. SOEM 기본 대기 2 ms 는 그 늦은 응답을 "응답 없음"으로 세고 있었다. 그래서 응답 대기를 plan-v1 1.4 가 정한 "주기 스레드의 허용 최대 지연" **20 ms** 로 맞췄다(`ecat.RECV_US`). 이 정의에서 WKC 오류는 "20 ms 안에 응답이 안 왔다"는 뜻이 되고, 늦은 응답은 WKC 오류가 아니라 주기 통계(늦은 주기 수 · p99.9 · 최대)에 그대로 드러난다. 이 정의를 ① 의 판정에 쓸지는 아래 '결정 필요'에 올렸다.

## 결정 필요

1. **① 의 WKC 오류를 어느 정의로 판정할지.** 응답 대기 20 ms(plan-v1 1.4 의 허용 최대 지연)로는 본 시험 10분 동안 0건이다. SOEM 기본 2 ms 로 쟀다면 이 USB 랜카드에서는 늦은 응답 때문에 30초에 4건이 나왔다(잃은 프레임은 0 — 4.2절). 이 기록은 20 ms 정의로 ① 을 판정했다. 2 ms 정의를 쓰면 30초 만에 4건이 나왔으므로 ① 은 불통과이고, 그때의 처방은 소프트웨어가 아니라 랜카드 쪽(USB 랜카드의 인터럽트 조절 설정, 또는 PCIe 랜카드)에서 찾아야 한다 `[추정]`.
2. **M1 → M2 관문** — plan-v2 결정 3 그대로다. 아래 '남은 것'의 사람 몫(부호 s · 센서 대응 · 24시간 공존)과 이 기록을 보고 방향 부호 · 소프트 리미트 · 상한을 승인해야 M2 로 간다.

## 남은 것 (요청 범위 안)

- **사람이 할 것(미실시/사용자):** ③ 부호 s — `monitor` 를 켠 채 축을 한쪽으로 손으로 밀고 `motion.json` 의 `now.pos` 가 커지는지 작아지는지 본다. ④ 0x60FD 비트와 옵티컬 센서 대응 — 스테이지를 home/end 센서에 대 보며 비트가 바뀌는지 본다(배선돼 있다면). ⑧ 의 뒷부분 — cell-bench 감시자와 같은 PC 에서 24시간 공존.
- **매뉴얼로 확정할 것:** 2.3 표의 단위 `[확인 필요]`, 0x60FD 의 제조사 비트(16~31번) 뜻.
- **의존성 표기:** pysoem 은 작업 트리 venv 에만 설치돼 있고 `cell-bench/requirements.txt` 에는 아직 없다(기존 파일을 고치지 않는다는 지시에 따름). 다른 PC 로 옮길 때 함께 적어야 한다.
- **배선:** 감시자의 모터 차선 · 결과판 `/api/motion` · `bench.json` 의 `motor` 줄은 M3 변경 목록(plan-v2 6.1) 몫이다. 지금 `motion.json` 을 읽는 프로그램은 없다.

## 참고 — 함께 발견한 것 (요청 밖, 지시가 없으면 착수하지 않는다)

- **드라이브 쪽 소프트 리미트(0x607D)가 INT32 전 범위다.** plan-v1 2.1 의 "겹 2(드라이브 소프트 리미트)"가 지금은 비어 있다는 뜻이다. plan-v1 2.3 은 M2 전에 이 값을 SDO 로 쓰자고 했는데, 그것은 SDO **쓰기**라 사용자 승인이 필요한 별도 단계다. 최대 가속(0x60C5)도 상한이 없는 값으로 읽혔다.
- **위치가 −3,972 ~ −3,973 pulse(약 −3.97 mm)다.** 위치 0 은 드라이브 전원을 넣은 자리이므로(시운전 §2), 전원 투입 뒤 스테이지가 약 4 mm 움직였거나 Home 끝이 아닌 곳에서 전원이 들어갔다는 뜻이다. 원점 신뢰 판정(plan-v1 2.2 의 `|pos| > 2 mm` 이면 "원점 신뢰 불가")에 걸리는 값이다.
