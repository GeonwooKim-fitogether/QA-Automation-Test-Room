# 마이그레이션 파일명 규칙 — 번호를 버리고 시각으로 짓는다

> 한 줄 요지: **새로 만드는 마이그레이션 파일의 이름은 `YYYYMMDDHHMMSS_이름.sql`이다.** 예: `20260806131500_item_lifecycle_index.sql` — 파일을 만든 UTC 시각 열네 자리를 앞에 붙인다. `0090_...`처럼 순번을 매기는 방식은 더 쓰지 않는다.

여기서 마이그레이션(migration)은 데이터베이스의 구조를 바꾸는 SQL 스크립트를 말하며 보통 `supabase/migrations/`에 쌓인다. 순번 방식을 버린 이유는 병렬 세션들이 같은 번호를 집어도 **git이 충돌로 잡지 못하기** 때문이다 — 이름이 다른 별개 파일이라 두 PR 모두 초록불로 머지되고, 겹친 번호는 적용 이력 대조까지 오염시킨다. 실제 사고 기록과 "왜 시각인가"의 상세 논증은 [부록](./reference/migration-naming-history.md)에 있다.

## 규칙

1. **이름은 `YYYYMMDDHHMMSS_이름.sql`.** 앞 열네 자리는 파일을 만드는 시점의 UTC 시각(연4·월2·일2·시2·분2·초2), 그 뒤에 밑줄 하나와 영문 소문자·밑줄 이름. 열네 자리는 손으로 세지 말고 명령으로 얻는다.

   ```bash
   date -u +%Y%m%d%H%M%S    # 예: 20260806131500
   ```

2. **기존 번호 파일(`0001`~`0089`)은 개번하지 않는다.** 라이브 적용 이력에는 옛 이름이 적혀 있어 개번하면 "이 파일이 적용됐는가"의 이름 대조가 불가능해지고, 그 번호를 가리키는 문서·코드 참조가 함께 깨진다. 두 형식이 한 폴더에 섞여 있는 것이 의도된 상태다 — 사전순 정렬에서 번호(`0` 시작)는 항상 시각(`2` 시작)보다 앞에 오므로 정렬 순서가 그대로 적용 순서다.

3. **적용할 때 넘기는 이름 규칙은 그대로다.** `apply_migration`에 넘기는 `name`은 파일 이름에서 `.sql`만 뗀 것과 글자 하나까지 같아야 한다 — 저장소의 파일 목록과 라이브의 적용 이력이라는 두 장부를 일치시키는 장치다. 예: `20260806131500_item_lifecycle_index.sql` → `20260806131500_item_lifecycle_index`. 시각을 빼거나 뒤로 옮기는 것은 규칙 위반이다.

4. **도입할 때 저장소마다 한 가지를 확인한다.** 그 저장소에 "파일 이름이 네 자리 번호로 시작하는지" 검사하는 자동 장치가 있으면, 첫 시각 형식 파일을 만들기 전에 그 검사가 두 형식을 모두 받아들이도록 고친다. 자동 검사는 `.github/workflows/`에 있고 그 폴더는 동기화 봇이 내려보내지 않으므로, 이 확인은 저장소마다 사람이 한 번 한다.

## 적용 범위

- 데이터베이스 마이그레이션 파일을 두는 저장소에 적용된다.
- 단일 원본은 창고(Template-repository)의 `.claude/rules/migration-naming.md`다. 여기서만 고치고, 동기화 봇이 내려보낸다.
- 저장소별 마이그레이션 **적용 절차** 문서가 따로 있으면, 절차는 그 문서가, 파일명 형식은 이 규칙이 정본이다.
