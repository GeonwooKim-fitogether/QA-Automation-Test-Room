# cell-bench — 셀 내구 시험대 무인 충방전 제어

> 한 줄 요지: **셀 24대를 켜 둔 채, 스마트 플러그 하나로 Dock 충전을 켜고 끄며 "방전 → 추출 → 충전" 사이클을 사람 없이 반복하고, 사이클마다 작동시간·충전 전력량을 CSV 로 남긴다.** 셀 펌웨어는 손대지 않는다.

```
방전(플러그 OFF) ─▶ 기준선 30% ─▶ 플러그 ON ─▶ 추출(충전 중, 6대씩) ─▶ 만충 판정 ─▶ 플러그 OFF ─▶ (반복)
```

## 구성

|---|---|

## 준비 (한 번)

> 구조를 처음 볼 때는 [시스템 지도](docs/system-map.md) 부터 — 한 장 요약에서 흐름 순서까지 흐름도로 내려간다.
> 새 노트북으로 옮길 때는 [제어 PC 준비 · 이식](docs/control-pc-setup.md) 을 따르고 `python tools/check_env.py` 로 확인한다.
> 휴대폰에서 보고 제어하려면 [원격 모니터링 · 제어](docs/remote-access.md).
> 다른 PC 나 새 Claude 세션에서 이어 받을 때는 [인수인계](docs/handover.md) 를 먼저 읽는다 — 코드에 없는 결정·실측·사고가 거기 있다.

1. PC Wi-Fi 를 LiveHub `FTG-3D93-5G` 에 고정 주소 `192.168.1.100` 으로 붙인다(셀은 이 주소로만 라이브를 보낸다). 인터넷은 이더넷으로.
2. `pip install -r requirements.txt`
3. 플러그는 Tapo 앱에서 LiveHub 2.4 GHz 에 등록하고 **나 → Tapo Lab → Third-Party Compatibility** 를 켠다.
4. `python tools/plug_cli.py setup` — 입력 창에 TP-Link 계정을 넣는다. 값은 자격 증명 관리자에만 저장된다.

## 실행

```bash
cd cell-bench
python -m pytest -q                      # 장비 없이 판정 로직 검사
python tools/battery_table.py            # 셀 24대 배터리 표 (10초, 셀 안 건드림)
python tools/plug_cli.py status          # 플러그 상태·전력
python run_cycle.py --dry-run            # 플러그·셀 안 건드리고 흐름만
python run_cycle.py                      # 무인 실행 — 시험 목표(target_cycles 500)에 닿을 때까지 사이클을 이어 간다 (아래 '안전망' 의 '놀지 않기')
python serve_board.py                    # 결과판 → 브라우저로 http://127.0.0.1:8765
```

## 감시자 (엔진 밖에서 되살리기)

시험 프로그램이 사라지거나(업데이트 재시작·정전·예외·창 닫힘) 멈추면(행) 아무도 모르던 것을 막는다. 작업 스케줄러 작업
**"CellBench Supervisor"** 가 로그온 때 `pythonw supervise.py` 를 창 없이 띄우고, 감시자는 1분마다 시험망 · 결과판 서버 · 엔진을 점검한다.
엔진이 이유 없이 사라졌거나 심박(`now.json` 의 `beat`)이 5분(추출 중 20분) 넘게 두 번 연속 멈춰 있으면, **플러그를 먼저 켜고**
남은 사이클 수로 `run_cycle.py --precharge` 를 처음과 같은 인자(`--config` 등)로 다시 띄운다. 1시간에 3번을 넘기면 멈추고 Slack 으로 사람을 부른다.

- **등록(한 번):** `powershell -ExecutionPolicy Bypass -File tools\install_supervisor.ps1` — 관리자 권한 필요 없음. 옛 임시 감시자(`cell-bench watchdog`)가 있으면 사용 안 함으로 바꾸고 그 프로세스를 끝낸다. 되돌리기는 `-Uninstall`.
- **보는 법:** `data/supervisor.json` 의 `t` 가 1분마다 바뀌고 `checks`(시험망·결과판·엔진·심박)가 보인다. 조치와 상태 변화는 `data/supervisor.log` 에 한 줄씩.
- **되살리지 않는 것:** 다 돈 엔진, 결과판의 '안전 정지', Ctrl+C, 설정 오류(플러그는 켜고 사람을 부른다), 연속 실패로 스스로 멈춘 엔진.
- **엔진이 돌지 않는 동안 플러그 지키기:** 위처럼 엔진이 멈춰 있거나 기록이 없으면 감시자가 10분마다 플러그를 읽어, 꺼짐이면 켜고 켜짐인데 10 W 미만이 1분 이어지면 30초 끊었다 켠다(1시간 3번까지 — 그 뒤로는 빨강). 결과는 `data/supervisor.json` 의 `plug_guard`. **사람이 일부러 플러그를 꺼 두는 수동 작업 때는 `data/supervisor_pause` 를 먼저 둔다** — 표지가 있으면 지키지 않는다.
- **일부러 멈출 때:** 감시자가 띄운 엔진은 창이 없다. 결과판의 '안전 정지'를 쓴다. 작업 관리자에서 끝내면 감시자는 비정상 종료로 보고 되살린다.
- **코드 교체·이관 동안:** `data/supervisor_pause` 파일을 두면 감시자는 점검만 하고 조치하지 않는다(빨강·미확인 알림은 그래도 보낸다). 내용은 `{"reason": "이관", "until": <epoch 초>}` — until 이 지나면 무시하고, until 이 없으면 파일을 쓴 뒤 2시간(`supervisor_pause_max_h`)이 지나면 무시한다. `tools/restart_at_boundary.ps1` 은 교체하는 동안 이 표지를 스스로 둔다.
- **설정:** 감시자는 엔진과 같은 순서(기본값 ← `bench.json` ← 엔진의 `--config`)로 설정을 읽는다. 감시자 쪽 플러그 MAC · data 폴더가 엔진과 다르면 `supervisor.log` 에 경고를 남긴다.

`data/supervisor.json` 의 `plug_guard` (화면이 읽는다):

| 키 | 뜻 |
|---|---|
| `active` | 엔진이 돌지 않아 감시자가 플러그를 지키는 중인가 (false 면 `why` 에 이유 — 엔진이 돈다 · 일시 중지 · 옛 감시자) |
| `since` · `checked_t` · `next_t` | 지키기 시작한 시각 · 마지막으로 읽은 시각 · 다음에 읽을 시각 (epoch 초) |
| `on` · `watts` | 마지막으로 읽은 켜짐 여부와 전력(W) |
| `action` · `action_t` | 마지막 판정(`ok` · `low_seen` · `plug_on` · `recharge` · `capped` · `plug_on_failed` · `read_failed` · `no_read`)과 마지막으로 켜거나 끊었다 켠 시각 |
| `recharges_1h` · `fail` · `error` | 지난 1시간 끊었다 켠 횟수 · 연달아 켜지 못한 횟수 · 읽기 실패 이유 |

`data/supervisor.json` 의 `config_warning` 은 감시자와 엔진의 설정이 다를 때 그 한 줄(없으면 null)이다.
- **주의:** 로그온해야 감시자가 뜬다. 재부팅 뒤 자동 로그온이 켜져 있어야 사람 없이 복귀한다(`tools/check_env.py` 로 확인).

## 안전망 (엔진이 스스로 잡는 고장 — FMEA P4)

엔진(`run_cycle.py`)이 표본(20초)마다 아래를 보고, 판정은 `cellbench/guards.py` 의 순수 함수가 한다. 원칙은 **모를 때는 충전 쪽**이다 —
플러그를 켜는 조치는 자동이고, 전원을 끊는 자동 조치는 "방전 중에 누가 켠 플러그를 원래대로 끄는 것" 하나뿐이다(그것도 최저 배터리가 기준선 + 10%p 보다 높을 때만).

| 무엇을 잡나 | 엔진이 하는 일 | 남기는 이상 (불) |
|---|---|---|
| 셀 저장이 가득 참(≈160 MB, 10-10 실측) | 추출 뒤 삭제 — 끝 표지 · 오류 블록 0 · 받은 바이트 ≥ 크기일 때만. 저장량은 추출 때의 크기에서 3.45 MB/h 로 추정. 12시간(`cell_storage_known_max_h`) 넘은 기록과 삭제를 켜기 전 기록은 '모름'으로 빼고 빨강·Slack 을 내지 않는다(엔진 밖에서 지웠을 수 있다) | `extract`(노랑, 못 지움) · `cell_storage`(노랑, 80%) · `cell_storage_critical`(빨강, 95%) · `cell_storage_full`(빨강, 라이브 끊김 + 95%) |
| 플러그가 켜졌는데 Dock 이 안 끌어 씀(10 W 미만 또는 꺼짐 1분) | 예비 충전·플러그 켜기·충전·복구 대기에서 30초 끊었다 켬, 단계마다 3번까지. 켜지 못한 시도는 세지 않고, 3번을 다 쓴 뒤에도 꺼짐은 켠다. 끝낼 때도 30초 끊었다 켜고 1분 뒤 다시 읽어 확인한다 | `plug`(노랑, 시도마다) · `dock_power`(빨강, 3번 다 실패) |
| 방전 중 누가 플러그를 켬 | 다시 끔. 최저 배터리가 기준선 + 10%p 이하이면 그대로 충전으로 넘김 | `manual_plug`(노랑) |
| 삭제 명령이 주소만 보고 다른 셀로 감(10-10 수동 작업, FMEA 6.8) | 깨우기 전 · 접속을 받을 때 · 삭제(0x13) 직전에 라이브의 주소↔시리얼을 확인. 어긋나면 깨우지·받지·지우지 않음(받은 파일은 `_unverified`). 한 추출의 걸린 셀은 한 줄로 묶는다 | `identity`(빨강, 주소 충돌) · `identity_stale`(노랑, 라이브가 끊겨 확인할 수 없음 — 대기·저장 가득 참 셀) |
| 충전 중 혼자 안 오르는 셀(접촉 불량) | 알림만 (다른 셀 중앙값 +10%p 인데 +2%p 미만 · 95% 미만) | `cell_not_charging`(노랑) |
| 방전 중 대기 모드 셀(0x16 만 옴, 60초) | 그 셀만 깨워 0x26 복귀, 셀당 10분에 한 번 | `cell_waiting`(노랑) |
| data 드라이브 여유 부족 (10분마다) | 알림만 | `disk`(노랑, 20 GB 미만) · `disk_critical`(빨강, 5 GB 미만) |
| 설정 오류 · 다른 PC 가 192.168.1.100 사용 중 | 시작 거부 (`engine.json` exit=`config_error`) — 감시자가 플러그를 켜고 사람을 부른다 | — |
| Ctrl+C 로 멈췄는데 플러그가 꺼져 있음 | 알림만 (플러그는 그대로 — 일시 중지 표지가 없으면 감시자가 10분 안에 켠다) | `interrupted_plug_off`(노랑) |
| 이번 실행의 `--cycles` 를 다 돌고 멈춤(10-11, 4시간 21분 공회전) | 멈추지 않는다 — 누적이 시험 목표 `target_cycles`(500)에 닿을 때까지 다음 사이클을 이어 간다. 누적 100사이클(`progress_notify_every`)마다 진척을 알린다 | `target_reached`(노랑, 기록만) · `progress`(노랑, Slack 1건 "목표 500 중 100사이클 완료 · 누적 방전 평균 Nh") |
| 예비 충전에서 Dock 이 재충전하지 않음(10-11, 셀 96~97% · 27.7 W 평탄으로 2시간 39분) | 시작 때 모든 셀 ≥ 95%(`precharge_skip_pct`)면 건너뛴다. 전력이 바닥(≤ 35 W `floor_w_max`)에서 10분 평탄하면 — 모든 셀 ≥ 95% 는 만충으로 치고, 미만이면 30초 끊었다 켠 뒤(1회) 그래도 같으면 사이클로 넘어간다. 정규 충전의 만충(모든 셀 100%)은 그대로 | `dock_no_recharge`(노랑) |
| 한 단계에 너무 오래 머묾(10-11, 9차선 전부 '정상') | 알림만 — 신호등 '프로그램' 차선이 단계 기대 시간(PRECHARGE 1h + 시작 잔량에 비례 · PLUG_ON 0.1h · EXTRACT 0.5h · CHARGE 는 `charge_timeout_h` 4h · DISCHARGE 5h · RECOVER 0.5h)의 1.5배에 노랑, 3배(예비 충전은 4배)에 빨강. 감시자가 Slack 으로 보낸다 | (이상 기록 없음 — 신호등 차선) |

**놀지 않기 — 시험 목표 500사이클(약 4개월).** 시험 전체 목표는 `Config.target_cycles`(500, `bench.json` 으로 덮어쓴다)이고, 엔진은 `cycles.csv` 의 누적이 거기 닿을 때까지 사이클을 이어 간다.
`--cycles N` 은 '이번 실행에서 최소 N'(하위 호환)일 뿐이다. 목표에 닿으면 그때만 `exit=done`(플러그 ON) 으로 끝나며, 그 밖에 멈추는 길은 결과판 '안전 정지'(`stop_safe`) · Ctrl+C · 연속 실패(`failsafe`)뿐이다.
감시자도 같은 값을 본다 — `engine.json` 이 `done` 인데 누적 < 목표면(옛 코드 엔진) 끝남이 아니라 되살릴 일로 보고, 남은 사이클 = 목표 − 누적으로 다시 띄운다. `auto_continue=false` 로 두면 예전처럼 `--cycles` 만 돌고 끝난다.
결과판·신호등의 '프로그램' 차선 값에 "누적 N / 목표 500" 이 보인다(`now.json` `metrics.cycles_done` · `target_cycles`).

이상 종류별 색은 `cellbench/record.py` 의 `EVENT_LIGHT`, 알림(Slack)으로도 보내는 종류는 `ALERT_KINDS` 가 정본이다.

**신호등 지표 — `data/now.json` 의 `metrics` (다음 단계와의 계약).** now.json 을 쓸 때마다(표본 20초마다 · 단계가 바뀔 때) 함께 갱신된다.

## 신호등 (조기 경보 — 10개 차선)

위 지표와 감시자가 직접 본 것, 운영체제 정보를 **10개 차선의 불**로 판정한다. 결과판 점검 탭에 "시험대 띠 한 줄 → 차선 10개"로 보이고,
같은 판정으로 Slack 알림(감시자)과 클라우드 결과판이 움직인다. 띠 한 줄만 읽어도 지금 무엇을 준비해야 하는지 나오게 했다.

| 정상 | 지표가 모두 기대 범위 안 | 보내지 않는다 |
| 준비 | 추세·여유·횟수가 문턱을 넘음. 아직 잃은 것은 없다 — AI 가 미리 조치하고 사람은 준비 | 새로 켜질 때 1건 (같은 이유는 1시간에 한 번) |

**어디서 계산하나.** 판정은 `cellbench/health.py` 의 순수 함수 `compute(now, sup, osinfo, cycles, cfg, now_t, plugs, engine, busy)` 하나다
(`engine` = data/engine.json — 감시자가 없어도 엔진이 끝난 이유를 본다, `busy` = 운전 중인 엔진이 쥔 셀·플러그 — 미등록 감지에서 뺀다).

- 감시자가 1분마다 계산해 `data/health.json` 에 쓰고, 차선 키 그대로 알림기(Slack)에 넘기고, 클라우드 `bench_health` 에 한 줄을 덮어쓴다.
  운영체제 정보는 감시자가 10분마다 읽기만 해서 `data/osinfo.json` 에 둔다(`cellbench/osinfo.py` — 판정은 `tools/check_env.py` 와 같은 함수).
- 결과판 서버(`GET /api/health`)는 요청마다 파일에서 새로 계산한다 — 감시자가 없어도 화면은 판정된다(그때 '프로그램' 차선에 "감시자 없음"이 준비로 보인다).
- 클라우드 결과판은 `bench_health` 를 읽고, `updated_at` 이 5분 넘게 묵으면 화면이 스스로 전체를 미확인으로 그린다(PC 가 죽어도 불이 켜진다).
- 엔진 기록이 멈추면 엔진만 아는 차선(Dock·셀 · 셀 수신 · 심박 · 사람 조작)은 미확인이 되지만 알림은 '프로그램' 차선 하나로만 간다 — 같은 원인으로 알림이 쏟아지지 않게.
  감시자가 그 일을 맡고 있지 않으면(판정이 없거나 '정상') '프로그램' 차선이 미확인으로 올라가 거기에 '확인' 단추가 선다. 감시자가 되살리는 중(노랑)이면
  그 사건은 노랑 1건이 설계라 올리지 않는다(되살릴 때마다 '미확인'+'복구' 2건과 15분 반복이 생기지 않게).

**문턱 바꾸는 곳.** 새 문턱은 `cellbench/config.py` 의 `HEALTH` 한 곳이다(심박 문턱 · 자동 재연결은 같은 파일의 `HR` — `bench.json` 의 `health` 로 함께 덮는다). `bench.json` 에 `"health": {"wifi_warn_dbm": -75}` 처럼 일부만 줘도 나머지는 기본값이다.
이미 있던 문턱(심박 `heartbeat_*` · 라이브 끊김 `live_gap_alarm_s` · 충전 한도 `charge_timeout_h` · 셀 저장량 `cell_storage_*_pct` · 디스크 `disk_*_gb`)은 그 값을 그대로 쓴다.
릴레이 수명 30,000회는 **가안**이다 — P110M 자료에 수명이 없어(2026-10-10 확인) 보수적으로 두었다.

**'확인' 단추.** 제어 PC 결과판의 조치·미확인 차선에 있고, 옆에 "Slack 반복만 멈춤"이라고 적혀 있다. 누르면 그 차선의 Slack 반복(15분마다)만 멈춘다(`POST /api/alert/ack {key, reason}` → `data/alert_ack.json`). 장비를 움직이지 않으므로 PIN 을 받지 않고, 키는 10개 차선 키만 받는다.
**확인은 그 원인에 묶인다.** 서버가 확인 시각과 함께 화면이 보던 이유를 적고(`{키: 시각, "_reason": {키: {reason, light}}}` — 알림기가 읽는 `키: 시각` 꼴은 그대로), 신호등은 지금 이유·불이 다르면 확인을 치지 않는다. 그래서 감시자가 없어도 새 원인이면 '다시 확인'(원인이 바뀜)이 선다. 감시자가 있으면 알림기의 사건 시작 시각(`since`)도 함께 본다.

**알림 키.** 신호등 이전의 감시자 키 넷은 차선으로 접혔다 — `engine`·`board` → `program`, `plug_on` → `plug`, `net` → `wireless`. 옛 `alert_state.json` 에 남은 옛 키는 감시자의 첫 점검에서 조용히 지운다.

## 심박 (블루투스 — 짝 표 · 보드 읽기 · 끊긴 셀 · 자동 재연결)

**결론: 세트 줄에 짝 표를 넣으면, 감시자가 보드를 읽고 신호등이 끊긴 셀과 원인을 가르며, 엔진이 '셀이 안 붙음'인 셀에 이름을 스스로 다시 보낸다.**
짝 표가 없는 세트에는 아무 일도 일어나지 않는다(결과판에 '심박 없음' 회색 — 오류가 아니다).

셀은 0x20 으로 받은 이름의 심박대에 블루투스로 붙는다. 심박대 대신 ESP32-C3 보드([firmware/hr-sim](firmware/hr-sim/README.md))가 `HRSIM-xxxx` 로 광고하고,
전원 USB 허브 둘(A 16 · B 8)에 꽂혀 제어 PC 의 USB 로 5초마다 `HRSIM name=… bpm=… conns=…` 를 낸다.

1. **짝 표** — `bench.json` 세트 줄의 `hr_pairs` (`{"셀": {"board": "HRSIM-4CF0", "no": 1, "hub": "A", "port": 1}}`). 허브 · 포트는 사람이 꽂은 대로 적는다 —
   USB 위치로 앞면 포트 번호를 추정하지 않는다(허브 안 4포트 칩 배치가 허브마다 달라 틀린 번호가 나왔다, 10-15 실측). 형식과 중복은 `validate` 가 본다.
   운전 중에는 손으로 고치지 말고 `python -X utf8 tools/hr_pair.py --import-csv 짝.csv --write` 로 넣는다(다시 읽어 검사 → 임시 파일 → 바꿔치기).
   허브 이름은 **그 세트 안의 이름**이다 — 세트 1 의 `A` 와 세트 2 의 `A` 는 다른 허브이고(결과판 키 `1A` · `2A`), 포트 중복도 세트 안에서만 본다.
   지금의 짝 표(`A` · `B`)는 고칠 것 없이 세트 1 의 허브로 읽힌다. 보드를 USB 충전기 · 전원 허브에만 꽂아 제어 PC 와 USB 데이터 연결이 없으면
   `hub` 를 **P 로 시작**하게 적는다(`"P3"`) — **전원만** 보드다. 감시자가 읽지 않고, 판정은 셀 심박만 본다(원인 '보드 상태 안 읽음'). 한 세트에 감시 허브와 P 허브를 섞어도 된다.
2. **보드 읽기** — 감시자(`supervise.py`) 안의 스레드(`hr.BoardWatch`)가 45초마다 짝 표의 보드만 포트를 최대 6초 열어 상태 줄 하나를 받고 닫는다.
   여는 순간 DTR · RTS 를 올리지 않는다(이 두 선이 칩을 리셋해 셀과의 연결을 끊는다). 결과는 `data/hr_boards.json` 에 원자적으로 쓴다.
   같은 바퀴에 제어 PC 의 USB 장치 수(허브 칩 · 보드 · 그 밖의 장치, 루트 허브와 인터페이스 조각 제외)를 Windows SetupAPI 한 번(실측 11 ms)으로 세어
   `usb_devices` 로 함께 적는다 — 결과판 제어 PC 의 USB 막대(규격 한도 127 · 흔한 한도 64 눈금). 이 PC 의 실측 한도를 알면 `bench.json` 의
   `"health": {"usb_limit": 64}` 로 주고, 그러면 눈금과 판정이 그 값을 쓴다(기본 없음). 못 세면 막대가 '모름'(회색)이다.
   엔진이 아니라 감시자에 둔 까닭: 포트 읽기가 엔진의 20초 표본을 늦추지 않고, 엔진이 멈춰도 '보드가 꺼졌나'를 본다.
3. **판정** — 신호등 '심박' 차선(위 표). 끊긴 셀의 원인은 짝 보드 상태로 가른다: 보드가 USB 에 없거나 오래 안 보임 → **보드 꺼짐(전원·케이블·허브 포트)** /
   켜짐 · 연결 0 → **셀이 안 붙음** / 연결 1 이상 → **다른 기기 연결 또는 셀 쪽 문제** / USB 는 있는데 응답 없음 → 보드 멈춤 · 포트 점유.
4. **자동 재연결** — 엔진이 표본마다(`cycle._watch_hr`) 짝 셀의 심박 0 이 10분 넘게 이어지고 짝 보드가 켜짐 · 연결 0 이며, 단계가 추출이 아니고
   다른 세트가 추출 문을 잡고 있지 않을 때만 그 셀에 0x20(짝 보드 이름) → 응답 확인 → 0x26 을 보낸다(`CellLink.set_ble_id` — 추출과 같은 신원 확인).
   같은 셀은 30분에 한 번, 시도마다 이상 `hr_repair`. 3번 보내도 돌아오지 않으면 그 셀에는 더 보내지 않고 멈춘다 — `hr_repair_fail` 한 번 + '심박' 노랑(자동 재연결 멈춤 — 사람 확인 필요, `tools/hr_pair.py --go --serials …` 로 수동 전송). 그 셀이 다시 심박을 받으면 멈춤이 풀린다. 셀이 재부팅하므로 시도마다 `live_gap` 1건(16~25초)이 정상이다.
   끄려면 `bench.json` 에 `"health": {"hr_repair": false}`.
5. **기록** — 사이클마다 방전이 끝날 때 `data/hr_####.csv`(셀별 방전 구간 표본 · 라이브 들린 표본 · 심박 > 0 표본 · 비율). `cycles.csv` 에 열을 더하지 않은
   까닭은 그 파일이 사이클 한 줄이라 셀 24대 값이 들어갈 자리가 없고, 머리줄이 처음에만 쓰여 이미 쌓인 파일에 열을 더하면 옛 줄과 칸이 어긋나기 때문이다.

결과판: 관제의 세트 카드 '심박 n/24', 시험실 구성(위 띠 = 제어 PC ─유선 인터넷─ 클라우드 · 그 아래 LiveHub, 아래 = 세트마다 한 줄 [세트] ┄블루투스┄ [보드 묶음].
왼쪽 줄기 = LiveHub 2.4 GHz, 오른쪽 줄기 = USB 데이터. 연결된 선은 줄기부터 가지까지 같은 색이고 가지 하나만 문제면 그 가지만 노랑 · 빨강.
보드 묶음은 감시 허브 칩 · 전원만 칩(USB 가지 없음) · 짝 표 없음 문구, 빈 세트는 '+ 세트 n' 칩 한 줄. 노드를 누르면 상세),
세트 상세의 셀 카드 '끊김' 표시와 셀 상세(짝 보드 · 허브 포트 · 보드 연결 · 원인). 클라우드 결과판도 같은 그림이다(`bench_health` 본문의 `hr` — 스키마 변경 없음).

## 세트 등록 (플러그 1 + 셀 24 를 한 세트로 묶는다)

새 Dock 을 시험대에 붙이면, 결과판이 그 장비를 **미등록 감지**로 보여 주고, 사람이 플러그 하나와 셀 24대를 골라 세트로 등록한다.
짝을 잘못 묶으면 그 세트를 끄려다 다른 세트의 전원을 끊으므로(FMEA 8.5), 저장하기 전에 프로그램이 **10초 검사**를 한다.
등록 결과는 `bench.json` 의 `sets` 끝에 한 줄로 붙는다(`config.add_set` — 다른 키는 그대로 두고, 임시 파일에 쓴 뒤 바꿔치기한다).

**등록만으로는 운전하지 않는다.** 등록한 세트는 결과판에 "세트 k · 운전 대기"(회색)로 보이고, 짝 검증 · 보정 · 클라우드 마이그레이션 관문을 모두
지나고 사람이 운전을 켜야 돈다 — 아래 '다중 세트 운전' 절. 새 세트는 언제나 목록 뒤에 붙으므로 운전 중인 세트 1 은 바뀌지 않는다.

**보는 법**

- **어디서:** 결과판(제어 PC) 첫 화면 → 관제 탭 → 머리글의 노란 칩 "미등록 감지 · 셀 n · 플러그 m", 또는 시험실 맵·세트 카드의 "세트 k · 미등록 감지 · 등록 →"
- **무엇을 하면:** 1 플러그를 고르고 → 2 시리얼 범위(예: 11594 ~ 11617)를 넣어 '범위 선택'(셀 카드를 하나씩 체크해도 된다) → 3 PIN 을 넣고 '저장 · 10초 검사'
- **무엇이 보이나:** 같은 자리에 검사 결과 네 줄. 통과면 "등록 완료 · 세트 k" 와 '세트 k 보기'(맵에서 세트 k 가 '대기'로 바뀐다). 저장됐어도 ④ 가 주의(꺼짐·전력 범위 밖)면 초록이 아니라 주의색 "등록됨 · 주의 1" 이고, 그 줄 아래에 사람이 실물로 확인할 일이 붙는다. 실패면 "등록 실패 · 저장 안 됨" 과 실패 이유 — 고른 것은 그대로 남고 '다시 검사' 할 수 있다
- **되돌리기:** 시험실의 세트 카드 "세트 k · 대기 — 짝 보기 · 등록 해제 →" 를 누르면 짝(플러그 별명·MAC · 셀 · 등록 시각 KST · 등록자)이 보이고, PIN 을 넣어 **등록 해제** 할 수 있다(확인 한 번 더). 브라우저 '뒤로'는 등록 화면에서 시험실로 돌아온다(주소의 `#register`)

**짝을 잘못 묶으면 되돌리는 길.** 등록 화면 맨 위에 "짝을 잘못 묶으면 다중 세트 운전 때 다른 세트의 전원을 끊는다 — 플러그 별명·케이블을 따라가 실물로 확인"이 늘 보인다.
등록 검사는 짝이 맞는지를 장비로 확인하지 못한다 — 그것은 **짝 검증**(아래 '다중 세트 운전' 절)과, 운전 중 모든 단계의 **방향 대조**가 한다.
등록 단계의 안전망은 사람의 실물 확인 · 주의 표시 · 등록 해제다. 운전이 켜졌거나 엔진이 쥔 세트(운전 · 짝 검증 중)는 해제할 수 없다. 등록 해제는 `POST /api/register/remove {pin, set_id}` (`register.remove_set`) — 첫 세트(운전 중)는 거부하고,
bench.json 에서 그 한 줄만 지운다(다른 키·세트는 그대로, 엔진과 같은 방법으로 다시 읽어 검사한 뒤 임시 파일에서 바꿔치기).

**운전 중인 엔진이 쥔 것은 고를 수 없다 (F13).** 엔진은 bench.json 위에 다른 설정 파일(engine.json 의 `args.config` — 예: `run_config.json` 의 22대)을 덮어 돌 수 있다.
그래서 bench.json 만 보지 않고, now.json 의 `cells`(엔진이 지금 도는 시리얼)와 그 설정 파일의 `serials` · `plug_mac` 도 "운전 중 · 세트 1"로 막는다(`register.engine_claims`).
화면의 셀 목록·범위 선택에서 빠지고, 플러그 표에서는 그 줄 첫 칸에 막힌 이유가 보이며, 서버의 검사 ③ 도 같은 것을 거부하고 ① 은 그 플러그에 접속하지 않는다.
엔진이 일부러 끝났으면(engine.json 의 `exit`) 풀린다. 머리글의 '미등록 감지' 수도 같은 것을 뺀 수다.

**감지 재료 — 두 곳에서 온다.**

| 무엇 | 누가 · 언제 | 어디에 |
|---|---|---|
| 미등록 셀 | 엔진이 now.json 을 쓸 때마다(20초) — 어느 세트에도 속하지 않는데 30초(`heard_window_s`) 안에 들린 셀 | `data/now.json` 의 `heard` = `[{serial, ip, battery, rssi, age}]` (클라우드 bench_state 에도 실린다) |
| 플러그 | 감시자가 10분(`plug_scan_every_s`)마다 시험망을 찾는다 · 등록 화면의 '다시 찾기'가 즉석에서 한 번 | `data/plugs.json` = `{t, plugs:[{mac, ip, alias, on, watts, set}], by}` |

플러그를 찾을 때 **등록된 플러그(세트 1 — 엔진이 쓰는 중)에는 접속하지 않는다.** 방송 응답의 MAC·주소만 적고, 로그인해서 별명·전력을 읽는 것은 미등록 플러그뿐이다
(`plug.discover_plugs`). 찾다 실패해도 감시자는 계속 돌고, 실패한 시각과 이유를 plugs.json 에 남겨 다음 탐색은 10분 뒤에 한다.

미등록 감지는 신호등의 **세트 목록**에 "등록 필요"(노랑)로 한 칸 붙는다. 차선이 아니므로 시험대 전체 불과 Slack 알림은 올리지 않는다 — 운전 중인 세트와 무관한,
사람이 할 일의 안내라서다. 클라우드 결과판도 이 표시를 보여 주지만 등록 단추 대신 "등록은 제어 PC 결과판에서"라고 안내한다(검사와 저장이 제어 PC 안에서만 되므로).

**10초 검사 넷** (`cellbench/register.py` — 화면의 줄 순서와 같다)

| 검사 | 통과 조건 | 실패하면 |
|---|---|---|
| ① 플러그 응답 | 고른 MAC 의 플러그를 한 번 읽는다(재시도 없이 8초 안, `register_plug_timeout_s`). 이미 등록된 플러그면 접속하지 않고 실패 | 저장 안 함 |
| ② 셀 24대 수신 | 고른 24대가 모두 15초(`live_gap_alarm_s`) 안에 들렸다 — 엔진이 돌면 now.json 의 heard, 엔진이 없으면 셀 라이브를 10초 직접 듣는다(다른 프로그램이 포트를 쓰면 그 사유로 실패) | 저장 안 함 |
| ③ 다른 세트와 겹침 없음 | 시리얼·플러그 MAC 이 등록된 세트와 겹치지 않고, 붙인 뒤의 설정이 `config.validate` 를 통과한다 | 저장 안 함 |
| ④ 플러그 전력 24대 규모 **(가안)** | 켜짐이고 5~120 W(`register_power_min_w` · `max_w`) | **주의만 — 저장은 막지 않는다.** Dock 이 1.4 W 로 멈춰 있는 일(10-10 실측)은 등록이 아니라 운전 안전망(P4)이 첫 충전에서 끊었다 켜서 잡는다 |

- **PIN 이 있어야 저장·해제한다** — 원격 명령과 같은 PIN·같은 잠금이다(보안을 약하게 하지 않으려고 따로 두지 않았다). 그래서 **5번 틀리면 원격 제어(안전 정지 포함)도 10분 잠긴다** — 등록 화면이 이것을 미리 적고, 틀릴 때마다 남은 횟수를 보인다(응답의 `left`). PIN 이 없으면 저장 단추가 꺼지고 `tools/remote_setup.py` 를 안내한다. 플러그 '다시 찾기'는 읽기만이라 PIN 을 받지 않는다.
- **셀은 정확히 24대(`cells_per_set`)일 때만** 저장 단추가 켜진다. 잔량 20% 미만 셀은 '잔량 이상' 꼬리표만 붙고 고를 수 있다(등록과 상태는 별개의 일이다).
- 서버 API: `GET /api/register` · `POST /api/register/plugs/scan` · `POST /api/register {pin, plug_mac, serials}` · `POST /api/register/remove {pin, set_id}` (`serve_board.py`). 장비 통로는 `make_handler(devices=…)` 로 바꿔 끼울 수 있다 — 검사는 가짜 장비를 넘긴다.
- 화면 확인용으로 다른 설정 파일을 쓰려면 `python serve_board.py --data <폴더> --bench <파일>`.

## 다중 세트 운전 (구현됨 · 지금은 세트 2 운전이 막혀 있다)

설계와 근거는 [다중 세트 설계 명세서](docs/design/multi-set-plan.md)가 정본이다. 여기서는 쓰는 법만 적는다.

**한 줄 요지.** 세트 1 만 운전하면 엔진은 지금 길 그대로 돈다(단일 모드). 세트 k 가 아래 관문을 모두 지나면 엔진이 세트 1 의 다음 만충 경계에서
스스로 다시 시작해 세트마다 실행기를 스레드로 돌린다(다중 모드). **짝 이상이 하나라도 보이면 등록된 모든 플러그를 켜고 운전 세트를 모두 세운다.**

| 세트 k 가 운전 목록에 드는 관문 | 지금 상태 |
|---|---|
| bench.json 의 그 세트 줄에 `"run": true` (결과판 · PIN) | 사람이 켠다 |
| 짝 검증 통과 — `data/set{k}/pair.json` 의 지문이 지금 플러그 MAC · 시리얼 · 등록 시각과 같다 | 보정 전에는 판정 검증이 열리지 않는다 |
| 보정 실측(U2) 끝 — `config.PAIR["calibrated"]` | **아직 아니다** |
| 클라우드 스키마 판 2 (마이그레이션 `20261010174625_bench_multi_set.sql` 적용, U1) | **적용하지 않았다** |

그래서 지금은 세트 2 를 등록해도 돌지 않는다 — `set_not_ready`(경고, 기록만)가 사유가 바뀔 때 한 번 남는다.

**모든 모드에 들어간 안전 장치** (정상 운전에서는 발동하지 않는다 · 명세 3-6):

| 장치 | 발동 조건 (가안) | 하는 일 |
|---|---|---|
| 충전 쪽 하락 | 플러그 켜짐 · 10 W 이상인데 20분에 셀 중앙값 2 %p 넘게 하락 | 짝 이상 → 등록된 모든 플러그 켬 · `exit=failsafe` |
| 방전 중 상승 | 플러그 꺼짐인데 20분에 2 %p 넘게 상승 | 같다 |
| 방전 시작 대조 | 끈 뒤 30분에 3 %p 도 안 내려감 | 같다 |
| 운전하지 않는 세트 교차 | 엔진이 끈 뒤 그 세트 셀이 내려감(끄기 전에는 멈춰 있었음) — 등록 세트가 둘 이상일 때 | 같다 |
| 방전 7시간 | 기준선에 닿지 않음 | 충전으로 넘긴다 · `discharge_timeout`(조치) |

**보는 법 (지금 상태에서 확인할 수 있는 것)**

- **어디서:** 결과판(제어 PC) → 관제 → 세트 2 카드("운전 대기") → 세트 2 화면의 '짝 검증' 카드
- **무엇을 하면:** 세트 2 를 등록해 둔 채 PIN 을 넣는다
- **무엇이 보이나:** '운전 관문' 다섯 줄(보정 실측 · 짝 검증 · 클라우드 판 · 설정 · 운전 켜기 — 각각 열림 · 닫힘 · 모름)과 '운전 켜기 잠김' 사유. '짝 검증' 단추는 잠김(점선), '기록 전용 보정'을 누르면 무엇을 얼마나 하는지(추출 · 준비 방전 · 켜고 끄기 · 약 40분 ~ 최대 3시간 더) 확인 상자가 먼저 뜬다. 보낸 뒤 엔진이 집기 전에는 '요청 취소'로 멈춘다

**짝 검증** (엔진 안에서만 — 셀 라이브 포트를 엔진이 독점하므로). 결과판 세트 k 화면에서 요청하면 엔진이 20초 안에 집어 간다:
세트 k 셀 추출 · 삭제 → (필요하면) 70 % 까지 준비 방전 → 빠른 검증(켬 3분 · 끔 5분) → 패턴 검증(5분씩 켬 · 끔 다섯 번). Pk 하나만 만지고
어떤 길로 끝나든 Pk 를 켠다. 결과는 `data/set{k}/pair.json`. API: `GET /api/pair?set=k` · `POST /api/pair {pin, set, action: start|abort, mode: verify|calib}` ·
`POST /api/run {pin, set, on}` (켜기는 짝 통과가 있어야 한다). 세트 지정 원격 명령은 `POST /api/control {cmd, pin, set}` — 운전 중이 아닌 세트는 거부한다.
세트 번호는 정수만 받는다(1.5 · "2a" 는 400). 다중 운전에서 전체 정지(세트 지정 없는 안전 정지)가 대기 중이면 세트 명령은 409 로 받지 않는다 —
같은 `data/control.json` 칸을 세트 1 명령이 덮어 전체 정지가 사라지지 않게. 운전 · 세트 정지 중인 세트의 짝 검증 시작도 409 다(먼저 운전 끄기).

**클라우드 결과판의 스키마 판 확인은 읽기 전용 RPC 다.** 클라우드 결과판은 새로 고칠 때마다 `POST /rest/v1/rpc/bench_schema_version` 을 부른다.
POST 지만 데이터를 바꾸지 않는다 — 함수가 `language sql immutable` 로 상수 `2` 만 돌려준다(마이그레이션 `20261010174625_bench_multi_set.sql`).
PostgREST(Supabase 의 REST 층)가 함수 호출을 POST 로 받기 때문에 POST 일 뿐이다. 함수가 없으면(마이그레이션 전) 404 이고 화면은 판 1 로 본다.

**파일.** 세트 1 은 `data/` 그대로, 세트 k 는 `data/set{k}/` 에 같은 이름. 다중 모드에서만 `data/beat.json`(엔진 심박) · `engine.json` 의 `mode` · `sets`.
세트 정지 표지 `data/hold` · `data/set{k}/hold`. 해제한 세트의 폴더는 `data/archive/set{k}-<시각>/` 로 옮긴다.

## 자동 합류 (PIN 한 번 — 보정 → 짝 검증 → 운전 켜기 → 다음 경계 합류)

**한 줄 요지.** 결과판 세트 k 화면의 **'자동 합류 시작'** 단추 하나(PIN)가 아래 단계를 시간 맞춰 끊김 없이 잇는다. 사람이 기록을 분석해
`PAIR["calibrated"]` 를 고치지 않는다 — 문턱은 보정 기록에서 엔진이 **보수적으로** 도출하고, 애매하면 정하지 않고 멈춰 알린다. 세트 1 은 건드리지 않는다.
엔진 안에서만 돈다(셀 라이브 포트 독점). 코드: `cellbench/onboard.py`(순서 · 상태) · `derive.py`(문턱 도출, 순수) · `verifier.py`(한 단계의 실행).

| 단계 | 하는 일 | 걸리는 시간 | 실패하면 |
|---|---|---|---|
| (a) 사전 확인 | 세트 k 셀 24대가 들리고 플러그를 읽을 수 있나 · 다른 검증이 없나 · 운전 목록에 없나 | 즉시 | 시작하지 않고 이유를 `onboard.json` 에(`refused`) |
| (b) 보정 기록 | 셀 추출 · 삭제 → (70 % 를 넘으면) 준비 방전 → 켬 · 끔 · 켬 · 끔 · 켬 · 끔 · 켬 5분씩 기록(`calib_<시각>.csv`). 세트 1 단계 전환과 겹치면 미룬다(최대 1시간) | 약 45분 (+ 준비 방전 최대 3시간) | 플러그 k 를 켠 채 멈춤 |
| (c) 문턱 도출 | 기록에서 판정 문턱을 정해 `data/set{k}/pair_thresholds.json` 에 근거 숫자와 함께 남긴다 | 즉시 | `inconclusive` 로 멈춤 · 대조군이 플러그를 따르면 짝 이상(모든 플러그 켬) |
| (d) 짝 검증 | 도출한 문턱으로 빠른 + 패턴 검증. 추출은 다시 하지 않는다 | 약 35분 | 실패면 운전을 켜지 않는다 · 짝 이상 → 등록된 모든 플러그 켬 |
| (e) 운전 켜기 | 운전 관문(보정 · 짝 · 클라우드 판 · 설정)을 보고 열려 있으면 `bench.json` 의 `run: true` 를 원자적으로 쓴다(결과판 '운전 켜기'와 같은 `config.set_run`) | 즉시 | 관문이 닫혀 있으면 켜지 않고 멈춤 |
| (f) 합류 | 세트 1 의 다음 만충 경계에서 엔진이 스스로 다시 시작해(재구성) 세트 k 가 운전 목록에 들고, **첫 방전을 시작하면 합류 완료** | 최대 약 7시간 (한도 12시간) | 한도를 넘거나 관문이 다시 닫히면 `run` 을 되돌리고 멈춤 |

각 전환마다 Slack 1건: `onboard_start` · `onboard_calib_done` · `onboard_verified` · `onboard_run_on` · `onboard_joined`(노랑) · `onboard_failed`(빨강 — 이유와 플러그 k 상태).
상태는 `data/set{k}/onboard.json`(단계 `step` · 시작 `started` · 결과 `result` · 이유 `why`)에 원자적으로 쓰이고 결과판이 보여 준다.
`result` 는 진행 중이면 `null`, 끝나면 `joined` · `failed` · `inconclusive`(판정 불가) · `aborted`(멈춤 · 엔진 재시작) · `refused`(시작 안 함).

**문턱 도출 규칙 (`derive.derive_thresholds`, 상수는 `config.DERIVE`).** 켬 · 끔 전환마다 셀별 r = 켬 구간 기울기 − 끔 구간 기울기(%/분)를 잰다.
세트 k 의 응답 하한(셀 24대 중 최소 · 전환 중앙값)과 대조군(세트 1 등 세트 k 밖의 셀)의 변동 상한(|r| 의 95 % 분위 · 무리 중앙값의 최댓값)을 구한 뒤,
문턱 = **응답 하한의 50 %** 와 **변동 상한의 3배** 중 큰 쪽(더 엄격한 쪽) · 절대 하한(r 셀 0.10 · r 중앙값 0.15 · 다른 무리 0.05 · Δ 0.15) 이상.
다음 중 하나라도 해당하면 **도출하지 않고 멈춘다**: 표본이 모자람 · 세트 셀이 하나라도 무반응(ρ 0.85 · 응답 · 켬끔 차 중 하나라도 모자람) · 응답이 대조군 변동의 4배에 못 미침 ·
대조군이 구간 사이에 흔들림(세트 1 단계 전환 등) · 세트 k 밖의 셀이 플러그를 따라 움직임(= 짝 틀림, 이때는 짝 이상과 같은 안전 동작).
`PAIR["calibrated"]`(전역) 상수는 고치지 않는다 — 세트 k 의 '보정 끝'은 `pair_thresholds.json`(state=derived · 지문 일치)으로 판정하므로 수동 경로는 달라지지 않는다.

**보는 법**

- **어디서:** 결과판(제어 PC) → 관제 → 세트 k 카드 → 세트 k 화면의 '짝 · 운전' 카드
- **무엇을 하면:** PIN 을 넣고 '자동 합류 시작' → 확인 상자(단계 · 소요 시간 · 위험)에서 '실행'
- **무엇이 보이나:** 카드 맨 위에 '자동 합류 진행 중 · 보정 기록 → 문턱 도출 → 짝 검증 → 운전 켜기 → 합류 기다림', 도출한 문턱 한 줄, 단계마다 Slack. 끝나면 '합류 완료'(또는 실패 이유)

**실패했을 때 할 일.** Slack 의 `onboard_failed` 와 카드의 '합류 이유'를 읽는다. 플러그 k 는 켜져 있다(감시자의 세트 지키기도 지킨다).
`refused`: 이유(셀이 안 들림 · 플러그 응답 없음)를 고치고 다시 누른다. `inconclusive`: 이유의 code 를 본다 — 무반응 셀이면 그 셀이 다른 Dock 에 꽂혔는지,
대조군이 흔들렸으면 세트 1 이 조용할 때(방전 중간) 다시. `failed` + 짝 이상: 케이블 · 플러그 별명을 실물로 확인한다(등록된 모든 플러그를 켜고 시험 프로그램이 멈춘다).
운전 관문이 닫혀 멈췄으면(예: 클라우드 판 2 확인 전, U1) 짝 검증 통과는 남는다 — 관문이 열린 뒤 다시 누르면 24시간 안에는 운전 켜기부터 이어 간다.
엔진이 도중에 다시 시작되면 `aborted` — 합류 기다림 단계만 이어 가고 나머지는 사람이 다시 누른다.

**세트 지키기 (감시자).** 엔진이 도는 동안 운전하지 않는 등록 세트(검증 · 자동 합류 보정/검증 중이 아닌)의 플러그를 감시자가 10분마다 읽어 꺼짐이면 켠다.
엔진이 `now.json` metrics 의 `registered_heard`(세트별 들린 셀 수) · `registered_batt_med`(잔량 중앙값)를 더하고(세트 1 만 등록이면 칸 없음), 그 세트 셀이
15분 넘게 하나도 안 들리면 신호등 '플러그' 차선이 노랑으로 "세트 k 셀이 15분 넘게 안 들림 — 방전돼 꺼졌을 수 있다. Dock 버튼 · 충전 확인"(`set_silent`, Slack).
셀이 안 들리는 동안에는 플러그를 끊었다 켜지 않는다. 셀이 들리고 중앙값이 만충(97 %)이 아닌데 전력이 20 W 이하인 읽기가 3번 연속이면 30초 끊었다 켠다(세트마다 1시간에 2번).

**충전 중 교체.** `tools\restart_at_boundary.ps1 -InCharge` — now.json 단계가 `CHARGE` 일 때만 즉시 교체한다(추출 · 예비 충전 · 플러그 켜기 · 방전 · 복구 대기는 거부, 종료 코드 2).
새 엔진은 시작할 때 '방전은 끝났고 충전 중에 끊긴 사이클'(discharge · cells 파일은 있고 cycles.csv 에 줄이 없다)을 cycles.csv 에 복구 행(`note=restart_in_charge`, 충전 칸은 빈칸)으로 쓰고
새 사이클 번호를 그 다음으로 이어 센 뒤 `--precharge` 로 충전을 이어 간다 — 감시자가 되살린 엔진도 같은 길을 탄다(`record.recover_cut_charge`). 방전 중 · 추출 중 끊김은 기존 동작이다.
